opt-in or partial), **Open/by-design** (accepted tradeoff, explicit non-goal or product decision,

## Decided: accepted tradeoffs (moved out of "Open, undecided" — a call was made, not a code fix)

| ID | Summary | Decision |
|---|---|---|
| OPEN-5 | Sender gets no notification when a `token_pending` entry silently expires (24h TTL) without ever reaching the recipient. | **Decided 2026-09-25: won't fix, kept as-is.** The only way to notify the *sender* is for the server to learn who the sender is — directly against the point of anonymous-token routing (the server deliberately never learns this for `anon_message`; see [THREAT_MODEL.md § E](THREAT_MODEL.md#e-compromised-or-malicious-server-operator)'s sealed-sender note). Explicitly chosen: preserve anonymity over adding structure/complexity to recover this case. Real-world impact assessed as low: the common case (recipient reconnects within the 24h window) redelivers automatically and transparently on `subscribe_tokens`, no user action needed; the message only truly vanishes if the recipient's device is unreachable for a full 24 continuous hours (lost/dead device, long connectivity gap, reinstall under a new identity) — and even then, the sender already sees the same ambiguous "stuck on single checkmark, never reaches delivered/read" signal every mainstream E2EE messenger gives for a long-offline contact, and already has a manual resend action (`chatContextResend`) available for exactly that situation, cause-agnostic. The gap is invisibility of the specific cause, not user friction — accepted. Revisit only if a future anonymity-preserving repair mechanism (e.g. an anonymous, unlinkable "delivery failed" callback) is designed; none is planned today. |

**Certificate pinning, resolved:** checked `NetworkConfig.kt` and `MessengerService.kt`'s
`buildOkHttpClient()`. Pinning is scoped to exactly one hardcoded hostname
(`NetworkConfig.SERVER_HOSTNAME`, the project's own official server) via a compile-time
`NetworkConfig.CERT_PIN` constant, and is applied conditionally
(`if (CERT_PIN.isNotEmpty() && SERVER_HOSTNAME.isNotEmpty())`) — OkHttp's `CertificatePinner` only
enforces the pin for connections to that specific hostname. **A self-hosted server the user adds at
runtime is a different hostname and gets no pinning at all** — it's validated through the normal
system CA trust store, same as any other HTTPS connection. This is a reasonable, deliberate scope
(there's no way to pre-pin an arbitrary self-hosted deployment's certificate without some
out-of-band provisioning step, which doesn't exist today) — not a bug, but worth stating plainly
rather than leaving "certificate pinning" as an unqualified claim that a reader might assume covers
every server a user connects to.

`finally` blocks (json, gzip, derived key, password chars) — those call sites were switched to
`SecureMemory` for consistency, not because they were wrong. `CryptoManager` keeps no in-memory key
cache (it reads from the Keystore or encrypted prefs per operation), so there is nothing there to
scrub. `deleteAllSessions()` already wiped chain keys, skipped-message keys and, when the DH ratchet
was active, root and ratchet keys. `allowBackup="false"` in the manifest, so no wipe can be undone
through Android cloud backup. EC `KeyPair`s held in `currentSpk`/`opkPool` cannot be scrubbed in
process — the private keys are provider-owned objects with no working `destroy()` — so dropping the
reference is the most that is available there; recorded under S10-5 rather than claimed as solved.

## S11. Attachment-bearing backups, format version 8 (2026-11-06)

Follow-up to S10-9, which recorded that a backup carried message text only.

| # | Finding | Severity | Status | Regression test |
|---|---|---|---|---|
| S11-1 | S10-9 resolved: attachments can now be exported (opt-in checkbox). Implemented as a new container rather than inline Base64 in the v7 JSON, because inlining would have held four copies of an already 4/3×-inflated payload in heap — an OOM on the feature whose purpose is not losing data | — | **Fixed** — `BackupContainer.kt`, streamed, 1 MiB chunks, peak memory independent of total size | `BackupContainerTest.kt` (12) incl. a 2.5-chunk blob round-trip |
| S11-2 | Frame reordering / splicing would otherwise be possible: a container of independently-encrypted frames under one key lets an attacker who holds the file permute them, delete one, or serve attachment A's bytes as attachment B | Would have been High | **Prevented by construction** — AAD `"SRBK8|<frameIndex>|<label>"` binds each frame's position and identity. | S11-3 | Truncation at a frame boundary leaves every surviving frame individually authentic, so GCM alone cannot detect it — a cut file would restore half an attachment and report success | Medium | **Fixed** — per-blob trailer frame declares total plaintext length; a short blob throws | `BackupContainerTest` |
| S11-4 | The 4-byte frame length is read before it can be authenticated — the only such value in the format. Unbounded, it is an arbitrary-allocation primitive for a hostile file | Medium | **Fixed** — bounded to `CHUNK_SIZE + 4096`, rejected before allocating | `BackupContainerTest` |
| S11-5 | Attachment paths in a backup are attacker-controlled strings that import would otherwise hand to `File()` | Medium | **Prevented** — only the blob id travels; the importing device recomputes the path via `SecureFileStorage.blobFile`, and ids containing `/`, `\` or `.` are rejected at both export and import. | S11-6 | An attachment whose blob file is already gone (expired or deleted) would, if skipped, shift every *later* attachment onto the wrong blob id during import | Medium | **Fixed** — written as a zero-length blob so the frame sequence stays aligned with the declared order; import deletes the empty file and counts it as failed. Export reports the count to the user | — |
| S11-7 | A v8 export interrupted mid-write leaves a file that looks like a backup and fails when it is needed. It cannot be rolled back through the ContentResolver reliably | Low | **Open, surfaced not fixed** — the error message states plainly that the file is incomplete and must be deleted. A proper fix is write-to-temp-then-rename, which SAF does not offer for a user-chosen location |  — |
| S11-8 | Frame sizes are visible to anyone holding the file, leaking the number of attachments and their approximate sizes | Informational | **Open, inherent** — v7 already leaks total size, and padding multi-gigabyte media to a fixed size is not a real option. | S11-9 | v8 cannot be read by the Desktop client, so a user who ticks the box and relies on it for cross-platform recovery is stuck | Low (availability) | **Open, mitigated** — the option is off by default, the checkbox subtitle states the incompatibility, and the guide article repeats it. This path is now disabled when attachments are on (for memory reasons), but the premature delete affects the metadata-only path too.

Changes made specifically so the project can be submitted to a funded security audit and to
Google's MASA validation. Grouped separately because they are governance and process, not findings
in the running code — except S12-1, which was both.

| # | Item | Status |
|---|---|---|
| S12-1 | **S9-1 closed: certificate pinning is no longer inert.** Pins now come from the `SUBROSA_CERT_PINS` build property, a `gradle.taskGraph.whenReady` check **fails any release build with an empty pin list**, malformed pins fail at configuration time, and a single pin logs a warning (one pin makes key loss an unrecoverable outage for every install).
