## Threat Model

Subrosa is designed to protect against the following adversaries:

### In scope

| Adversary | Capability | Mitigation |
|---|---|---|
| Network attacker | Intercept and modify traffic | TLS + E2EE (certificate pinning is implemented but **not active for the official server** — see [Certificate Pinning](#certificate-pinning)) |
| MITM with forged CA | Install user CA, proxy TLS | Intrusion detection (USER_CA + PROXY) |
| Server compromise | Server operator reads DB | E2EE; server stores no plaintext |
| Physical device theft | Offline extraction of filesystem | EncryptedSharedPreferences + SMK layer |
| Forensic examination | Cold-boot, JTAG, software extraction | SMK requires password; decoy mode |
| Coercion (legal demand) | Compelled decryption | Panic password, wipe, decoy mode |
| Shoulder surfing | Screen visibility | `FLAG_SECURE` screen protection |
| Debugging / dynamic analysis | Attach JDWP, logcat | Anti-debugging checks, Paranoid Mode log suppression |
| Rooted device attacker | Read prefs as root, bypass keystore | SMK PBKDF2 layer; root detection warning |
| Stolen private key (via backup theft, or raw extraction from a compromised device bypassing the backup flow entirely) | Register a new device under the victim's fingerprint, hijack their live session | Mandatory device-gated TOTP — see [Device-Gated TOTP](#device-gated-totp--recovery-codes) |

### Out of scope

| Scenario | Reason |
|---|---|
| Endpoint compromise (full device root + live RAM dump) | Key material resident in the running process — SMK while unlocked, and separately, SPK/OPK/PQ private keys/Double Ratchet session state for the lifetime of the process regardless of app-lock state (see "SPK / OPK private keys and Double Ratchet session state" below) — unavoidable for either without killing the process entirely |
| Server-side traffic correlation | Timing and metadata on the wire |
| Coercion of the recipient | Recipient device not controlled |
| Supply-chain attack (malicious build) | Requires independent APK verification |

## Cryptographic Design

### Key Hierarchy

```
User Password
    │
    ▼ PBKDF2-SHA256 (300 000 iter, 32B salt)
Password-derived Key (PDK)
    │
    ▼ AES-256-GCM
enc_smk_pwd  ──────────────────────────────────┐
                                               │ decrypt
AndroidKeyStore AES-256 ("beacon_smk_wrap")    │
    │                                          │
    ▼ AES-256-GCM                              ▼
enc_smk_ks  ──────────────────────► Storage Master Key (SMK)  [in memory]
                                               │
                    ┌──────────────────────────┼─────────────────────┐
                    ▼                          ▼                     ▼
           EC identity privkey          Group AES keys       Chat message blobs
         (beacon_ec_keys_enc)              (groups)         (chat_storage_encrypted)
```

### Identity Keys

Each user has one EC key pair on the P-256 (secp256r1) curve. This key pair serves as:
- The long-term identity key in X3DH (sender and recipient)
- The signing key for invite codes and authentication challenges

The private key is stored in `EncryptedSharedPreferences("beacon_ec_keys_enc")` under the key `"ec_priv"`. The stored value is:
- `"smk1:" + Base64(iv[12] + AES-256-GCM(privKey.encoded, smk))` when SMK is set up
- `Base64(privKey.encoded)` for legacy entries (migrated on next read when SMK is unlocked)

The public key is stored as plain Base64 and transmitted to the server on registration.

### Message Encryption

One-to-one messages are encrypted with AES-256-GCM:

```
plaintext
    │
    ▼ AES/GCM/NoPadding
    │  key:  session key (from Double Ratchet)
    │  iv:   12 random bytes (from Cipher.init)
    │  tag:  128-bit authentication tag (appended)
    ▼
iv[12] || ciphertext || tag[16]
```

The ciphertext blob is transmitted inside the `"text"` field of the JSON message, encoded as Base64. (Corrected 2026-11-03 — this said `"data"`, which is a real field but a different one: `"data"` carries the handshake challenge and chunked media payloads, not 1:1 message ciphertext. Harmless in itself, but it sent anyone tracing the protocol on the wire to the wrong field.)

### Traffic Analysis Resistance (Padding)

Even with the content fully encrypted, the *size* of a ciphertext leaks information: a server (or anyone observing the connection) can often guess message content from length alone — a 40-byte ciphertext is very unlikely to be anything but "ok" or "hi", a 2KB one is probably a paragraph, a photo-sized one is obviously a photo. Two independent, stacked padding layers close this:

1. **Content-level padding** (`CryptoManager.kt`, `addPadding`/`removePadding` for text, `addFilePadding`/`removeFilePadding` for files): before encryption, 128–512 random bytes (1024–4096 for files/images) are prepended to the plaintext, with a short length prefix so the real content can be recovered exactly after decryption. This runs inside `aesEncrypt`/`aesDecrypt` and `encryptFile`/`decryptFile`, so every 1:1 message, file, and image gets it automatically — there is no code path that skips it.
2. **Packet-level bucketing** (`MessengerService.kt`, `addPadding(packet: JSONObject)`): independently of the above, the *entire outgoing WebSocket JSON envelope* (ciphertext plus all the surrounding protocol fields) is padded with a random string in a `_p` field up to the next multiple of 512 bytes, right before every `sendWs(...)` call — direct messages, anon-routed messages, and cover-traffic noise packets alike.

The two layers serve different purposes: layer 1 hides how much *content* a message actually contains (a one-word reply and a full paragraph become indistinguishable in ciphertext length once padded to the same bucket), while layer 2 hides the *packet* size on the wire, including protocol overhead, so an eavesdropper watching raw WebSocket frames without any awareness of the JSON structure still can't fingerprint message types by size. Both were self-verified with dedicated checks in `CryptoManager.kt`'s test routines, surfaced in Security Diagnostics.

This defends against **length-based** traffic analysis. It does not defend against **timing-based** correlation (see cover traffic under item 12 in Known Limitations) or the **social-graph** metadata the server inherently sees (item 1).

### Forward Secrecy

X3DH-style initial key agreement:

1. Recipient publishes on server: `IK_B` (identity key), `SPK_B` (signed prekey), `OPK_B` (one-time prekey).
2. Sender fetches the bundle and computes:
   ```
   DH1 = ECDH(IK_A, SPK_B)
   DH2 = ECDH(EK_A, IK_B)       ← EK_A: ephemeral key, discarded after send
   DH3 = ECDH(EK_A, SPK_B)
   DH4 = ECDH(EK_A, OPK_B)      ← OPK_B: one-time, deleted by server after fetch
   master_secret = KDF(DH1 || DH2 || DH3 || DH4)
   ```
3. `master_secret` seeds the Double Ratchet.

Each subsequent message ratchets forward. Precisely (external review 2026-08-28, CRYPTO-09 — the
previous "does not compromise past or future" phrasing was too absolute, per the Double Ratchet
spec's own compromise model): compromising the current ratchet state does not reveal *already-
deleted* past message keys (those are wiped after use — see `SecureMemory.wipe` calls throughout
`CryptoManager.kt`/`SessionKeyManager.kt`). Future confidentiality is *not* immediate or
unconditional — an attacker holding the current chain key can compute upcoming message keys until
an uncompromised Diffie-Hellman ratchet step introduces new secret entropy the attacker doesn't
have. This is standard Double Ratchet behavior, not a bug, but "future keys are also safe" as a
blanket claim overstated the model.

The server is notified when OPK supply drops below the watermark (`OPK_LOW_WATERMARK = 5`) and prompts the client to upload more bundles.

### Post-Quantum Hybrid Key Agreement

X3DH's `master_secret` above is classical ECDH (secp256r1), which is vulnerable to a future quantum computer running Shor's algorithm — and more urgently, to **harvest-now-decrypt-later**: an adversary recording today's traffic could decrypt it retroactively once quantum computers mature. This matters for privileged/legal communication with a decades-long confidentiality requirement.

To close this, the prekey bundle also carries an **ML-KEM-768** public key (FIPS 203, NIST-standardized), signed with the same ECDSA identity key as the SPK and rotated on the same 7-day cadence:

```
pq_shared_secret = ML-KEM-Decapsulate(pq_private_key, pq_ciphertext)
master_secret     = KDF(DH1 || DH2 || DH3 || [DH4] || pq_shared_secret)
```

Only the *initial* X3DH root key needs this hardening — every subsequent Double Ratchet root key is `HKDF(dhOutput, salt=previousRootKey)`, so deriving it requires the actual secret previous root key, not just breaking that step's classical DH. A quantum adversary who breaks every individual ratchet-step DH still cannot advance the chain without the root, and the root is only recoverable by breaking **both** the classical and the ML-KEM component. This is the same reasoning behind Signal's PQXDH.

**Scope of this guarantee, stated precisely (external review 2026-08-28, CRYPTO-07 — the previous
phrasing implied a stronger, general property than the design actually provides):** this protects
against harvest-now-decrypt-later for a *passive* adversary who only records ciphertext traffic and
never compromises either endpoint or the session's root key. It is **not** a general continuous
post-quantum post-compromise security property. If an adversary compromises a device or its root
key *now* (by any means — not necessarily quantum) and continues recording that session's traffic,
a future quantum computer does not need to break ML-KEM at all — it already has everything a
classical attacker with the same compromise would have. Continuous protection against a
compromise-now-decrypt-later scenario (as opposed to harvest-now) would require a full
post-quantum ratchet construction (e.g. Signal's own PQ ratchet extensions), which this project
does not implement. ML-KEM-768 itself is a sound, NIST-standardized (FIPS 203) primitive choice —
the caveat above is about the boundary of what the *protocol construction* guarantees, not about
the primitive.

The same hybrid treatment is applied everywhere else a shared secret is derived via one-shot ephemeral ECDH outside the ratchet chain: the pre-session/legacy message fallback, `edit`, group key distribution, and image/file/voice encryption. A bundle or handshake missing the PQ component is rejected outright rather than silently accepted as classical-only, to close the obvious downgrade attack (a malicious server stripping the field).

**Known limitations:**
- Sessions established *before* this upgrade have a purely classical root key that cannot be hardened retroactively — only a fresh handshake protects a conversation going forward. See the migration note in `SessionKeyManager`.
- The anonymous-mailbox first-contact bootstrap message (see [README.md](README.md#privacy-architecture)) stays classical-only — an invite code carrying a ~1.2 KB ML-KEM key would make invite links/QR codes impractically large. The Double Ratchet session established immediately after it is full PQ-hybrid.

### Group Key Exchange

*Corrected 2026-08-28 (external review, CRYPTO-04): this section previously described a
classical-only `ECDH → AES-GCM(groupKey, KDF(shared))` wrap, contradicting the Post-Quantum Hybrid
section above, which claims group key distribution gets the same hybrid treatment as everything
else. Checked against the actual code — `GroupManager.encryptGroupKeyForMember()` calls
`CryptoManager.encrypt()`, the same one-shot hybrid function `sendImage`/`sendFile` use. The
Post-Quantum Hybrid section's claim was correct; this section's pseudocode was stale.*

Each group has a 256-bit random AES key (`groupKey`). It is distributed out-of-band to each member
individually, using the same hybrid ECDH+ML-KEM one-shot encryption as file/image transfer:

1. Admin calls `generateGroupKey()` → `KeyGenerator.getInstance("AES")` seeded with `SecureRandom()`, 256-bit output (functionally a fresh random AES-256 key either way).
2. For each member M, `GroupManager.encryptGroupKeyForMember()` calls `CryptoManager.encrypt()`:
   ```
   ephemeralKeyPair = generate fresh EC keypair
   classicalSecret  = ECDH(ephemeralKeyPair.private, M.identityPublicKey)
   (pqCiphertext, pqSharedSecret) = ML-KEM-768-Encapsulate(M.pqPublicKey)
   combinedSecret   = classicalSecret || pqSharedSecret
   aesKey           = HKDF-Extract-then-Expand(combinedSecret, info="BeaconECDHpq")
   encKey           = AES-256-GCM(groupKey, aesKey)
   wire format       = [ephemeralPublicKey][pqCiphertext][iv || encKey || tag]
   ```
   Breaking either the classical ECDH or the ML-KEM component alone does not recover `groupKey` —
   same reasoning as the Post-Quantum Hybrid section above, applied to group-key wrapping instead
   of message content.
3. `{memberId, encKey}` pairs are sent to the server in the `group_create`/`group_member_added`
   message; the server delivers each `encKey` only to the corresponding member (it cannot decrypt
   any of them — it never has any member's private key).
4. Member calls `GroupManager.decryptGroupKey(encKey)` → `CryptoManager.decrypt()` (the matching
   hybrid decrypt, using the member's own identity + PQ private keys) → `groupKey`.

Group messages:
```
plaintext
    │
    ▼ AES/GCM/NoPadding (key = groupKey, iv = random 12B)
iv[12] || ciphertext || tag[16]
```

Group message **authenticity is separate from the AES-GCM encryption**: since every member shares
the same symmetric `groupKey`, AES-GCM alone only proves *some* group member produced the
ciphertext, not *which* one. Every `group_message`/`group_reaction`/`group_key_rotation`/etc. is
additionally signed with the sender's own ECDSA identity key (`CryptoManager.sign`), verified
against their known identity public key on receipt before the message is trusted — a member cannot
forge a message under another member's name, even knowing the shared `groupKey`. (External review
2026-08-28, CRYPTO-05, confirmed by reading the code — this was already implemented, just not
documented here.)

**Key rotation happens on both member *removal* and member *addition*** (fixed 2026-09-25, closing
[KNOWN_SECURITY_ISSUES.md OPEN-7](KNOWN_SECURITY_ISSUES.md) — until then it was removal-only, and
this section said so explicitly; CRYPTO-08's 2026-08-28 correction was about documenting that gap
accurately, not about it being closed). On either a removal or an addition, the admin generates a
fresh `groupKey`: on removal it's redistributed to the remaining members, with the removed member
explicitly excluded (see [Known Limitations #15](#known-limitations) for the bug this closed, and
[THREAT_MODEL.md § C](THREAT_MODEL.md#c-removed-group-member) for the regression test covering it);
on addition, the new member receives the *fresh* key via their own `group_create` invite, and every
other existing member receives it via the same per-member-encrypted `group_key_rotation` message the
removal path already used — reusing that exact mechanism rather than inventing a second one
(`GroupInfoScreen.kt`'s add-member handler on Android; `WebSocketClient.addGroupMember()`/the new
shared `sendGroupKeyRotation()` helper on Desktop). A newly-added member therefore can no longer
decrypt group ciphertext from before they joined, closing the backward-secrecy gap this section used
to describe.

When stored locally, `groupKey` is wrapped with the SMK (`"smk1:"` prefix) if unlocked, otherwise
stored as plain Base64 (still inside `EncryptedSharedPreferences`/Keystore-backed storage — see the
[Double Encryption at Rest](#double-encryption-at-rest-smk) section for exactly what this fallback
does and doesn't lose).

### Double Encryption at Rest (SMK)

Sensitive at-rest values receive a second encryption layer on top of `EncryptedSharedPreferences`
**when the SMK is unlocked**. Corrected 2026-08-28 (external review, CRYPTO-02 — the previous
"all sensitive values" phrasing directly contradicted this same document's own Group Key Exchange
and SPK/OPK/session-state sections a few paragraphs down, both of which describe a plain-Base64
fallback for writes made while locked): the SMK layer is the normal case, not an unconditional
guarantee. See "Value Wrapping" below for exactly when the fallback applies and what it does and
doesn't lose — the fallback value is still inside `EncryptedSharedPreferences`/AndroidKeyStore-backed
storage, so this is "single-layer instead of double-layer protection" for that value until the next
unlock triggers the documented self-healing re-wrap, not plaintext-on-disk.

#### SMK Generation

On first registration:
```kotlin
val smk  = SecureRandom().nextBytes(32)   // 256-bit random key
val salt = SecureRandom().nextBytes(32)   // 256-bit random salt

enc_smk_pwd = AES-256-GCM(smk, PBKDF2(password, salt, 300_000, 256))
enc_smk_ks  = AES-256-GCM(smk, keystoreKey)   // AndroidKeyStore AES-256
```

Both ciphertexts are stored in `EncryptedSharedPreferences("smk_config")`.

#### SMK Unlock Paths

| Path | How | When |
|---|---|---|
| Password login | PBKDF2(password, salt, 300 000) → decrypt `enc_smk_pwd` | Every login |
| Biometric login | AndroidKeyStore key → decrypt `enc_smk_ks` | Biometric success |
| App re-lock unlock | Same two paths | After timeout / screen-off lock |

PBKDF2 operations run on `Dispatchers.IO` — never on the Main thread.

#### SMK Lock

`StorageKeyManager.lock()` fills the in-memory `smk` byte array with zeros and sets it to `null`. Called:
- Before `isAppLocked = true` (screen-off, auto-lock timeout)
- As the first operation in `WipeManager.wipe()`

#### Value Wrapping

```
wrapBytes(bytes):
    iv = random 12 bytes
    ct = AES-256-GCM(bytes, smk, iv)
    return "smk1:" + Base64(iv || ct || tag)

unwrapBytes(stored):
    if not stored.startsWith("smk1:"):
        return Base64.decode(stored)      # legacy fallback
    blob = Base64.decode(stored[5:])
    iv = blob[0:12]
    ct = blob[12:]
    return AES-256-GCM-decrypt(ct, smk, iv)
```

Transparent migration: existing unprotected values are read as legacy Base64 without error. On next write, the value is wrapped. The EC private key uses eager re-wrap: if `StorageKeyManager.isUnlocked` but the stored value has no `"smk1:"` prefix, it is immediately re-wrapped on the first read.

#### SPK / OPK private keys and Double Ratchet session state — now wrapped too

**Previously not wrapped**, on the stated reasoning "needed at cold start before login." That reasoning didn't hold up against how the EC identity key already worked: the identity key faces the exact same requirement (it's needed to process incoming X3DH the moment a message arrives, possibly before the user has opened the app) and was already wrapped — the SPK/OPK/session-state omission was an inconsistency, not a deliberate design call, and was closed in `SessionKeyManager.kt`.

The key realization: none of this material is re-read from disk on every message. It's loaded once into memory at `SessionKeyManager.initialize()` (current SPK, the OPK pool, all session states) and kept resident in the running process from then on — locking `StorageKeyManager` only zeros the in-memory SMK, it doesn't touch anything `SessionKeyManager` already loaded. So wrapping this data only matters at the *narrow* moment of a genuine process cold start (device reboot, or the OS killing the background service under memory pressure) that happens to land before the user has unlocked in that new process — not "every message while locked," which would have been a real regression.

Implementation, mirroring the existing EC-identity-key pattern exactly:
- **SPK, previous-SPK, current/previous PQ KEM private keys, OPK pool entries**: each wrapped individually via `StorageKeyManager.wrapBytes()`/`unwrapBytes()` when writing/reading the Base64 string stored in `EncryptedSharedPreferences("session_keys_secure")`, same as `CryptoManager`'s identity key.
- **Double Ratchet session state** (`SessionState` — chain keys, root key, ratchet keypair, skipped-message keys): the whole per-contact JSON blob is wrapped as one unit (`"smk1:"` + `Base64(AES-256-GCM(json_bytes))`) rather than field-by-field, since it's already persisted as a single JSON string per contact.
- **The cold-start-while-locked case is handled explicitly, not left to throw**: a new `tryUnwrapKeyBytes()` helper catches the "SMK is locked" exception and returns null instead of propagating it, so a process cold start before unlock degrades to "this particular SPK/OPK/session isn't available yet" (logged, skipped) rather than crashing `SessionKeyManager.initialize()` outright — regenerating a fresh SPK in that situation was considered and rejected, since the real key is still on disk and just temporarily inaccessible; regenerating would gratuitously invalidate an already-published bundle.
- **`SessionKeyManager.reloadSessionsIfNeeded()`**, called from `StorageKeyManager.unlockWithPassword()`/`unlockWithKeystore()` right after a successful unlock, re-attempts anything that came up unavailable during the locked cold-start window. Idempotent and cheap to call on every unlock, including the common case where everything already loaded fine.

**Desktop had the identical gap, checked and fixed the same day**: Desktop's `SessionKeyManager.kt` mirrors Android's almost line-for-line (same SPK/OPK/PQ-KEM/session-state persistence shape, just via `DesktopStorage.get/put` instead of `EncryptedSharedPreferences`), and Desktop's own `StorageKeyManager` already had the identical `wrapBytes`/`unwrapBytes`/`isUnlocked` primitives — already used for group keys (`GroupManager.kt`) and messages (`ChatStorage.kt`), just never extended to session keys, same oversight as Android. Fixed with the same approach: `wrapKeyBytes`/`tryUnwrapKeyBytes` helpers, wrapped SPK/prev-SPK/PQ-KEM/prev-PQ-KEM/OPK-pool entries and the whole per-contact session-state JSON blob, and `reloadSessionsIfNeeded()` wired into both `StorageKeyManager.unlockWithPassword()`/`unlockWithKeystore()`. Compiles clean.

Note: unlike Android, Desktop's own identity key (`CryptoManager.kt`) is *not* SMK-wrapped — it uses a separate protection mechanism instead (`DesktopKeyStore`, a machine-bound PKCS12 keystore), an intentionally different design already in place before this pass, not part of this gap.

### Password Hashing

Application passwords are hashed before storage:

```
v2:<saltB64>:<hashB64>
  salt = SecureRandom().nextBytes(16)
  hash = PBKDF2WithHmacSHA256(password, salt, iterations=100_000, keyLen=256)
```

On login, the stored hash is compared to the freshly derived hash. Auto-migration from legacy `SHA-256(password)` (format without `"v2:"` prefix) is performed on the first successful login.

### Backup Encryption

Backup files use a deliberately different, memory-hard KDF from the password hash above — Argon2id, not PBKDF2 — since a backup file is something an attacker who obtains a copy can brute-force offline indefinitely, with no rate limiting and no device involved at all:

```
salt    = SecureRandom().nextBytes(32)
key     = Argon2id(backupPassword, salt, memoryKB=65_536, iterations=3, parallelism=1, keyLen=32)
iv      = SecureRandom().nextBytes(12)
payload = AES-256-GCM(serialized_data, key, iv)   // 128-bit tag
file    = base64(salt[32] || iv[12] || payload)
```

Two properties of the resulting file that are easy to get wrong, so they are stated explicitly:

- **It survives every wipe level.** The file is written through SAF to a location the user chooses, outside app storage; `WipeManager` cannot reach it and does not try. A panic wipe therefore does not remove a backup, and a user who wipes should delete their backup copy separately. The user-facing guide says this.
- **Contents are text only unless attachments were requested.** A v7 export stores `text`/`isOwn`/`timestamp` per message and nothing else. Attachments require the export option described next.

### Version 8 Container (attachments)

Added 2026-11-06. Selecting "include attachments" at export switches to `BackupContainer`, a framed, streamed format. Leaving it off produces the unchanged v7 string, which is the format the Desktop client can import.

```
"SRBK8\n"                    6 bytes, ASCII magic
salt                        32 bytes
frame*                       repeated to EOF

frame := iv(12) ‖ len(4, big-endian) ‖ GCM(type(1) ‖ body, key, iv, aad)
aad   := "SRBK8|<frameIndex>|<label>"
label := "meta"  |  "blob:<blobId>"
type  := 0x00 metadata (gzipped JSON)  |  0x01 attachment chunk  |  0x02 attachment trailer
```

Design points and the reasoning behind each:

- **Streamed, 1 MiB chunks.** Peak memory is one chunk and its ciphertext regardless of total size. Base64-ing attachments into the v7 JSON would have held four copies of an already 4/3×-inflated payload — an `OutOfMemoryError` on the one feature whose purpose is not losing data. For the same reason, the destination URI is chosen *before* the export runs, and "share via another app" is not offered with attachments on (it would require a second full copy in the cache directory).
- **One key for the file.** `Argon2id(password, salt, 64 MiB, t=3, p=1)` — identical parameters to v7, so offline brute-force cost is unchanged. Deriving per frame would allocate 64 MiB hundreds of times.
- **AAD binds position and identity.** An attacker holding the file cannot reorder frames, delete one from the middle, or move attachment A's bytes onto attachment B's id — each changes the frame index or the label, and GCM rejects it. Regression tests cover all three separately (`BackupContainerTest`).
- **Truncation is the one authentic-looking edit**, because every surviving frame is still individually valid. Hence the `0x02` trailer declaring the blob's total plaintext length; a cut file fails instead of restoring half an attachment.
- **The frame length is the only value read before it can be authenticated.** It is bounded to `CHUNK_SIZE + 4096` so a hostile file cannot drive an arbitrary allocation.
- **Fresh 96-bit IV per frame** from `SecureRandom`, under one key — a test asserts no IV repeats across a file, since reuse under GCM is catastrophic rather than cosmetic.
- **Attachments are re-encrypted on restore.** The bytes travel protected by the backup password and land under the importing device's Keystore key via `SecureFileStorage`. That is what makes them portable at all — the on-disk `.enc` files are bound to the Keystore of the device that wrote them. It also means a restored attachment is exactly as protected as one received normally.
- **Paths are never carried.** Only the blob id (the filename stem) travels; the importing device recomputes its own path with `SecureFileStorage.blobFile`. A path out of a backup file is an attacker-controlled string, and ids are rejected if they contain `/`, `\` or `.`.
- **Blob order is declared in the metadata**, and import walks that list rather than re-deriving the order from the message arrays. An attachment whose source file was already gone is written as a zero-length blob rather than skipped, so the frame sequence stays aligned with the list — skipping it would shift every later attachment onto the wrong id.

What leaks to anyone holding the file: the frame sizes, hence the number of attachments and their approximate sizes. v7 leaks total size already, and padding multi-gigabyte media to a fixed size is not a real option. Someone holding the file already knows they hold a messenger backup.

### Read-Only Archive (offline history)

Added 2026-11-06. `importBackup()` is the only other way into a backup's contents and it is identity-level and destructive: it wipes the identity currently on the device and requires the TOTP secret or a recovery code. That is the wrong tool for "the server is gone and I need to read one conversation", so `BackupArchive` + `ArchiveScreen` provide a strictly weaker path:

| Property | How it is enforced |
|---|---|
| Writes nothing | `BackupArchive` takes no `Context` anywhere in the file — structurally unable to touch prefs, the Keystore, `filesDir` or the live identity |
| Restores no keys | `parse()` reads `username`, `display_name`, contacts, groups and message text. `ec_private_key`, `spk_private`, `pq_private`, `groupKey`, `anon_tokens` are present in the decrypted JSON and deliberately dropped; a regression test asserts none of them reach the rendered model |
| Needs no server | Decryption is local; this is the point of the feature |
| Needs no TOTP | Nothing is being restored, so there is no identity to second-factor. The backup password alone gates it, exactly as it gates offline brute force of the same file |
| Plaintext lifetime is bounded | Dropped on `Lifecycle.ON_STOP` as well as on dispose, along with the password field and the container key. Nothing is ever read whole — the file is streamed from its `content://` URI and never copied into app storage |
| Attachments are extracted one at a time | `Archive.extract()` re-walks the container per attachment. That is O(file) rather than a seek *by design*: decrypting frame *n* requires having counted every frame before it, and an offset index would let a tampered file redirect a read to a frame that authenticates at a different position. Images are capped at 24 MiB for inline display; "save" hands the bytes to the SAF picker, which is the only route out of the screen and requires an explicit action. There is deliberately no "open with", which would hand a decrypted file to an arbitrary third-party app |
| Unavailable under duress | Decoy mode routes to the fake inbox and never renders this branch, so a coerced unlock cannot use the app as a decryption oracle for a backup file the adversary is holding |

A wrong password and a damaged/foreign file return the same result (`BadPasswordOrCorrupt`) — the GCM tag failure cannot distinguish them, and the UI does not guess.

### Key Material in Memory

`SecureMemory.wipe()` overwrites a buffer with random bytes, then `0xFF`, then zeros, and finally stores a byte of it into a `@Volatile` field.

The pass count is not the point and is not a disk-wipe analogy — DRAM has no residual state to recover a previous value from, and one overwrite destroys the secret as completely as thirty. Two things in that sequence do real work:

- **The volatile store.** `fill(0)` on a buffer that is never read again is a dead store, and both HotSpot and ART are permitted to delete it. A volatile write has observable effects under the JMM and cannot be elided, so it is what makes the overwrite actually happen.
- **The random pass.** An all-zero 32-byte buffer is a valid AES key, a valid HMAC key and a valid chain key, so a use-after-wipe bug keeps producing output under a key an attacker can guess. Passing through random bytes means such output does not match anything precomputable. The zero pass runs last so a leaked buffer does not read as fresh entropy.

What is wiped: the SMK (on `lock()`, the first operation of any wipe), PBKDF2 inputs and outputs in `StorageKeyManager.deriveKey()`, every intermediate in `BackupManager` (JSON, gzip stream, derived key, password chars), session chain keys, skipped-message keys, root and ratchet keys, and the ML-KEM-768 private key.

What cannot be wiped in process, stated rather than glossed:

- `SecretKeySpec` clones its input and AOSP does not implement its `destroy()`; the provider may clone again inside `Cipher.init`. Those copies are unreachable and wait for GC.
- EC `KeyPair`s (`currentSpk`, the OPK pool) hold provider-owned private key objects with no working `destroy()`. Dropping the reference is all that is available.
- `String` cannot be reliably wiped. `SecureMemory.wipe(String)` attempts reflection on `String.value` and is expected to fail silently on ART (blocked non-SDK member since API 28); even on success, mutating a `String` can corrupt a shared backing array, and the string is rarely the only copy. The real fix is for passwords never to be `String` — `CharArray` from the text field down — which is an outstanding UI-layer change, not a solved problem.

Because of the above, the primary defence against in-memory key recovery remains `Process.killProcess()` at the end of `WipeManager.hardWipe()`, which releases the entire heap. Scrubbing is what carries `wipeForDecoyKeepAlive()`, the duress path, where the process deliberately stays alive to keep the decoy on screen.

## Authentication

### Server Handshake

Authentication is challenge-response via ECDSA. The server never stores or transmits the password — the password only ever protects local storage (SMK), it is never part of the network protocol at all:

1. Client connects; server sends `{type: "challenge", data: "<32 random bytes base64>"}`.
2. Client signs the challenge bytes with its EC private key (SHA256withECDSA) and replies `{type: "challenge_response", public_key, signature}`.
3. Server verifies the signature against the supplied public key and, on success, replies `{type: "handshake_ok"}`, remembering the verified key bytes for the next step.
4. Client sends a separate `{type: "register", name, public_key, device_id, ...}` — `public_key` here is checked to match exactly the key that was just proven in step 2/3 (identity-binding fix, see [SECURITY_CHANGELOG.md](SECURITY_CHANGELOG.md) item 14); a mismatch is rejected outright, closing the connection.
5. The server derives the fingerprint (`SHA-256(public_key)[:8]`), which is also the username, and applies any additional gates before accepting the registration — in order: optional one-time access-code allowlist for private/business deployments (`access_code_required` on failure), then device-gated TOTP if the account has it enabled (`totp_required` on failure — see [Device-Gated TOTP](#device-gated-totp--recovery-codes) below). Only once these pass does the server accept the connection, resolve `session_conflict` if another device is already registered under this fingerprint, and later send `{type: "turn_config", ...}` for call signaling.

**Fingerprint length, analyzed (external review 2026-08-28, AUTH-01):** 8 bytes = 64 bits. Targeted
preimage (find a keypair matching one specific victim's fingerprint) stays infeasible at 2^64.
Birthday-bound *collision* resistance is the relevant number for a shared identity-namespace,
though: ~2^32 (about 4.3 billion) registered fingerprints before an accidental collision becomes
likely. That's far beyond this product's realistic scale, so not a practical concern today. Worth
noting as a real (if currently theoretical) scaling ceiling: `register()` stores/overwrites
`clients[fingerprint]`'s public key on every registration with no check against a previously-seen
public key for that fingerprint, and `registered_fingerprints.fingerprint` is a SQLite `PRIMARY KEY`
— so a genuine collision (two different keypairs hashing to the same 8 bytes) would let the second
key silently overwrite/impersonate the first in `clients` (in-memory). Not fixed, since it isn't
reachable at realistic scale — flagged for the record, not treated as an active vulnerability.

**Corrected 2026-11-03**: this paragraph previously added that "the DB insert would just no-op
(`INSERT OR IGNORE`) rather than surface the collision at all". That is wrong three ways, all in
the pessimistic direction. (a) There is no `INSERT OR IGNORE` —
`_db_admit_new_fingerprint_sync()` uses a plain `INSERT`, and its enclosing
`except Exception: conn.rollback(); raise` propagates rather than swallows. (b) A collision never
reaches that insert: the same `BEGIN IMMEDIATE` transaction first runs
`SELECT 1 FROM registered_fingerprints WHERE fingerprint = ?` and returns `"exists"`, so the
second registration is **refused**, atomically against a concurrent claimant. (c) Device-gated
TOTP (items 17/18 of `SECURITY_INVARIANTS.md`) independently blocks the impersonation described:
a colliding attacker's `device_id` is necessarily new for that fingerprint, which requires a valid
TOTP or recovery code *plus* a device-local signature whose keypair never leaves the original
device and is excluded from the identity backup. The conclusion above ("not an active
vulnerability") was right; the reasoning given for it was not, and the real posture is better than
this entry described.

Handshake timeout: 15 seconds.

Session conflict: when a second `device_id` registers for the same fingerprint, the server sends `{type: "session_conflict", ts}` to the existing session (and a push notification via FCM if the old session isn't live to receive the WebSocket message). The existing client disconnects and notifies the user. The server's `connect()` reconnect loop on both clients does not currently distinguish `session_conflict` from an ordinary network disconnect, so both devices can end up in a "reconnect war" alternately displacing each other — device-gated TOTP (below) prevents this for any device the fingerprint hasn't registered with a valid code, but does not resolve the race for two device_ids the account has already registered.

### Device-Gated TOTP + Recovery Codes

Since 2026-08-10, TOTP is a **mandatory** step immediately after registration, not opt-in — the client won't proceed to the chat list until it's set up. It serves two purposes with the same secret:

- **Backup import gate**: `BackupManager.importBackup()` requires a valid current TOTP code if the backup being restored has `totp_enabled=true` — closes the "file + password alone is enough to hijack the identity" gap for anyone who also enabled this. Also required to *export* a new backup at all (`BackupScreen.kt`/Desktop equivalent won't produce a new file without TOTP enabled first).
- **Device-gated server registration**: the server (`user_totp_secrets`, `server.py`) requires a valid TOTP code in `register()` whenever `device_id` is new for that fingerprint — exactly the condition that would otherwise open the reconnect-war/session-hijack window described above. A reconnect from an already-known, already re-authenticated `device_id` never needs a code, so this doesn't affect ordinary mobile-network reconnect churn. **Both "new" and "already-known" are now decided from durable state and a device-local cryptographic credential, not from a live session or a bare client-supplied string — see below, rewritten 2026-09-03.**

The secret is generated client-side, shown once with an `otpauth://` URI for any standard authenticator app, and is never included in the backup file itself (only the boolean `totp_enabled` flag is) — deliberately, so a stolen backup + password alone can't also recover the TOTP secret.

**Device gating, rewritten 2026-09-03 (external review, two rounds) — from "session-only" to durable, cryptographically-bound device authentication.** The original design had two real gaps, found and closed in sequence:

*Round 1 — the "new device" check itself was RAM-only.* `is_new_device` used to be derived by comparing the incoming `device_id` against whatever was currently sitting in the in-memory `clients[username]` entry for a live session. That entry is gone the instant the real owner's app closes, or the server restarts — at which point `existing` is `None`, `is_new_device` comes out `False`, and TOTP is never even asked for. An attacker holding a stolen identity private key (backup theft, or raw extraction bypassing the backup flow entirely) could pass `challenge_response` — which only proves *key* possession, nothing about TOTP — and `register()` straight through with any `device_id`, any time the real owner wasn't actively connected. In practice this meant TOTP was only ever protecting against a *second* device connecting *while* the real owner's session was still live — not the stolen-key scenario in the threat model table above, the one that matters most. Fixed with a durable, per-fingerprint device allowlist (`authorized_devices` table: `username`, `device_id`, `device_pubkey`, `added_at`) — checked instead of the live `clients` dict, and — same principle as the fingerprint-registration-cap fix below — never written to until *after* TOTP/recovery has actually succeeded for that device.

*Round 2 — a durable allowlist keyed only on `device_id` is still a bearer-token check.* `device_id` is a client-supplied string, sent in the clear on every `register()` call — nothing about it is secret. Durability alone closed the live-session gap, but an attacker with the stolen identity key who also learned (not hard — it's an identifier, not a secret) a legitimate `device_id` could present that same string and have the durable allowlist answer "already authorized," skipping TOTP a second way. Closed by requiring an actual credential behind the string: each device generates its own separate EC keypair (P-256, same curve as the identity key), stored locally and **deliberately excluded from the identity backup** — so restoring an identity backup onto a fresh device correctly starts that device with no device keypair of its own, and it must earn a pin the normal TOTP-gated way under a fresh `device_id`, exactly like any other never-seen device. Every `register()` — not just first enrollment — must now carry a signature (ECDSA, SHA-256) over `SUBROSA_DEVICE_V1 || challenge || username || device_id`, using the same fresh, per-connection `challenge` bytes the identity-key handshake already uses (so a captured signature from a past connection is worthless against a new one). Once a `device_pubkey` is pinned to a `(username, device_id)` pair, it is **never replaced** by any code path — a `device_id` presented with a different key than the one on file is refused outright (`device_auth_failed`), never treated as "unknown device, please prove TOTP" (which would let a successful TOTP/recovery-code compromise re-pin someone else's `device_id` to an attacker-controlled key). A device that loses its local keypair (app reinstall, data wipe) is expected to register under a fresh `device_id` and go through the TOTP-gated first-time pin again, not reclaim the old one.

**Deployment status**: server-side, Android, and Desktop are all live (`desktop/src/main/kotlin/com/bcon/desktop/DeviceKeyManager.kt`, wired into `WebSocketClient.register()`). **Corrected 2026-09-25**: this paragraph previously said Desktop didn't implement the device-keypair/signature side yet — that was true when written, but Desktop's port was completed some time later and this note was never updated (`docs/KNOWN_SECURITY_ISSUES.md` OPEN-9, closed as a documentation-drift instance, not a live gap). Full protocol detail (message format, server-side state machine, the exact bug each round closed): `PROTOCOL_STATE_MACHINE.md` §8; standalone checkable invariants: `SECURITY_INVARIANTS.md` #17–18.

**Decryption-failure fail-open — fixed 2026-09-04.** If `TOTP_SECRET_ENCRYPTION_KEY` was set when a secret was stored but missing, wrong, or invalid at a later boot, the server used to silently drop that one account out of `user_totp_secrets` — indistinguishable from an account that never enabled TOTP at all, despite the decrypt function's own comment claiming this "fails closed." Since `register()`'s TOTP gate is exactly `username in user_totp_secrets`, a stolen identity private key was again sufficient to register a new device for that account the moment the encryption key was unavailable; `totp_setup` would also have let a caller re-provision a fresh secret with no proof of the old one. Now `_totp_decrypt_from_storage()` raises instead of returning an empty string, and `_db_load_totp_sync()` (run synchronously at startup, before the server binds/serves) propagates that — an account whose secret can't be decrypted refuses the entire server's startup, not just that account's protection. Standalone invariant: `SECURITY_INVARIANTS.md` #32.

**Online brute-force of the TOTP code itself — fixed 2026-09-04.** Neither `register()`'s unknown-device path, `totp_setup` re-enrollment, nor `totp_disable` had a dedicated attempt limit — `totp_verify_and_consume()`'s anti-replay only rejects an already-used counter, so a wrong 6-digit guess cost an attacker nothing and consumed nothing; `rate_limit_check()` doesn't cover these message types, and is RAM-only where it applies elsewhere. A 6-digit code (10⁶ space) is realistically guessable online without a durable cap. Added `second_factor_guard` (SQLite, per-fingerprint): 5 attempts per rolling 5-minute window, then a 15-minute lock, checked and spent *before* the code is verified at all three sites — recovery codes go through the same gate too, even though their own 80-bit entropy isn't realistically brute-forceable, so they can't become a lower-friction bypass or a free DB-DoS path. Standalone invariant: `SECURITY_INVARIANTS.md` #33.

**Server-wide lock DoS during TOTP verification — fixed 2026-09-04.** `register()` used to `await` the TOTP/recovery-code check and `db_bind_device_pubkey()`/`db_authorize_device()` (all SQLite calls) from *inside* `async with lock:` — the one server-wide lock nearly every other coroutine in the server also needs. A purely per-connection proof check for one account became a server-wide availability bottleneck under SQLite contention: everything else waiting on that lock had to wait for whichever TOTP/DB call was in flight. Split into two phases — Phase 1 runs every security/DB proof with no lock held; Phase 2 (`async with lock:`) is RAM-only (`clients`/`authenticated_users` commit, session-conflict eviction scheduled via `asyncio.create_task()`, which schedules rather than awaits). Standalone invariant: `SECURITY_INVARIANTS.md` #34.

**Setup/disable commit atomicity — fixed 2026-09-04.** `totp_setup`/`totp_disable` used to reply `totp_setup_ok`/`totp_disable_ok` before their writes actually landed — each fired two independent, unawaited `create_task()`s (secret row, recovery-codes rows) *after* the client had already been told the operation succeeded. A crash in that window could leave an account the client believes is TOTP-protected with no `user_totp` row at all (silent downgrade back to disabled on next restart), or a freshly-enrolled secret with no matching recovery codes (permanently unrecoverable). Both paths now commit secret + recovery codes (or their deletion) in one atomic SQLite transaction, `await`ed, before either RAM (`user_totp_secrets`) is updated or the `_ok` reply is sent. Full detail: `PROTOCOL_STATE_MACHINE.md` §9; standalone invariant: `SECURITY_INVARIANTS.md` #30.

**Recovery codes**: 8 one-time codes are generated and shown once when TOTP is enabled (`totp_setup_ok.recovery_codes`), the same model as GitHub/Google 2FA. Format and entropy, stated explicitly (external review 2026-08-28, AUTH-02 — this section previously said only "the server stores SHA-256 hashes," without specifying the code's own entropy, which is what actually determines offline brute-force resistance against a stolen copy of those hashes): each code is `secrets.token_hex(10)` — **80 bits**, formatted as four 5-hex-character groups (`XXXXX-XXXXX-XXXXX-XXXXX`) for readability. Bumped from an original 40 bits (`secrets.token_hex(5)`) after this same external review flagged that 40 bits against a single unsalted SHA-256 hash is crackable offline in well under a minute on one consumer GPU — a real, live weakness given a stolen/unencrypted server DB (`totp_recovery_codes` table) exposes exactly these hashes; see the composite-attack discussion in [THREAT_MODEL.md § F](THREAT_MODEL.md#f-attacker-with-offline-access-to-the-servers-database-stolen-disk-backup-hosting-provider-access). The server stores only the SHA-256 hash of each code (`totp_recovery_codes` table) — a single unsalted hash is an acceptable choice for an 80-bit *server-generated* random token (not a user-chosen low-entropy password), since the entropy itself, not hash cost, is what needs to resist brute force here. A recovery code can substitute for a TOTP code in `register()` if the authenticator is lost; redeeming one is atomic (`UPDATE ... WHERE used = 0`, so two simultaneous redemption attempts of the same code can't both succeed — regression-tested, `test_recovery_code_consumed_exactly_once_under_concurrency`).

**"Recovery-code takeover window" — fixed 2026-08-30.** A successful recovery-code redemption used to immediately revoke the account's entire TOTP secret and *every other* unused recovery code, not just the one spent — meaning any future new-device registration under that fingerprint needed no code at all, ever, until someone happened to notice and manually re-enrolled from a trusted device. That's a much wider window than "one recovery event" implies: an attacker holding the stolen identity private key plus a single leaked recovery code could use it once, and from that point on every future device registration under the victim's fingerprint was completely ungated — not just the one the attacker registered. Now, redemption consumes only the single code used; the secret and the remaining codes stay live, so every subsequent new-device registration still needs a valid TOTP code or one of the dwindling recovery codes, never nothing. This does not weaken the "lost the authenticator" recovery path: `totp_setup` (re-enrollment) and `totp_disable`, which previously refused outright whenever a secret was already on file, now also accept a valid unused recovery code as authorization to replace or remove it — so a user who just proved (via the recovery code that got them in) that they lost their authenticator can immediately spend one more code to properly re-enroll with a fresh secret, rather than being stuck re-spending codes on every future device until they run out. The existing `session_conflict` mechanism already notifies whoever holds the account's other live session in real time whenever any new device successfully registers, recovery-code-based or not — that detection path needed no change.

**Known limitation**: accounts created before 2026-08-10 were not migrated to mandatory TOTP retroactively — this only applies to registrations after that date. There is currently no recovery path if both the TOTP secret *and* all recovery codes are lost (by design, same rationale as the backup password having no recovery mechanism below) — the account's fingerprint becomes permanently unable to register a new `device_id` until an operator manually clears its `user_totp_secrets` row.

### Invite Codes

Invite codes are ECDSA-signed binary blobs, prefixed and Base64url-encoded (no padding):

```
bc:<base64url(payload)>
```

Payload layout (current format, version `0x03`):

```
version(1B) | ts(4B) | nonce(8B) | mailboxTag(16B) | fp(8B) | ecPoint(65B) | nameLen(1B) | name(nameLen B) | rawSig(64B)
```

- `ecPoint` is the raw 65-byte uncompressed EC point (X9.62 `0x04 || X || Y`); the P-256 X.509 SPKI header is reconstructed on parse rather than carried in the invite.
- `rawSig` is the raw `r || s` ECDSA signature (32 bytes each, sign-corrected), not DER — converted to/from DER only around the JCA `Signature` API.
- Version `0x02` (legacy, no `mailboxTag` field) is **rejected outright** on parse — it used to be accepted for backward compatibility, with a client-side fallback to a direct, server-visible `get_key` lookup naming the target fingerprint when no mailbox tag was present. That fallback silently dropped the anonymous-mailbox guarantee with no warning to the user; found while building `SCENARIOS.md`'s "First contact" scenario as a branching tree and cut entirely the same day, on both platforms (Desktop's version of the bug was worse — it called the direct lookup unconditionally, on every contact add, not only when a tag was missing). A code in the old format now just fails to parse, same as any other invalid code.

Signed payload (everything before `rawSig`): `version | ts | nonce | [mailboxTag] | fp | ecPoint | nameLen | name`.
Signature algorithm: SHA256withECDSA with the inviter's identity key.
TTL: 7 days from `ts`.

Verification:
1. Reconstruct the EC public key from `ecPoint` (prepend the fixed X.509 header).
2. Recompute `fp` = first 8 bytes of SHA-256(X.509-encoded public key), compare.
3. Check `ts` + 7 days > now.
4. Verify ECDSA signature over the signed payload.

Desktop and Android share this exact binary format (byte-for-byte, including the DER↔raw signature conversion and EC-point reconstruction) — see [SECURITY_CHANGELOG.md](SECURITY_CHANGELOG.md) item 13 for the history of that port.

## Anti-Forensics

### Paranoid Mode

When enabled:
- `Log.d`/`Log.i`/`Log.w` calls that go through the `BLog` wrapper are suppressed (`BLog` checks `ParanoidMode.isEnabled`). **Corrected 2026-09-25**: this used to say "all" such calls are suppressed — in practice at least a dozen files still call `android.util.Log` directly rather than routing through `BLog`, including diagnostic logging inside `CryptoManager.kt`'s `decrypt()` (SPK epoch IDs, PQ public-key hashes, wire-format lengths — no raw key material) that predates a `BAD_DECRYPT` bug investigation. None of that raw-`Log` output is suppressed by Paranoid Mode. Tightening `BLog` coverage (or lint-banning raw `Log.*` calls outside it) is tracked as follow-up, not yet a numbered Known Limitation.
- `logcat -c` is executed to clear the current process logcat buffer.
- `IntrusionDetector.scan()` is run on every `onResume()` (on `Dispatchers.IO`).
- On threat detection (`handleThreat()`):
  1. Logcat cleared again.
  2. HTTP POST to user-configured alert URL (fire-and-forget coroutine).
  3. If "wipe on breach" enabled: `WipeManager.wipe(level)`.
  4. Otherwise: stealth mode (show `DecoyScreen`).

### Screen Protection

`WindowManager.LayoutParams.FLAG_SECURE` is applied to the main activity window. This prevents:
- Screenshots via the system screenshot shortcut.
- Screen recording apps capturing the window content.
- The app thumbnail appearing in the Recents screen.

### Anti-Debugging and Instrumentation Detection

**Corrected 2026-09-25** — this section previously described a JDWP-port socket probe that doesn't
exist, and undersold the actual detection surface, which is broader and covers instrumentation
frameworks, not just a debugger. All of the following are folded into `RootDetector.kt`'s single
`checkResult()` pass, not a separate pre-UI gate:
- `android.os.Debug.isDebuggerConnected()` — detects an attached JDWP debugger.
- `TracerPid` in `/proc/self/status` — detects ptrace attachment generally (catches native/`gdb`
  debugging that `isDebuggerConnected()` alone wouldn't).
- Frida instrumentation: a socket probe against `127.0.0.1:27042` (Frida's well-known default listen
  port — not a JDWP port), a `/proc/self/maps` scan for Frida-related library strings, and a running-
  process scan.
- Xposed-framework detection: bridge presence, known package names, `/proc/self/maps` scan.

Results feed a two-tier `WARNING`/`DANGER` severity (`RootLevel`) with granular `RootReason` codes,
surfaced via the same `AlertDialog`s as root detection below — not a silent pre-UI terminate.

### Root Detection

### Certificate Pinning

OkHttp's `CertificatePinner` pins the server's SPKI. A connection presenting an unexpected key is rejected even if its certificate is signed by a trusted CA.

**Corrected 2026-11-06 — it was inert until this date.** `NetworkConfig.CERT_PIN` was an empty `const val`, nothing assigned it, and the pinning branch in `MessengerService.buildHttpClient()` was guarded by `CERT_PIN.isNotEmpty()`. So the branch never executed and every release fell back to the system CA store, while the code read as though pinning were in force. Compounding it, a second complete pinning implementation (`CertificatePinner.kt`) held a real-looking SPKI pin and was called from nowhere, so a reader could not tell which of the two was live. The dead file has been deleted. Recorded as S9-1 / S12-1 in [KNOWN_SECURITY_ISSUES.md](KNOWN_SECURITY_ISSUES.md).

Current design, shaped so that "configured but inert" cannot ship:

- Pins come from the `SUBROSA_CERT_PINS` build property (`local.properties` or environment), comma-separated, in OkHttp's `sha256/BASE64` form — same handling as the signing credentials, and for the same reason: per-deployment, not repository content.
- **A release build with an empty pin list fails.** A `gradle.taskGraph.whenReady` check throws before any release task runs, with the `openssl` invocations needed to compute a pin in the message. Debug builds are unaffected, because they legitimately talk to localhost, the emulator host and a test server. Override is `-PsubrosaAllowUnpinnedRelease=true`, deliberately verbose.
- Malformed pins fail at configuration time (`require(startsWith("sha256/"))`), rather than at the first connection attempt on a user's phone.
- A single configured pin logs a warning. **Pin the key, not the certificate**: generate the server keypair once, renew with `certbot --reuse-key`, and the SPKI hash survives every renewal. Ship a second pin from an offline backup keypair — with one pin, losing that key is a permanent outage for every installed copy, which is the failure mode that makes people disable pinning entirely.
- Belt-and-braces: a release build that somehow has no pins logs an error at client construction, so the state is visible in logcat rather than silent.

**Unavailable for the official server while it is CDN-fronted (found 2026-11-11).** Everything above describes a design that cannot currently be used for `api.subrosamessenger.com`, and the releases shipped so far are built with `-PsubrosaAllowUnpinnedRelease=true` because of it.

The reason is architectural, not an oversight in the pinning code. TLS for the official hostname is terminated by **Cloudflare**, so the key a client sees is Cloudflare's, not this project's. Checked against the live endpoint on both 443 and 8443: `issuer=C=US, O=Google Trust Services, CN=WE1`, `subject=CN=subrosamessenger.com`, 90-day validity, wildcard SAN — Cloudflare Universal SSL. Cloudflare rotates those certificates automatically and does **not** reuse the key, so the SPKI hash changes on every renewal.

The advice two bullets above — pin the key, renew with `certbot --reuse-key`, the hash survives — is correct only for a client that reaches this project's own nginx. No shipped client does. Pinning the key observed today would therefore break every installed copy within about three months: precisely the permanent-outage failure mode that bullet warns about.

Consequences, stated plainly rather than left implied:

- The threat-model row above listing "TLS + certificate pinning + E2EE" against a network attacker currently delivers TLS + E2EE. Pinning contributes nothing today.
- A network attacker who can obtain a certificate for `subrosamessenger.com` from any CA the device trusts is not stopped by pinning, because there is none. They are still stopped from reading message content, which is end-to-end encrypted with keys the transport never sees; what they gain is metadata and the ability to disrupt.
- Cloudflare itself terminates TLS and can therefore see all transport metadata. That is already recorded as an accepted trade-off for reaching users in networks where the origin IP is blocked — pinning would not have changed it.

The intended fix is a second hostname with Cloudflare proxying **disabled**, so clients reach nginx directly and present this project's own certbot certificate, pinned with `--reuse-key` for a stable hash; the CDN hostname stays as an unpinned fallback for networks that block the origin. That splits the two properties instead of trading one for the other, and fits the two-entrance arrangement the deployment already uses. Not implemented yet.

**Scope, stated explicitly (external review 2026-08-28):** the pin set is
tied to exactly one hardcoded hostname (`NetworkConfig.SERVER_HOSTNAME` — the project's own official
server). **A self-hosted
server a user adds at runtime is a different hostname and receives no pinning at all** — it's
validated through the normal system CA trust store instead. Deliberate scope, not a gap: there's no
mechanism today to pre-pin an arbitrary self-hosted deployment's certificate (would need some
out-of-band provisioning step — TOFU, QR-code-carried pin, etc. — none of which exist yet).

## Emergency Mechanisms

### Wipe Levels

| Level | Operations | Use case |
|---|---|---|
| `HARD` | Delete all prefs, files, databases, WebView data, AndroidKeyStore keys | Threat detected, border crossing |
| `NUCLEAR` | `HARD` + `ActivityManager.clearApplicationUserData()` | Maximum urgency; process is killed by system |

Exact scope of `eraseEverything()`, the single implementation all levels funnel through, in execution order:

1. `StorageKeyManager.lock()` — SMK overwritten in RAM via `SecureMemory` (see "Key Material in Memory" above), before anything else.
2. `PanicNotificationManager.dismiss()` — the notification outlives the process, and its DESTROY action stays functional if left behind.
3. Read out the decoy profile fields (only when `keepDecoyProfile`), before the storage holding them is destroyed. The calculator disguise is carried forward only if its unlock code survives alongside it — restoring `disguise=true` with no code would lock the user out of their own restored profile.
4. `SessionKeyManager.deleteAllSessions()` (chain keys, skipped-message keys, root/ratchet keys, ML-KEM private key) and `CryptoManager.deleteKeys()`.
5. AndroidKeyStore aliases: `_androidx_security_master_key`, `_androidx_security_crypto_master_key_`, `beacon_smk_wrap`.
6. Filesystem: `shared_prefs`, `filesDir`, `cacheDir`, `externalCacheDir`, `databases`, `app_webview`, `no_backup`, and the app-scoped external directory.
7. Stop `MessengerService`.
8. `UserStorage.reestablishDecoyProfile()` — into freshly created encrypted prefs, when a decoy profile was captured in step 3.

`hardWipe` = the above + `Process.killProcess()`. `wipeForDecoyKeepAlive` = the above, process left alive so the decoy stays on screen. `NUCLEAR` hands steps 5–7 to the framework via `clearApplicationUserData()`, which erases the whole data directory — so `NUCLEAR` and decoy survival are mutually exclusive by construction, and its `withDecoy` parameter governs only the fallback used when the framework call is unavailable.

**Not erased by any level**, documented because the opposite is a natural assumption:

- An exported backup file. It lives outside app storage, by design — see "Backup Encryption".
- Messages already delivered to contacts' devices.
- Nothing is recoverable through Android cloud backup: `allowBackup="false"`.

Deletion is `unlink`, not overwrite. The guarantee rests on the keys being destroyed, not on the blocks being unreadable — every file deleted above was encrypted under the SMK or the Keystore master key, both of which are gone by step 5.

A `SOFT` level existed briefly but was removed (`WipeManager.kt`) — it was never wired to any trigger, yet was shown to the user in `WipeSettingsScreen.kt` as if it were a working option ("Мягкий (SOFT)" / "Очищает кеш и оперативную память"), which was misleading in a security-critical settings screen rather than merely dead code. `HARD`/`NUCLEAR` were not affected by the removal.

`StorageKeyManager.lock()` is called as the very first operation of any wipe, ensuring the SMK is zeroed from memory before any other destructive step.

**Corrected 2026-11-05**: that was true of `WipeManager`'s paths but not of `MessengerService.performEmergencyWipe()` (the 5-volume-press trigger), which was a third hand-written copy of the wipe and called neither `lock()` nor `PanicNotificationManager.dismiss()`, and did not delete the `beacon_smk_wrap` Keystore alias the other paths delete. All three copies have since been collapsed into one implementation (`WipeManager.eraseEverything()`); `performEmergencyWipe()` now delegates to `hardWipe()`. The invariant holds on every path because there is only one path.

### Panic Password

The user can configure a secondary "panic password" in settings. Entering it instead of the real password shows the decoy immediately and destroys the real data behind it.

**Corrected 2026-11-05**: this section previously claimed the app "begins `WipeManager.wipe(HARD)` in the background" and "may display a fake loading screen to buy time". Neither was accurate — there is no fake loading screen, and the function called is a different one with deliberately different behaviour. What actually happens:

1. `PasswordGate.evaluate()` checks the panic password **before** the rate limiter and before the real password. That ordering is deliberate: under coercion the wipe must stay reachable even for an account currently locked out after failed attempts.
2. The screen switches to `DecoyScreen` straight away.
3. 400 ms later — just enough for the decoy to draw — `WipeManager.wipeForDecoyKeepAlive()` runs. Same erasure as `hardWipe()` but **without** killing the process, so the decoy stays on screen instead of the app dying in front of whoever triggered it. The job runs on a process-scoped `SupervisorJob`, not the composition's scope: on the latter, killing the activity inside that 400 ms window cancelled the wipe outright and left the real data intact.

The same password is also accepted on the app-lock overlay, which routes through `emergencyWipe(withDecoy = true)` → `hardWipe()` and *does* kill the process.

The panic password must differ from the login password, and is rejected at configuration time if it does not (`ProfileScreen`), with the mirror check when the login password is changed (`ChangePasswordScreen`). Because the gate checks panic first, an identical pair would silently turn every normal login into an irreversible wipe.

### Login Rate Limiting

`LoginAttemptManager` allows 3 attempts at the real password, then blocks for 5 / 15 / 30 / 60 minutes and finally indefinitely, escalating per block.

**Corrected 2026-11-05**: until this date none of that was in effect. `recordFailedAttempt()` and `recordSuccessfulLogin()` were not called from anywhere in the app, so the counter stayed at 0, `block_until` stayed at 0 and `canAttemptLogin()` always answered "yes" — login was unlimited-attempt, and `getRemainingAttempts()`/`isPermanentlyLocked()` were dead code. The app-lock overlay, a second password prompt reachable without restarting the app, did not call even the inert check. Both now go through `PasswordGate`, which owns the ordering (panic → lockout → real password), records outcomes, and runs both PBKDF2 passes on `Dispatchers.IO` instead of the main thread. Regression tests: `PasswordGateTest.kt`.

### Dead Man's Switch

A scheduled alarm (`AlarmManager.setExactAndAllowWhileIdle`) fires if the user has not performed a check-in within the configured interval (hours or days). On alarm:
1. `WipeReceiver` receives `DMS_FIRE`.
2. `WipeManager.wipe()` is triggered.

Normal check-in: user opens the app (automatic) or taps the manual check-in button. The last check-in timestamp is stored in `EncryptedSharedPreferences`.

`BootReceiver` restores the DMS alarm after device reboot.

### Decoy Mode

When `HARD` wipe is triggered with "post-wipe decoy" enabled:

1. Before deletion, the wipe reads out of `user_prefs`:
   - `username`
   - `password_hash` (the hash, not the password)
   - `user_id`
   - the calculator-disguise flag and its unlock code, when that disguise is active

   **Corrected 2026-11-03**: this list previously also claimed "a random selection of contact names". No contact names are saved, and `UserStorage.migrateDecoyState()` reads nothing else. The stale wording appears to describe an earlier design in which real contact names were carried across the wipe — worth correcting in this direction too, since the old text described a privacy weakness that does not exist.

2. Performs the full erasure.

3. Immediately afterwards, those fields are written back into freshly created `EncryptedSharedPreferences` together with `decoy_mode = true` (`UserStorage.reestablishDecoyProfile()`). The wipe destroyed both the Keystore master key and the prefs file, so this creates a new master key and a new file — indistinguishable from a first-run profile.

   **Changed 2026-11-05**: the hand-off used to go through `beacon_recovery`, a `MODE_PRIVATE` (i.e. **unencrypted**) SharedPreferences file holding `username`/`user_id`/`password_hash` until the next cold start, when `migrateDecoyState()` moved them across and cleared it. That file was itself the problem the decoy exists to avoid: a plaintext artefact named `beacon_recovery` containing a `password_hash` is direct evidence that a real account existed and was wiped. It was worst on the panic-password path, which never kills the process — the file sat there for the entire time the decoy was on screen, which is exactly the window in which someone else is holding the phone. Nothing writes it any more; `migrateDecoyState()` is kept only to drain a file left by an older build.

4. The decoy conversations are generated per install from a 32-byte seed (`DecoyData.kt`), not drawn from a hardcoded pool. See [ARCHITECTURE.md](ARCHITECTURE.md#decoydatakt). The dataset is pinned in memory for the life of the process, because the panic-password wipe deletes the seed from under a decoy that is already on screen — re-reading it would regenerate every contact and conversation in front of the person looking at them.

The decoy account cannot decrypt any real messages (all keys were destroyed). It provides plausible deniability against a cursory inspection or a coercing party demanding to see the device's *contents* — not against a forensic examination of the *device itself*: a sophisticated examiner may still find filesystem timestamps, journal entries, or flash wear-leveling patterns indicating a prior wipe occurred (see Known Limitations item 7). Deniability of what's on screen, not undetectability of the wipe.

## Session Security

- One active session per device per username (fingerprint).
- `device_id` is a UUID generated once per installation and transmitted on every authentication.
- If a second, previously-unseen `device_id` registers for the same fingerprint, the server sends `session_conflict` to the older session, which then disconnects and alerts the user — see [Device-Gated TOTP](#device-gated-totp--recovery-codes) for what gates that new `device_id` from registering in the first place.
- Session tokens are not stored; full ECDSA re-authentication occurs on each WebSocket connection.

## Known Limitations

*Fully resolved items are not listed here — see [SECURITY_CHANGELOG.md](SECURITY_CHANGELOG.md).
Numbering below has gaps where an item moved there; numbers are preserved rather than
renumbered so existing cross-references (this repo's own docs, `docs/KNOWN_SECURITY_ISSUES.md`'s
`KL-N` IDs) stay valid.*

1. **Server metadata**: The server sees message timestamps and, for anything still routed outside anon-token coverage, who communicates with whom. As of item 31, the `anon_message` payload itself no longer hands the server the sender/recipient pair in plaintext for the message types listed in item 12. As of item 32, the **connection that submits** an `anon_message` no longer has to be an authenticated, identity-bound socket at all — the operator can no longer read the sender off `clients[username]` for that connection the way it always could for the recipient side, closing what item 31 explicitly left open ("the server could still reconstruct it by correlating token-subscription records against usage"). See item 32 for the exact scope of what this does and does not cover — the recipient side (who currently owns a given token) is still identity-bound via `subscribe_tokens`, and first-contact/prekey-bundle fetch (item 11) remains identified in both directions. It does not know message content. **Length-based** traffic analysis is mitigated by the two-layer padding scheme (see [Traffic Analysis Resistance](#traffic-analysis-resistance-padding)), but **timing-based** correlation is not addressed by padding — see item 12 for what anon-token routing does and does not cover.

2. **SMK in memory — and the lock is evaluated on *resume*, not on screen-off.** Corrected 2026-11-03; this previously read "while the app is unlocked **and in the foreground**", which was wrong in two directions. Backgrounding the app does **not** zero the SMK: `onPause()` only records a timestamp, and `onStop()` locks only when the calculator disguise is enabled (off by default). Neither does the screen locking: the `ACTION_SCREEN_OFF` receiver's entire body sets a `screenWasLocked` flag. Both that flag and the auto-lock timeout are acted on inside `onResume()` — i.e. `StorageKeyManager.lock()` runs when the user **comes back to the app**, which correctly gates access to message history but does not bound RAM exposure in the meantime. `MessengerService` is a foreground `dataSync` service specifically so the WebSocket survives backgrounding, so the process is deliberately kept alive and the window is "until the user next opens the app", not "until Android reclaims the process". A full RAM dump from a rooted or exploited device in that window could extract the SMK. Also note, per the correction recorded in `SECURITY_MODEL.md` (CRYPTO-03), that `SessionKeyManager`'s SPK, OPK pool and Double Ratchet session states stay resident regardless of lock state once loaded — locking only zeroes the SMK itself. This whole row sits inside the existing non-goal "protection against a fully compromised endpoint with live process-memory access"; it is stated precisely here because `Subrosa_Architecture_Overview.md` §3.4 previously drew a seizure-resistance conclusion from the stronger, incorrect version.

3. **AndroidKeyStore software keys**: On devices without a hardware-backed Secure Element, AndroidKeyStore keys are stored as software keys in the TEE or in `/data`. An attacker with deep OS-level access may be able to extract them, bypassing the `enc_smk_ks` path. The `enc_smk_pwd` path (PBKDF2 300K) provides protection independent of the Keystore.

5. **Group key distribution**: Group keys are distributed through the server. A compromised server could refuse to deliver a new group key to a member after rotation, effectively excluding them silently. Out-of-band verification of group membership is recommended for high-security use cases.

6. **Backup password**: The backup password is not stored anywhere. If it is lost, the backup cannot be decrypted. There is no recovery mechanism.

7. **Decoy mode forensics**: A sophisticated forensic examiner may detect evidence of a prior wipe (filesystem timestamps, journal entries, wear-leveling patterns on flash storage). Decoy mode provides social/legal cover, not technical undetectability.

8. **Desktop keystroke interception**: Unlike Android's `FLAG_SECURE` (a real OS-enforced guarantee for that app's window), there is no userspace defense against a hardware keylogger (inline USB device) or an OS-level low-level keyboard hook (e.g. Windows `WH_KEYBOARD_LL`) — these intercept key-press events before any application, including this one, ever receives them. The desktop client mitigates this with an on-screen keyboard, available both for password fields (login, registration, backup, change-password, auto-lock unlock) and for regular chat message composition, with a layout randomized on each open, so text can be entered via mouse clicks without generating a single keystroke. This closes the most common real-world keylogger class (hardware/driver-level keyboard capture). It is complemented by screen-capture exclusion (`WDA_EXCLUDEFROMCAPTURE` on Windows, `NSWindowSharingNone` on macOS) so the on-screen keyboard and message content are not readable via screenshots or screen recording either, and by clipboard hygiene (auto-clear after 30s, exclusion from Windows Clipboard History and Cloud Clipboard sync) for copied message text. None of this defends against memory-scraping malware with kernel-level access, or against the Windows Accessibility/UI Automation API, which can read on-screen control text programmatically — bypassing pixel-level capture protection entirely; there is no cross-toolkit way to opt a window out of this without also breaking legitimate assistive-technology users. Physical typing remains available and is not blocked outside of password fields, so the on-screen keyboard is opt-in per message. On macOS specifically, a stronger mechanism exists (`EnableSecureEventInput()`, the same API Terminal and 1Password use for password prompts) but is not yet wired up.

9. **Desktop swap/hibernation exposure beyond the SMK**: The Storage Master Key is held in a locked, non-pageable native buffer (`VirtualLock`/`mlock`) and message keys are zeroed after use, but the JVM heap as a whole (including transient decrypted message text held by the UI) is not, and cannot practically be, locked against paging by an application running without elevated privileges. On a machine without full-disk encryption (BitLocker/FileVault/LUKS), plaintext could theoretically be recovered from the swap file or a hibernation image. Enabling OS-level full-disk encryption is a deployment recommendation, not something the app can enforce.

10. **Desktop attachment temp files**: Opening a received file attachment decrypts it to a temporary file so the OS can hand it to an external viewer. The temp file is overwritten with `secureDelete` (3-pass) on a timer and on JVM shutdown, rather than left for a plain OS delete — but a hard crash or `kill -9` before either fires can still leave recoverable plaintext in the OS temp directory. The external viewer application may also retain its own reference to the path (e.g. an MRU/recent-files list) outside this app's control.

11. ~~Prekey-bundle fetch reveals a fingerprint pair to the server~~ — **partially mitigated, with known residual leaks**: `get_prekey_bundle` used to tell the server directly "A wants B's bundle" — the same limitation Signal's own server has. This is now reduced three ways, reusing existing primitives rather than new cryptography: (a) **batched anonymous fetch** (`get_prekey_bundles_batch`) — the real target is padded with decoy targets, never consuming a decoy's one-time prekey. (b) **Server-suggested decoy candidates** (`get_decoy_candidates`, added 2026-11-03) — see correction below; this is what actually closes the "requester has too few contacts for real cover" case that (a) alone could not. (c) **Bootstrap token** — every bundle the server hands out (batched or direct) is now also stamped, at serve time, with one of the bundle owner's currently-registered anonymous tokens (from the pool already maintained by `AnonTokenManager`/`subscribe_tokens`), letting the resulting `session_init` be delivered via `anon_message` instead of directly addressed — closing the follow-on leak where batching only the fetch would still be undone by a directly-addressed `session_init` moments later.

    **Corrected 2026-11-03 — residual gap (ii) below is closed, not just "found during self-audit."** Decoys are no longer limited to the requester's own contacts: `requestPrekeyBundle()` (`MessengerService.kt`) first fills the batch from real contacts, then tops the rest up to `MAX_BATCH_BUNDLE_TARGETS - 1` via `get_decoy_candidates` — a new server call that samples random *other* accounts with a currently-published bundle (from `prekey_bundles`, never from bundle content, never consuming an OPK — identities only) and hands them back as additional decoy material. Freshly sampled per call, never cached or reused server-side, specifically so a logging adversary can't separate "stable across requests" (decoy) from "the one that varies" (real target) by intersecting multiple batches over time. The old single-target fallback now only fires when truly no decoy exists at all (zero contacts **and** the server has nobody else with a published bundle to offer) — previously it fired any time contacts were scarce, which was the common case for a new or lightly-connected account.

    **Residual gaps, honestly restated after the above fix:** (i) **unchanged, still open** — decoys drawn from the requester's own contacts (when any exist) are still sent in cleartext as part of the batch; the server still sees that requester's actual contact graph up to `MAX_BATCH_BUNDLE_TARGETS - 1` entries. Today's fix adds *more* cover on top for low-contact accounts, it does not stop revealing the real contacts that do exist. (ii) **closed** — batch size no longer shrinks below `MAX_BATCH_BUNDLE_TARGETS` based on contact count; `get_decoy_candidates` pads it to the same size every time, regardless of how many real contacts the requester has, removing the approximate-contact-list-size leak. (iii) **unchanged, still open** — the `bootstrap_token`-omission downgrade described below is untouched by this fix. **New residual gap introduced by the fix itself**, stated plainly rather than left implicit: `get_decoy_candidates` teaches the server "these N other fingerprints exist and currently have a published bundle" — information a pure contacts-only decoy pool never revealed, since the requester previously only ever asked about fingerprints it already knew. Accepted deliberately for this product's actual deployment shape (one server per company, SECURITY_MODEL.md's "trusted admin" boundary) where colleague existence is not meaningfully new information; **a public/multi-tenant deployment with strangers on the same server should weigh this trade-off differently** before relying on it. None of this breaks message confidentiality (the E2EE payload itself is unaffected), but it meaningfully shapes the anonymity property this mechanism was built for.

    **This mitigation (unlike the ML-KEM/X3DH crypto elsewhere in this document) is original protocol-design work, not an implementation of an independently peer-reviewed anonymity standard** — the same honest caveat that already applies to the anon-token-routing/mailbox/cover-traffic system it extends. It has not been independently audited.

    **Not addressed by item 32's sealed-sender work**: bootstrap/first-contact remains identified in both directions even after item 32 — `get_prekey_bundle`/`get_prekey_bundles_batch` still run over the normal authenticated socket (the requester's `username` is known to the server for that call), and the target's own bundle is registered under their `username` too. Sealed-sender's de-identified channel only covers ongoing `anon_message` traffic once a token relationship already exists — establishing that relationship in the first place is a separate, still-open problem.

12. **Anonymous routing coverage is not yet complete**: 1:1 text, typing, read receipts, reactions, edits, deletes, image/file/video chunks, group messages, group-message deletion, and (per [SECURITY_CHANGELOG.md](SECURITY_CHANGELOG.md) item 18) 1:1 call signaling are anonymized via token routing. There is no fingerprint-addressed fallback for any of these — if no anon token is available for a contact, the message queues locally and retries via anon-token refill / mailbox bootstrap rather than sending in the clear (see the "cut the direct fallback" decision this was changed to). Group-call signaling (`call_group_*`) is deliberately **excluded** — see [SECURITY_CHANGELOG.md](SECURITY_CHANGELOG.md) item 18. `channel_post` is not covered — the server could see who posts and channel subscriber lists are inherently visible — but the Channels feature is currently disabled at the UI layer on both clients (see `ARCHITECTURE.md`), so this gap has no live attack surface today. If channels are ever re-enabled, anonymizing distribution needs the same mailbox-based subscriber-token exchange described when that decision was made.

26. **No protection against mass registration of new identities (Sybil flood) — added**: `rate_limit_check()` is keyed on `username`, i.e. on identity — and identity is free to mint, a new ECDSA keypair per connection. An attacker with many devices/IPs trivially defeats any IP-based limit by minting a new identity instead of one. Added `MAX_REGISTERED_USERS` (a hard cap on the total number of identities ever registered, unlimited by default — a per-deployment setting) and `POW_DIFFICULTY_BITS` (proof-of-work on each fingerprint's very first registration — the cost is real device CPU time, not an IP address an attacker with many devices can swap for free). Both apply only to brand-new identities, never to a reconnect of an already-known one. **Corrected 2026-09-25**: this used to say both are "off by default (`0` = disabled)" — only `MAX_REGISTERED_USERS` actually defaults to `0`/unbounded (and even then, `REGISTERED_ACCOUNTS_HARD_MAX_ROWS`, default 1,000,000, still applies underneath as an always-on hard ceiling — `docs/KNOWN_SECURITY_ISSUES.md` S6-56). `POW_DIFFICULTY_BITS` defaults to **18** (`os.environ.get("POW_DIFFICULTY_BITS", "18")`) — real proof-of-work friction is on by default; an operator has to explicitly set it to `0` to disable it.

27. **No protection against offline access to the server's message database — mitigated, opt-in**: `server.py`'s SQLite database (`messages.db`) was always stored unencrypted on disk — a stolen disk, an unencrypted backup, or a hosting provider with filesystem access could read it directly, including the permanent `registered_fingerprints`/`revoked_fingerprints` tables and (unless `TOTP_SECRET_ENCRYPTION_KEY` is also set) plaintext TOTP secrets. Added optional SQLCipher-backed encryption at rest, enabled by setting `DB_ENCRYPTION_KEY_HEX` (a 32-byte hex key) in the server's environment; off by default, so existing deployments are unaffected until an operator opts in. **This defends only against offline/at-rest access** — a root-level attacker on the *live* process can still read the key from the environment, same limitation as `TOTP_SECRET_ENCRYPTION_KEY`. Relayed message payloads themselves are opaque ciphertext either way (server never has the E2EE keys), so this closes a metadata gap, not a content one. Enabling it on an existing deployment requires starting from an empty database — SQLCipher cannot open a file that was written in plain SQLite format.

29. **Only one invite-code mailbox tag can be "live" per device at a time**: each invite code embeds a one-time anonymous-mailbox tag (see [Invite Codes](#invite-codes)), and generating a fresh code (tapping Copy/Share/Show-QR in Profile) replaces the single tag the device is currently polling for. If a code has already been given to someone who hasn't redeemed it yet, and a second code is then generated for a different person, the first code still looks structurally valid (signature and TTL both check out) but its mailbox deposit is never picked up — the first person's connection attempt fails silently, with no error on either side. This is a deliberate tradeoff, not an oversight: minting additional tags increases the number of distinct tags the anonymous-mailbox/cover-traffic system has to carry, which is a cost for every user's traffic-analysis resistance, not just the person generating them — supporting multiple simultaneously-live tags per device was considered and rejected on that basis. The UI (Profile screen and the in-app security guide) now warns explicitly not to regenerate a code until its recipient has connected.

30. **Invariant: `server.py` must never read a client's real IP address.** The application layer has no legitimate use for it — routing is entirely token-based (see item 12) — so `server.py` only ever calls `websocket.remote_address`, which is always the reverse proxy's own loopback address in a normal deployment, and never parses `X-Forwarded-For`/`X-Real-IP` from request headers. This held by accident rather than by design until 2026-08-29: the Docker deployment config (`deploy/nginx.conf`) was actively setting `proxy_set_header X-Real-IP`/`X-Forwarded-For` toward the backend (the production `docs/nginx-subrosamessenger.conf.snippet` config was not), meaning the headers were sitting there, unread only because no code happened to parse them yet — one well-intentioned "let's improve rate-limiting" change away from silently exposing every client's IP to the application layer and its logs/DB. `deploy/nginx.conf` no longer forwards either header to the backend. **This is now a hard invariant, not an implementation detail**: any future change that makes `server.py` read a client IP from anything other than a federation peer's own handshake (federation peers are a different trust model — they're pre-shared-secret-authenticated servers, not anonymous end users) should be treated as a regression.

    This says nothing about IP visibility elsewhere in the stack — nginx itself, and the hosting/CDN provider, still see it, and that's a separate, expected part of operating a TLS-terminating reverse proxy. The production config additionally restricts inbound traffic to Cloudflare's IP ranges, which meant (before 2026-08-29) nginx's own `access_log` recorded Cloudflare's edge IP rather than the actual client, making the operator's own IP-based abuse mitigation (fail2ban etc.) look at the wrong address entirely. Added `set_real_ip_from`/`real_ip_header CF-Connecting-IP` (trusting only the same Cloudflare ranges already allow-listed, so it can't be spoofed by a client claiming to be Cloudflare) so nginx's own logging is accurate for the operator's use — this is orthogonal to, and does not weaken, the invariant above: the recovered real IP still stops at nginx and is never forwarded to `server.py`.

31. **`anon_message` payloads carried the sender/recipient pair in plaintext — fixed 2026-08-29.** An oversight, not a deliberate design choice: federation was implemented before anonymous token routing, and `from`/`to` were never moved out of the plaintext envelope when token routing was added later. Only the `text` field was ever encrypted (via the recipient's Double Ratchet session); `from` and `to` sat in the same JSON object as plain strings. The token protects *routing* — the server never needs to know from/to to deliver by token, `token_to_ws.get(token)` is enough — but the payload it actually holds during that lookup was fully readable by anyone with access to the server process at that moment, and the federation fallback path (`payload.get("to")`, used when a token isn't known locally) explicitly read it. Fixed by having `sendAnonOrDirect()` and `sendWithForwardSecrecy()` seal the entire packet (from/to included) with one more layer of hybrid asymmetric encryption keyed to the recipient's own identity key (`sealPacketForRecipient()`) — the recipient decrypts with their own private key, which doesn't require knowing who sent it first (unlike the Double Ratchet session itself, which does need "from" to pick the right session before decryption). Covers every message type routed through those two functions — the list in item 12. Mailbox-deposited messages (`depositTokensViaMailbox`/`depositSessionInitViaMailbox`) were never affected by this gap; that path already encrypts the entire inner structure, from/to included, as one opaque blob. **Deliberate trade-off accepted with the operator**: federation's by-fingerprint fallback routing no longer works for anything sent this way, since the server can no longer read `to` to forward it. Backward compatible on receipt (an absent `blob` field falls back to the old unsealed shape), but a new client talking to an un-updated peer breaks in the new→old direction (the old code doesn't know to look for `blob`) — both sides need the update together.

    **Correction, 2026-11-03 — this entry used to claim the fix was "the same mechanism `sendAnonTokensTo()` already used for `__beacon_tokens__`". That was false, and the false claim concealed a live instance of the exact gap this item describes.** `sendAnonTokensToLocked()` — the resupply message that hands a contact a fresh token batch — only ever encrypted the `text` *field* via `CryptoManager.encrypt()` and then assembled its `anon_message` payload by hand with `from`/`to` as plain JSON strings. It never called `sealPacketForRecipient()` at all; that function had exactly two call sites, neither of them this path. So from 2026-08-29 until this correction, every token resupply placed a readable `from → to` pair in server memory during the `token_to_ws` lookup. The marginal exposure was limited — that send deliberately goes out on the identified socket (item 32(d)) and the token's owner is recorded in `anon_token_state` regardless — but it turned the social-graph edge into a single readable object instead of something an observer had to correlate from two separate places, so any payload capture, crash dump or compelled live-memory read yielded it directly. Token resupply is routine traffic, not an edge case. **Now actually sealed**: `sendAnonTokensToLocked()` calls `sealPacketForRecipient()` and, if the recipient's PQ key isn't cached, falls back to the anonymous mailbox (which encrypts the whole inner structure anyway) — never to the unsealed shape. Found by a documentation-versus-code audit rather than an incident, which is the case this project's honesty norm exists to catch: a document asserting a property the code did not have.

    **Decision finalized 2026-08-30: accept this as permanent, not a gap to eventually close.** Federation in this project is a same-deployment father/son redundancy mechanism (peer servers under one firm's shared `FEDERATION_SECRET`, discovered dynamically via `peer_announce` — see `.env.example`), not cross-firm messaging between separate Subrosa deployments. Checked against real client behavior: the plain fingerprint-addressed `message`/`session_init` types (whose federation-forward path *does* still work, `to` stays outside any seal) are barely ever sent by current client code — the direct-`sendWs()` fallback for both was deliberately removed earlier in this same line of work (see the "session_init тихо откатывается на прямую адресацию" fix), so virtually all real 1:1 traffic goes through `anon_message` or the anonymous mailbox instead. That made the `anon_message` federation-fallback (`payload.get("to")`) the only path that mattered for real cross-peer delivery, and it was already silently dead — sealed payloads never carry a readable `to`, so the fallback always found `fed_to = None` and queued locally regardless, with no error and no user-visible sign it had stopped working. The dead code was removed from `server.py` (rather than left as a misleading no-op) on 2026-08-30. **Net effect, stated plainly**: a message sent while the recipient's home peer server is unreachable now queues (delivered once the recipient reconnects to whichever peer is live and re-subscribes tokens) rather than being forwarded live to a different peer — an availability trade-off, not a confidentiality one; nothing is lost, delivery is just not instant across a mid-conversation peer failover. Building real anonymized cross-peer routing (e.g., encrypting `to` to a specific peer's own key) was considered and explicitly deferred — not needed for the redundancy use case federation actually serves today.

32. **Sealed sender for `anon_message` — added 2026-08-29, partial rollout.** By design, per the model above, item 31's sealing hides `from`/`to` from anyone reading the payload, but the server could still identify the sender through a channel item 31 explicitly left open: `anon_message` was submitted over the same persistent, authenticated WebSocket used for everything else (`clients[username]`), so `rate_limit_check(username, "anon_message")` (and the connection object itself) tied every send event to a known account in real time — not from a log, from the live process. This closes that channel, inspired by (not a reimplementation of) [Signal's Sealed Sender](https://signal.org/blog/sealed-sender/):

    - **Sender certificate**: on request (`request_sender_cert`, sent right after `register()` over the normal authenticated socket — nothing to hide at that step, the request carries no addressee), the server signs `{fingerprint, public_key, issued_at, expires_at}` with a dedicated EC P-256 key (`secrets/sender_cert_signing_key.pem`, generated per-deployment on first run, unrelated to the TLS key) over a fixed pipe-delimited string (deliberately not JSON — cross-language JSON canonicalization, in particular float formatting, is not something to build a signature over). Cached client-side (`SenderCertManager`), refreshed ~4h before its 24h expiry.
    - **Sealed delivery**: the cert travels *inside* `sealPacketForRecipient()`'s envelope (item 31's mechanism) — the server never reads it, only the recipient, who verifies the signature against the server's public key (pinned per-deployment, same mechanism as `CertificatePinner`) and cross-checks the cert's `fingerprint` against the claimed `from`.
    - **De-identified submission channel**: a second WebSocket connection (`anon_channel`) that skips the identity-proving handshake entirely — no public key, no signature, server never learns a `username` for it, and it is hard-restricted server-side to the single message type `anon_message` (anything else closes the connection). Real `anon_message` traffic and AGGRESSIVE-mode cover-traffic decoys both go out over this channel, at the same paced cadence in AGGRESSIVE mode, so a real send is not distinguishable from a decoy by timing either.
    - **Anti-spam without identity**: since there's no `username` to key `rate_limit_check()` on for this channel, abuse containment is a per-connection cap (`ANON_CHANNEL_MAX_PER_MINUTE`) plus the fact that a flood of unregistered tokens is already cheap to reject (`is_known`/`is_spent` lookup, same "fake ack" path used for cover-traffic decoys).
    - **No identified-socket fallback**: an earlier version of this fell back to sending over the main authenticated socket whenever `anon_channel` wasn't ready yet — silently, with no warning, an "anonymous → identified fail-open." Removed 2026-08-29: `sendOnAnonChannelNow()` now queues (`anonChannelPendingQueue`) and waits for the channel to actually become ready rather than degrading security silently — same principle as removing `freshTokensToShare()`'s blind pool eviction earlier the same day (a fallback that quietly weakens a security property is worse than making the caller wait). The one deliberate exception is (d) below.
    - **No structural correlation between the two connections**: found via code review, not statistical traffic analysis — two signals that would have let an observer pair the main socket and `anon_channel` with high confidence *without* needing IP or content. (i) Both used to share the same `OkHttpClient` instance as the main socket, hence the same TLS session cache — under TLS 1.3 the second connection could resume a session ticket issued during the first's handshake, a direct cryptographic link visible before any application data. Fixed by giving `anon_channel` its own separate `OkHttpClient` instance(s) (`anonWsClient`/`anonWsTorClient`), with their own `SSLContext`. (ii) `anon_channel` used to open at a fixed, near-immediate interval after the main socket every single time (`connectAnonChannel()` called right after the main connection's own setup) — an observer just watching connection-accept timestamps could pair "these two opened within ~1s of each other," no IP or TLS inspection needed. Fixed with a randomized 0–3s delay before the socket actually opens; `sendOnAnonChannelNow()` already queues rather than blocking during that window, so this costs no reliability.

    **What this closes**: even a fully malicious or compelled operator — actively reading server memory in real time, not just handed logs after the fact — can no longer read the sender of an `anon_message` off the connection that submitted it, because that connection was never told who it belongs to. This is a materially stronger claim than "we don't log it": there is nothing to compel, live or retrospectively, because the linkage never exists on the server at all for this specific event.

    **What this does not close, and should not be oversold as closing**: (a) **the recipient side is unchanged** — whoever currently owns a token is still known to the server via `subscribe_tokens` on their normal authenticated socket, so the server still learns *who received* something, just not who sent it; (b) **first contact remains fully identified in both directions** — see item 11's residual-gaps note; a session established via prekey-bundle fetch still ties both parties' `username` to that bootstrap event; (c) **global passive network-level traffic analysis is out of scope** — this defends against the operator (including under legal compulsion), not against an adversary correlating packet timing/volume across the network from outside; at the deployment scale this product targets (tens–low hundreds of concurrently online accounts per firm, not millions), that kind of anonymity-set-dependent protection isn't achievable regardless of what's built at the application layer, and claiming otherwise would be overclaiming; (d) `sendAnonTokensToLocked()` (the resupply message that hands a contact a fresh token batch) deliberately still uses the identified socket — its `subscribe_tokens` must land on the server strictly before the `anon_message` that references those tokens, a guarantee that only holds on a single connection, so moving it to `anon_channel` would reopen a token-registration race fixed the same day.

    **Deployment gaps, not yet closed**: the server's per-deployment public signing key must be copied into `SenderCertManager.SERVER_CERT_PUBLIC_KEY_B64` at build time (currently a placeholder in the shipped source — `verify()` fails closed, logging a warning, until an operator does this for their build) — same manual step as `CertificatePinner`'s TLS pin. Verification of a received cert currently only logs its result (`anon_delivery` handler) and does not yet reject a message on mismatch/invalid signature — enforcement is intentionally deferred until the update has rolled out across the deployment's active clients, to avoid dropping legitimate messages from not-yet-updated peers.

    **This is original protocol-design work adapting a published concept, not an audited implementation of Signal's own sealed sender** — it has not been independently reviewed.

33. **Local-only contact block list + explicit token revocation — added 2026-08-29.** Two related gaps closed together: (a) deleting a contact previously only stopped re-subscribing their tokens on the *next* reconnect (`wipeMyTokenPool()`) — any already-registered, unspent token they still held kept routing to this device until then. `unsubscribe_tokens` (server-side, mirrors `subscribe_tokens` but subtracts) now revokes immediately, regardless of reconnects; client-side bookkeeping of which token values were given to which contact (`AnonTokenManager.recordTokensGivenTo()`, never sent to the server — the server still has no concept of which contact a token belongs to) makes this possible. (b) even with tokens revoked, a compromised contact could still re-establish contact from scratch via a fresh `session_init` (prekey-bundle fetch always issues a new bootstrap token to any requester, by design — needed for legitimate cold outreach) — and `processSessionInit()` used to save the sender's key and establish a new session *before* the existing `isMutuallyAdded()` content-level gate ever ran, so a deleted contact's `session_init` did real cryptographic/state work even though the resulting message was correctly dropped. Fixed with a **local-only** block list (`ChatStorage.blockContact()`/`isBlocked()`) checked as literally the first line of `processSessionInit()`, before any side effect — a server-side block list was considered and explicitly rejected: it would require telling the server "I know and am blocking fingerprint X," a direct, permanent, voluntary admission of a relationship, which is a worse leak than what item 32 exists to prevent. Both are wired into `forgetContact()` automatically (fires on contact deletion, no separate "block" UI exists yet) and both reverse automatically if the same fingerprint is legitimately re-added via a fresh invite (`ChatStorage.addContact()` calls `unblockContact()`), so the supported delete-then-reinvite flow keeps working.

34. **Federation TLS accepted any certificate at all — fixed 2026-09-04.** `main()`'s SSL context for every outgoing federation connection (`FEDERATION_PEERS`, and dynamically discovered peers from `peer_announce`/`peer_roster` gossip) set `check_hostname = False` and `verify_mode = ssl.CERT_NONE` unconditionally — TLS still encrypted the link, but authenticated nobody on the other end. The `FEDERATION_SECRET` HMAC handshake does **not** compensate for this: it proves each endpoint knows the shared secret, not that the TLS *channel* they're talking through is the real peer's — a MITM never needs to know `FEDERATION_SECRET` at all, it just relays the challenge and the HMAC response verbatim between two separate TLS sessions it terminates on each side, and both real endpoints see a valid `federation_auth` exchange with *each other*. Past that point federation frames carry no per-message MAC or channel binding, so the MITM reads and modifies every frame indefinitely — `ssl.CERT_NONE` turned a relay-proof HMAC handshake into a fully relayable one. Fixed: `build_federation_ssl_context()` now requires real certificate verification (`verify_mode = ssl.CERT_REQUIRED`, `check_hostname = True`), with an optional `FEDERATION_CA_FILE` (a private federation CA's certificate) for deployments using self-signed peer certs rather than publicly-trusted ones — self-signed certs are still fully supported, just verified against a CA the operator controls instead of not verified at all. `FEDERATION_PEERS` entries must all be `wss://` (checked at startup; `RuntimeError` on any `ws://` entry, refusing to start rather than silently running one peer connection with no transport security at all); dynamically discovered peer URLs from `peer_announce`/`peer_roster` are rejected the same way, before ever being added to `dynamic_peer_urls` or reaching `federation_connect_to_peer()`. Standalone invariant: `SECURITY_INVARIANTS.md` #35.

35. **Unbounded dynamic-peer gossip, and un-cancellable evicted-peer reconnect loops — fixed 2026-09-04.** A single `peer_roster` message from any authenticated federation peer could previously introduce an unlimited number of URLs — each became a permanent `dynamic_peer_urls` entry AND its own infinite-reconnect `asyncio.Task` (`federation_connect_to_peer()`'s own `while True`), costing memory, sockets, DNS/TLS CPU, and outbound traffic per bogus entry, indefinitely; one malicious gossip message could mint thousands. `federation_watchdog()`'s existing eviction (after `DYNAMIC_PEER_MAX_STRIKES` unresponsive hourly checks) didn't fully close this either: it only ever removed the URL from `dynamic_peer_urls`/`dynamic_peer_strikes`/`federation_ws` — the Task actually running that peer's reconnect loop was never tracked anywhere, so an evicted peer's loop kept reconnecting forever in the background regardless. Fixed with three input bounds (`MAX_DYNAMIC_PEERS` total, `MAX_ROSTER_PEERS` per `peer_roster` message, `MAX_PEER_URL_LEN` per URL) and a real task-lifecycle registry: `start_dynamic_peer()` is now the sole admission point for a gossip-discovered peer, and `federation_watchdog()`'s eviction actually cancels that peer's `asyncio.Task` (tracked in the new `dynamic_peer_tasks`) and closes its websocket, not just bookkeeping; `federation_connect_to_peer(dynamic=True)` additionally self-terminates once its own URL leaves `dynamic_peer_urls`, so a lost/failed cancellation still can't resurrect an evicted peer. **Deliberately not addressed here, tracked separately**: `wss://` restricts the *protocol*, not which *hosts* an already-authorized peer can direct this server to connect to — an address-range/host allowlist (and whether federation should reach LAN addresses at all) is a distinct SSRF/egress policy question. See `docs/KNOWN_SECURITY_ISSUES.md` OPEN-11, closed by item 36 below. Standalone invariant: `SECURITY_INVARIANTS.md` #36.

36. **Federation SSRF/egress — dynamic-peer gossip could direct outbound connections to internal addresses — fixed 2026-09-04.** `wss://` + certificate verification (item 34) authenticates who a peer's certificate says it is, but says nothing about *where* this server is being told to connect — a compromised/malicious federation peer could announce an internal hostname or IP via `peer_announce`/`peer_roster` (a LAN admin panel, a cloud metadata endpoint, a localhost-bound service on this same machine) and get this server to open an outbound TLS connection there; TLS verification doesn't defend against this at all, since the malicious "peer" IS the connection's actual destination in that scenario, not an interceptor. Fixed with three fail-closed gates before any DNS/TCP/TLS activity for a gossip-discovered URL: `parse_federation_url()` (strict `wss` syntax, a real hostname, no embedded `user:pass@` credentials), `federation_host_allowed()` (resolves the hostname via `getaddrinfo()`, requires every returned address to pass policy), and `_federation_ip_allowed()` (rejects loopback/private/link-local/multicast/unspecified/reserved addresses unless they fall inside an operator-configured `FEDERATION_ALLOWED_PRIVATE_CIDRS` allowlist — empty and deny-all by default). Static, operator-configured `FEDERATION_PEERS` are not filtered by this — that's explicit operator trust, not attacker-influenced input; the threat model here is a peer already inside the mesh directing this server elsewhere. **Known, explicitly accepted residual gap**: this resolves the hostname once for the check, but `websockets.connect()` resolves it again independently moments later when the connection actually opens — the two resolutions aren't atomic, so a host under active attacker DNS control (or DNS-cache-poisoning reach) could in principle serve a public address to the check and a private one to the real connection (DNS TOCTOU/rebinding). This meaningfully raises the bar but is not a complete fix; a fully rebinding-proof design needs network-layer egress policy (firewall/container rules restricting the federation process to known peer CIDRs/ports — recommended for genuinely strict deployments) or resolving once and connecting directly to the verified IP while keeping the hostname only for SNI/certificate verification. Neither is implemented — tracked at `docs/KNOWN_SECURITY_ISSUES.md` OPEN-12. Standalone invariant: `SECURITY_INVARIANTS.md` #37.

37. **Two live wire-paths served the same X3DH prekey bundle with different security semantics — fixed 2026-09-04.** `request_prekey` (legacy) returned `prekey_bundles[target]` completely as-is: no `opks.pop(0)`, no persisted OPK-consumed state, no `bootstrap_token` attached, no `revoked`-fingerprint flag — a second, weaker route to the exact same bundle data that bypassed every single-use/anonymity/revocation guarantee the canonical `get_prekey_bundle`/`get_prekey_bundles_batch` path enforces. Confirmed dead client-side (grepped both Android and Desktop source trees — zero callers), so it was removed entirely (handler and its `ALLOWED_TYPES` entry) rather than hardened. Separately, and more seriously: `register_bundle` (legacy, but still Android's *only* prekey-registration call, sent unconditionally on every connect) stored a bundle raw (`prekey_bundles[username] = bundle`), while `publish_prekey_bundle` (canonical, used by Desktop and Android's own OPK-replenishment path) wrapped it as `{"bundle": ..., "updated_at": ...}`. `get_prekey_bundle`'s OPK-consumption logic only recognizes the wrapped shape — a bundle registered via `register_bundle` fell through to a "serve the whole thing, nothing ever popped" branch, silently voiding the one-time-prekey guarantee for whichever bundle actually arrived that way, which in practice was most Android connections' bundle, not a rare edge case. `register_bundle` couldn't simply be removed (Android still depends on it), so fixed by extracting one canonical function, `store_prekey_bundle()`, that both `register_bundle` and `publish_prekey_bundle` now call — one write path, one shape, the two message types can no longer disagree about what a stored bundle looks like. Standalone invariant: `SECURITY_INVARIANTS.md` #38.

38. **OPK deletion (§ "Forward Secrecy" above, "`OPK_B`: one-time, deleted by server after fetch") was not actually durable at the moment of that fetch — fixed 2026-09-04.** `get_prekey_bundle` popped the OPK from the RAM cache under the server-wide `lock`, then scheduled persistence as a fire-and-forget `asyncio.create_task(db_save_bundle(...))` — a crash in the window between the RAM pop and that task actually running (or the process simply dying first) meant the exact same OPK could be handed out again after a restart, or to a second requester racing the first, silently defeating the one-time-use property this section's own X3DH diagram states as fact. The incoming-federation path (`federated_get_bundle`) was worse: it popped the OPK from RAM with **no persistence at all**, so a federation peer re-requesting the same target's bundle — after any restart, or simply a second concurrent request — could receive the identical OPK every time, not just in a narrow crash window. Fixed with one canonical, durable consume operation used by both paths: `_db_consume_prekey_opk_sync()` (a single `BEGIN IMMEDIATE` SQLite transaction covering the read, the pop, and the write-back; rolls back and re-raises on any failure, never reporting an OPK consumed that wasn't actually committed) plus `consume_prekey_bundle_for_serve()` (a narrow per-target lock, separate from the server-wide `lock`, so the DB write can be safely awaited without violating `SECURITY_INVARIANTS.md` #34's "never await DB under the global lock" rule — the RAM cache is synced to the durable state only *after* the commit succeeds, never before). `store_prekey_bundle()` (publish) now shares that same per-target lock and DB-first ordering, so a concurrent republish and a concurrent OPK consumption for one target can never interleave into an inconsistent state. `get_prekey_bundles_batch` was and remains unaffected — it never consumed an OPK to begin with. Standalone invariant: `SECURITY_INVARIANTS.md` #39.

39. **`publish_prekey_bundle` had no rate limit at all, and `register_bundle`'s was keyed separately from it — fixed 2026-09-04.** Item 38's durable-store fix means both `register_bundle` and `publish_prekey_bundle` now perform a real SQLite write, a per-target mutation-lock acquisition, and executor-thread work on every call. `register_bundle` alone was rate-limited (a bucket keyed on its own message-type string, 20 per 60s); `publish_prekey_bundle` had no limit whatsoever, so an authenticated client could spam it to force unbounded durable writes. Simply adding a limit to `publish_prekey_bundle` wouldn't have been enough on its own, either: keeping the two message types on separate buckets would still let a client double its effective write rate by alternating between the two aliases for the same operation. Fixed with one shared `"prekey_publish"` bucket (20/60s) checked by both handlers, before any bundle-size validation or the `store_prekey_bundle()` call — a rejected request never reaches the durable write path at all. The old `register_bundle`-only bucket key was removed rather than left dangling. Standalone invariant: `SECURITY_INVARIANTS.md` #40.

40. **Item 39's per-user prekey-publish bucket didn't bound aggregate write load under open registration — fixed 2026-09-04.** An attacker able to register many valid identities (limited only by `POW_DIFFICULTY_BITS`/`MAX_REGISTERED_USERS`, if a deployment even configures those) gets a fresh 20-per-60s allowance per identity minted — the per-user bucket gives fairness between accounts, but the aggregate durable SQLite write rate this server absorbs scales linearly with however many identities the attacker mints, exactly the write amplification item 38's durable-store fix made each individual write more expensive to begin with. Fixed with a second, orthogonal budget: `global_prekey_publish_rate_ok()`, a single process-local counter checked by both `register_bundle` and `publish_prekey_bundle` right after the per-user check, still before any bundle-size validation or the durable write — both rejections return the identical generic error, so a caller can't tell which bucket was exhausted. Deliberately RAM-only rather than SQLite-backed (using a SQLite write to guard against excess SQLite writes would defeat much of the point), and deliberately lock-free (no `await` in the check-and-increment, so a single asyncio event loop makes it atomic with respect to every other coroutine with no explicit lock needed). `PREKEY_PUBLISH_GLOBAL_LIMIT` is env-configurable (default 200/60s); `0` explicitly disables the aggregate check, a negative value refuses to start the server rather than being silently, ambiguously interpreted. **Explicitly documented as process-local, not cross-process durable**: this is correct and sufficient for this deployment's current single-process shape, but multiple server replicas behind a load balancer would each get their own independent quota — the real aggregate rate across the whole deployment would then be the configured limit multiplied by the replica count. A genuinely multi-process deployment needs a shared external limiter (Redis, a gateway/sidecar rate limit, etc.), which this mechanism does not provide and does not claim to. Added in the same pass, optimization only (not a substitute for either rate limiter): `store_prekey_bundle()` now skips the SQLite UPDATE/REPLACE entirely when the exact same bundle content is already the durable current one for that identity — e.g. `register_bundle` re-sending an unchanged bundle on every Android reconnect no longer costs a write. Standalone invariant: `SECURITY_INVARIANTS.md` #41.

41. **Anonymous-mailbox TTL was lazy-per-tag, allowing unbounded unique-tag RAM retention — fixed 2026-09-04.** `MAILBOX_TTL` (48h) was previously enforced only at the exact moment the SAME tag was next touched by `mailbox_put`/`mailbox_fetch` — a tag never touched again (the normal case for a one-shot first-contact bootstrap tag whose recipient never fetches it) stayed in the `mailbox` dict forever, well past its supposed lifetime, since nothing ever swept it. The existing per-tag cap (5) does nothing against unique tags: a fresh, distinct, otherwise-valid random tag on every `mailbox_put` never approaches it. At the existing rate limit (20/min) and `MAILBOX_MAX_BLOB` (8 KiB), one authenticated identity could add roughly 225 MiB of RAM-resident payload per day that nothing reclaimed short of a restart; Sybil identities multiply that without bound. Fixed with real global expiry AND a hard capacity bound, both needed together — TTL alone bounds average-case growth, not worst-case burst growth within one TTL window: `mailbox_watchdog()` sweeps the whole mailbox every `MAILBOX_CLEANUP_INTERVAL_SEC` (300s default), decrementing exact running byte/blob counters for everything it removes; `mailbox_put`'s own fast path only ever cleans the ONE tag it's about to write to, never triggering a full scan per request (the two hard caps below are what keep the periodic full scan itself bounded). Two new caps, `MAILBOX_MAX_TOTAL_BYTES` (64 MiB default) and `MAILBOX_MAX_TOTAL_BLOBS` (10000 default), checked before appending — a put that would exceed either is rejected the same externally-indistinguishable way as any other `mailbox_put` failure. Both required strictly positive (unlike `PREKEY_PUBLISH_GLOBAL_LIMIT` above, `0` is not a valid "disabled" state here) — a hard, always-on process-protection bound, not an optional knob; a misconfigured value refuses to start the server. `mailbox_fetch`'s existing delete-on-fetch behavior is unchanged (a separate question, deliberately not addressed by this fix); it now also decrements the counters for every entry actually removed by that delete, including any already-expired entry sharing a tag with a still-live one, not just what's returned to the caller. **Deliberately does not persist sender identity per mailbox entry** to implement a per-user occupancy quota instead of, or alongside, this global one — the server already sees the authenticated `mailbox_put` request, but retaining a sender→tag mapping for 48h would be a strictly worse metadata-retention posture than this blind, sender-less storage already has. **Explicitly process-local**, same caveat as item 40's aggregate prekey budget: correct for this deployment's current single-process shape; a future horizontally-replicated deployment sharing one logical mailbox needs shared, bounded external storage, not an assumption these RAM counters aggregate across processes. Standalone invariant: `SECURITY_INVARIANTS.md` #42.

42. **`token_pending` had a 24h TTL but no aggregate RAM bound — fixed 2026-09-04.** The TTL bounds how LONG a single queued `anon_delivery` sits in RAM, but a valid, authenticated subscriber's token can hold one potentially-large delivery from the moment `anon_message` fires until either `anon_delivery_ack` or the TTL sweep — many simultaneously-live valid tokens therefore produce bounded retention *time* per entry but UNBOUNDED *peak* RAM in aggregate, the same class of gap item 41 (mailbox) closed applied here to anonymous-token pending delivery. Deliberately a patch-level resource bound, not a protocol redesign: the one-token/one-message semantics, the 24h TTL, ACK semantics, RAM-only (never persisted) payload retention, the sealed-payload wire format, and `anon_channel`'s identity-less authentication model are all unchanged. 43. **`pending_messages` (the durable offline-message queue) had a TTL but no hard capacity bound, and the TTL sweep itself was startup-only — fixed 2026-09-04.** `MSG_TTL_SEC` bounded how LONG a row could live, not how MUCH the queue could grow while still within that window — the same class of gap items 41/42 (mailbox, `token_pending`) closed, applied here to the durable SQLite offline queue, and worse in one respect: the TTL sweep only ever ran once, at server startup, so a long-running process never re-swept expired rows at all. Every other `db_store()` callsite was grepped and confirmed to never have claimed persistence succeeded via any wire-level signal in the first place, so none needed a corresponding change. 70. **A voice message's cryptographic signature proved only who encrypted its audio content, not that its accompanying identifier or stated length were the exact ones that same person intended — meaning a relay could keep a genuinely authentic recording and its genuinely valid signature while quietly substituting a different identifier, with real and previously undisclosed consequences — fixed 2026-09-06, High severity (raised from an initially-assumed Medium once the actual consequence was established).** The previous fix closed off using voice messages as a resource-exhaustion vector but left one thing unaddressed, flagged explicitly at the time as a candidate for follow-up: the signature accompanying a voice message covered only its encrypted audio bytes, never the identifier used to file and display that recording locally, nor the number of seconds it claimed to represent. Investigating that gap concretely, rather than leaving it as a theoretical concern, revealed something more serious than originally suspected: on the mobile app, incoming messages of any kind are matched against existing conversation history purely by that shared identifier, with no distinction for whether a matching entry was originally something the user themselves had sent — meaning a relay that substituted a different, already-used identifier onto an otherwise genuine voice message could cause the app to silently overwrite the text and file references of an entirely different, previously received or even self-sent message in that same conversation. This new combined value uses the exact same underlying signing method already in place, with no new keys and no other cryptographic change. Two things this new value deliberately does NOT separately include, and why: which account sent the recording is already established by whose stored key successfully verifies the signature in the first place, so repeating that same information inside the signed value itself would add nothing; and which account was meant to receive the recording is already established by the fact that the recording's encrypted content can only ever be successfully unlocked using that specific recipient's own private key, so a relay attempting to redirect an intact recording to any different recipient already fails for unrelated reasons before this fix and continues to do so after it. One concrete, deliberately accepted consequence follows directly from that choice: any voice recording that was sent by an unupgraded app and was still waiting for delivery on the server at the moment a recipient upgraded will fail this new verification once it finally arrives, and will be discarded exactly as any other invalid signature already would be — a small, one-time, explicitly acknowledged cost in exchange for actually closing the gap rather than leaving a permanent, exploitable secondary path alongside the new one. Both apps now also deliberately check for a repeat delivery only after successfully confirming the new signature is genuine, rather than before, specifically to prevent a scenario where an attacker could send a deliberately broken or unsigned attempt using a real person's upcoming identifier merely to make that identifier look "already handled," causing the real, legitimate recording to be silently ignored as a false repeat once it actually arrived shortly after.
