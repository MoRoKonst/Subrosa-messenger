# Как скрыть граф социальных связей в мессенджере: токены, cover traffic и Tor

Сквозное шифрование — отличная технология. Но у E2EE есть фундаментальный слепой пятно: оно защищает **содержимое** сообщений, но не **факт общения**. Сервер по-прежнему видит кто с кем говорит, когда и как часто. Этого достаточно для атаки на метаданные.

В этой статье разберём, как можно закрыть этот вектор на уровне архитектуры — на примере конкретной реализации с открытым кодом.

## Проблема метаданных

Стандартный пакет в большинстве мессенджеров выглядит так:

```json
{
  "type": "message",
  "from": "A1B2C3D4E5F6A7B8",
  "to":   "9F8E7D6C5B4A3210",
  "text": "<зашифровано>"
}
```

Даже если содержимое зашифровано идеально, сервер видит пару `from → to` при каждой отправке. Накопив логи, можно восстановить **граф социальных связей** — карту того, кто с кем контактирует.

Для журналиста, связанного с источником, или активиста, координирующего акцию — это критическая уязвимость даже при идеальном E2EE.

Сервер знает:

- Кто с кем общается (`fingerprint` отправителя → `fingerprint` получателя)
- Когда именно происходит общение
- Как часто и какой объём

## Анонимная маршрутизация по токенам

Решение: адресовать сообщения не по fingerprint пользователя, а по **одноразовым случайным токенам**.

### Схема

При подключении клиент генерирует пул из 50 случайных 128-битных токенов и регистрирует их на сервере:

```kotlin
fun ensureMyTokenPool(ctx: Context): List<String> {
    val existing = getMyTokens(ctx)
    if (existing.size >= POOL_SIZE / 2) return existing
    val needed = POOL_SIZE - existing.size
    val newTokens = (1..needed).map { generateToken() }
    // ...сохраняем и возвращаем
}

private fun generateToken(): String {
    val bytes = ByteArray(16)
    rng.nextBytes(bytes)
    val sb = StringBuilder(32)
    for (b in bytes) {
        val v = b.toInt() and 0xff
        if (v < 16) sb.append('0')
        sb.append(v.toString(16))
    }
    return sb.toString()
}
```

Сервер хранит только маппинг `токен → WebSocket`, без привязки к identity пользователя:

```python
token_to_ws:  dict = {}   # token → websocket
ws_to_tokens: dict = {}   # websocket → set[str]
known_tokens: set  = set() # токены которые хоть раз регистрировались
```

Клиенты обмениваются токенами через E2EE — отправляют друг другу свой пул зашифрованным системным сообщением. После обмена пакет выглядит так:

```json
{
  "type": "anon_message",
  "token": "e39f013483715c300e9a7db2b601709c",
  "payload": "<зашифровано>"
}
```

Сервер знает, кто отправил пакет — отправка требует аутентифицированного соединения, как и в любом мессенджере с сервером-посредником — но не знает, кто получатель: просто находит WebSocket по токену и доставляет. Токен одноразовый: после доставки удаляется из таблицы.

### Проблема первого контакта

Классическая проблема токенной маршрутизации — **первое сообщение**. Чтобы обменяться токенами, нужно сначала как-то связаться. В большинстве мессенджеров это означает: сервер видит `A → B` хотя бы один раз.

Решение — **анонимный mailbox**, встроенный в инвайт-код.

Инвайт-код содержит не только публичный ключ и fingerprint, но и случайный 16-байтный `mailbox_tag`:

```
[version][timestamp][nonce][mailbox_tag(16б)][fingerprint][ec_point][name][sig]
```

Схема работы:

```
Alice создаёт инвайт → внутри mailbox_tag T
Bob принимает инвайт → шифрует первое сообщение ключом Alice → кладёт в mailbox[T]
Alice при подключении → спрашивает сервер: "есть ли что-то для тегов [T, X, Y, Z, ...]?"
Сервер → возвращает блобы по совпавшим тегам
Alice → расшифровывает, получает сообщение + токены Bob'а
```

Ключевой момент: Alice запрашивает **всегда ровно 20 тегов** — свой настоящий плюс случайные фейковые. Сервер не знает какой из них реальный:

```kotlin
fun buildFetchTagList(ctx: Context): List<String> {
    val real = getMyMailboxTags(ctx)
    val fakeCount = maxOf(MBOX_TOTAL - real.size, 0)  // всегда итого 20
    val fakes = (1..fakeCount).map { generateToken() }
    return (real + fakes).shuffled()
}
```

Сервер при получении `mailbox_fetch` возвращает только теги у которых есть блобы, и сразу их удаляет. Блобы без запроса автоматически удаляются через 48 часов.

Таким образом **первое сообщение больше не раскрывает пару `A → B`**. Сервер видит, что Алиса запрашивает mailbox, и видит анонимный блоб из 20 тегов — но не знает, чей блоб она забирает и кто его туда положил.

### Доверие к ключу

При первом контакте клиенты обмениваются публичными ключами. Откуда вы знаете, что получили именно ключ собеседника, а не ключ сервера-посредника? Теоретически враждебный сервер мог подменить ключ и читать всё шифрование (MITM).

Решение — **fingerprint**: SHA-256 хэш публичного ключа, который пользователи сверяют **вне системы**: показывают экраны друг другу, зачитывают по телефону, сравнивают в другом мессенджере. Та же концепция что "Safety numbers" в Signal.

```
Сверили fingerprint вне системы
    → ключ подлинный
    → шифрование надёжно
    → токены и mailbox-сообщения защищены
    → всё дальнейшее общение анонимно
```

### Что видит сервер после внедрения

До: `A1B2C3D4 → 9F8E7D6C (сообщение)`  
После: `anon_message → токен e39f0134... (доставлено)`

Граф социальных связей недоступен для **утёкших логов**. Важная оговорка: сервер хранит маппинг `токен → WebSocket`, поэтому активно враждебный оператор сервера всё равно может восстановить кто с кем общается — по внутренней таблице маршрутизации. Токены защищают от пассивной утечки логов, но не от намеренно недобросовестного сервера. Именно поэтому важна возможность самохостинга.

## Cover Traffic: скрытие по времени

Даже без fingerprint остаётся **timing-атака**. Если наблюдатель контролирует трафик обоих абонентов, он может статистически сопоставить: "Алиса отправила пакет в 14:23:01.337, Боб получил пакет в 14:23:01.891 — разница 554 мс, совпадает 1000 раз из 1000 → они общаются".

### Почему случайный шум не помогает

Первая идея — отправлять фейковые сообщения случайно, раз в 30–120 секунд. Это создаёт шум, но не решает проблему. На графе трафика такой подход выглядит как редкие пакеты без ответа — на фоне стабильного обмена между двумя пользователями они легко фильтруются статистически.

### Constant-rate cover traffic

Правильное решение — именно так работает академический протокол Loopix. Клиент **всегда** шлёт поток с фиксированным интервалом. Когда есть реальное сообщение — оно занимает место очередного шумового пакета:

```
Без защиты:  ────M──────────M──M──────────  (M = сообщение, паттерн виден)
С защитой:   N─N─M─N─N─N─N─M─NM─N─N─N─N─  (N = шум, всё одинаково)
```

Реализация: реальные сообщения ставятся в очередь, корутина с фиксированным интервалом берёт из неё следующий пакет — или отправляет шум если очередь пуста:

```kotlin
private val outboundQueue = LinkedBlockingQueue<String>()

private fun startCoverTraffic() {
    val intervalMs = if (mode == AGGRESSIVE) 1_000L else 5_000L
    coverTrafficJob = scope.launch(Dispatchers.IO) {
        val rng = SecureRandom()
        while (isActive) {
            delay(intervalMs)
            if (!isConnected) continue
            val packet = outboundQueue.poll()
            if (packet != null) {
                webSocket?.send(packet)       // реальное сообщение
            } else {
                webSocket?.send(buildNoisePacket(rng))  // шум
            }
        }
    }
}
```

Шумовой пакет намеренно неотличим от реального по структуре — тот же тип `anon_message`, случайный токен, случайный payload с паддингом до одного из нескольких фиксированных размеров.

Сервер тихо дропает пакеты с неизвестными токенами без записи в лог:

```python
async with lock:
    is_known = token in known_tokens
if not is_known:
    # cover traffic — дропаем без лога
    if msg_id:
        await send_safe(websocket, json.dumps({"type": "ack", "id": msg_id}))
    continue
```

Возможные режимы:

| Режим | Интервал | Трафик |
|---|---|---|
| Выключен | — | только реальные сообщения |
| Умеренный | 1 пакет / 5 сек | ~2–3 МБ/час |
| Агрессивный | 1 пакет / сек | ~20–30 МБ/час |

Это явно опциональная фича с предупреждением о расходе трафика и батареи — не для обычного использования.

### Честно об ограничениях

Постоянный поток скрывает timing при наблюдении с **одной стороны** (например, ISP только отправителя). Если наблюдатель контролирует трафик у обоих абонентов одновременно — статистическая корреляция всё ещё возможна, просто значительно сложнее. Полностью решить эту проблему без mix network (Nym, Loopix) с намеренными задержками и перемешиванием пакетов невозможно. Но это уровень целенаправленной операции против конкретного человека — не массового пассивного прослушивания.

## Tor Hidden Service: скрытие IP

Анонимные токены скрывают граф связей от сервера. Но сервер всё ещё видит IP адрес клиента при подключении. Для задач где важна анонимность — это недопустимо.

Решение — **Tor Hidden Service**. Обычный Tor через exit-ноды имеет проблему: Cloudflare и многие хостинги блокируют exit-ноды. `.onion` адрес решает это: трафик идёт полностью внутри сети Tor, без exit-нод и без Cloudflare в цепочке.

Конфигурация на сервере минимальная:

```
HiddenServiceDir /var/lib/tor/Subrosa/
HiddenServicePort 80 127.0.0.1:9000
```

Важный нюанс при реализации на Android: Orbot работает в двух режимах — SOCKS прокси (порт 9050) и системный VPN. В VPN режиме явный SOCKS прокси создаёт конфликт двойного туннелирования. Для `.onion` адресов нужно использовать обычный HTTP клиент — Orbot перехватит трафик на уровне системы сам:

```kotlin
// Onion через Orbot VPN — не используем явный SOCKS прокси
val client = if (wsUrl.contains(".onion")) plainWsClient else socksWsClient()
webSocket = client.newWebSocket(request, listener)
```

## Итоговая таблица угроз

| Наблюдатель | Видит без защиты | Видит с описанной архитектурой |
|---|---|---|
| Честный сервер / утёкшие логи | Граф `from → to`, содержимое | Только анонимные блобы и токены без привязки к identity |
| Враждебный сервер | Граф `from → to`, содержимое | Таблица токенов (решение — самохостинг) |
| ISP отправителя | IP сервера, время и объём | Зашифрованный Tor трафик |
| ISP получателя | IP сервера, время и объём | Зашифрованный Tor трафик |
| Оба ISP одновременно | Timing корреляция | Статистически затруднена (constant-rate) |
| Целевая операция (MITM, устройство) | Всё | Содержимое защищено E2EE |

## Итог

Четыре слоя, каждый закрывает свой вектор:

1. **Анонимный mailbox** — первый контакт не раскрывает пару `A → B`; сервер видит только блобы по случайным тегам
2. **Одноразовые токены** — все последующие сообщения маршрутизируются без fingerprint
3. **Constant-rate cover traffic** — timing-корреляция затруднена; наблюдатель видит равномерный поток
4. **Tor hidden service** — IP адрес скрыт; нет exit-нод и блокировок

Это не mix network и не абсолютная анонимность. Но для защиты от пассивного массового наблюдения и утечки логов оператора — практически достаточно.
