## Модель угроз

Subrosa разработан для противодействия следующим типам нарушителей:

### В области действия защиты

| Нарушитель | Возможности | Защита |
|---|---|---|
| Сетевой атакующий | Перехват и модификация трафика | TLS + привязка сертификата + E2EE |
| MITM с поддельным CA | Установить пользовательский CA, проксировать TLS | Обнаружение вторжения (USER_CA + PROXY) |
| Компрометация сервера | Оператор сервера читает БД | E2EE; сервер не хранит открытый текст |
| Кража физического устройства | Офлайн-извлечение файловой системы | EncryptedSharedPreferences + слой SMK |
| Форензический анализ | Cold-boot, JTAG, программное извлечение | SMK требует пароль; режим-приманка |
| Принуждение (юридическое требование) | Принудительная расшифровка | Пароль-паника, уничтожение данных, режим-приманка |
| Отладка / динамический анализ | Подключение JDWP, logcat | Антиотладка, подавление логов в Параноидном режиме |
| Атакующий на рутованном устройстве | Читать преференции от root, обходить keystore | Слой PBKDF2 SMK; предупреждение об обнаружении root |

### Вне области действия защиты

| Сценарий | Причина |
|---|---|
| Полная компрометация конечной точки (root + дамп RAM в реальном времени) | SMK находится в памяти пока приложение разблокировано |
| Корреляция трафика на стороне сервера | Временны́е метки и метаданные в сети |
| Принуждение получателя | Устройство получателя вне контроля |
| Атака на цепочку поставок (вредоносная сборка) | Требует независимой верификации APK |

## Криптографическая схема

### Иерархия ключей

```
Пароль пользователя
    │
    ▼ PBKDF2-SHA256 (300 000 итераций, соль 32 байта)
Ключ, выведенный из пароля (PDK)
    │
    ▼ AES-256-GCM
enc_smk_pwd  ──────────────────────────────────┐
                                               │ расшифровка
AndroidKeyStore AES-256 ("beacon_smk_wrap")    │
    │                                          │
    ▼ AES-256-GCM                              ▼
enc_smk_ks  ──────────────────► Storage Master Key (SMK)  [в памяти]
                                               │
                    ┌──────────────────────────┼──────────────────────┐
                    ▼                          ▼                      ▼
           EC identity privkey          Групповые AES-ключи    Блобы сообщений
         (beacon_ec_keys_enc)               (groups)      (chat_storage_encrypted)
```

### Identity-ключи

Каждый пользователь имеет одну ключевую пару EC на кривой P-256 (secp256r1). Эта пара выступает:
- Долгосрочным identity-ключом в X3DH (отправитель и получатель)
- Ключом подписи для инвайт-кодов и challenge аутентификации

Приватный ключ хранится в `EncryptedSharedPreferences("beacon_ec_keys_enc")` под ключом `"ec_priv"`. Формат хранения:
- `"smk1:" + Base64(iv[12] + AES-256-GCM(privKey.encoded, smk))` — когда SMK настроен
- `Base64(privKey.encoded)` — для устаревших записей (принудительно переоборачивается при первом чтении, если SMK разблокирован)

Публичный ключ хранится как обычный Base64 и передаётся на сервер при регистрации.

### Шифрование сообщений

Сообщения один-на-один шифруются с помощью AES-256-GCM:

```
открытый текст
    │
    ▼ AES/GCM/NoPadding
    │  ключ:  сессионный ключ (из Double Ratchet)
    │  iv:    12 случайных байт (из Cipher.init)
    │  тег:   128-битный тег аутентификации (добавляется в конец)
    ▼
iv[12] || шифртекст || тег[16]
```

Блоб шифртекста передаётся в поле `"data"` JSON-сообщения, закодированный в Base64.

### Прямая секретность

Начальное согласование ключей по схеме X3DH:

1. Получатель публикует на сервере: `IK_B` (identity key), `SPK_B` (signed prekey), `OPK_B` (one-time prekey).
2. Отправитель получает пакет и вычисляет:
   ```
   DH1 = ECDH(IK_A, SPK_B)
   DH2 = ECDH(EK_A, IK_B)       ← EK_A: эфемерный ключ, удаляется после отправки
   DH3 = ECDH(EK_A, SPK_B)
   DH4 = ECDH(EK_A, OPK_B)      ← OPK_B: одноразовый, удаляется сервером после выдачи
   master_secret = KDF(DH1 || DH2 || DH3 || DH4)
   ```
3. `master_secret` инициализирует Double Ratchet.

Каждое последующее сообщение продвигает ratchet. Компрометация одного сессионного ключа не компрометирует прошлые или будущие ключи.

Сервер уведомляет клиента, когда запас OPK опускается ниже порога (`OPK_LOW_WATERMARK = 5`) и предлагает загрузить новые пакеты.

### Постквантовое гибридное согласование ключей

`master_secret` выше в X3DH — классический ECDH (secp256r1), уязвимый к будущему квантовому компьютеру с алгоритмом Шора — и что более актуально, к атаке **"harvest now, decrypt later"**: противник, записывающий сегодняшний трафик, сможет расшифровать его ретроактивно, когда квантовые компьютеры созреют. Это критично для privileged/юридической переписки с требованием конфиденциальности на десятилетия.

Чтобы закрыть это, prekey-бандл теперь также несёт публичный ключ **ML-KEM-768** (FIPS 203, стандартизирован NIST), подписанный тем же ECDSA identity-ключом, что и SPK, и ротируемый по тому же 7-дневному циклу:

```
pq_shared_secret = ML-KEM-Decapsulate(pq_private_key, pq_ciphertext)
master_secret     = KDF(DH1 || DH2 || DH3 || [DH4] || pq_shared_secret)
```

Достаточно защитить только *начальный* корневой ключ X3DH — каждый следующий корневой ключ Double Ratchet выводится как `HKDF(dhOutput, salt=предыдущий_root_key)`, а значит для его получения нужен именно секретный предыдущий root key, а не просто взлом классического DH на этом шаге. Квантовый противник, сломавший каждый отдельный DH-шаг ratchet'а, всё равно не сможет продвинуться по цепочке без root key, а сам root key восстановим только при взломе **обоих** компонентов — классического и ML-KEM. Та же логика лежит в основе PQXDH у Signal.

Та же гибридная обработка применена везде, где секрет выводится одноразовым эфемерным ECDH вне цепочки ratchet'а: legacy-фолбэк до установления сессии, `edit`, распределение группового ключа, шифрование картинок/файлов/голосовых. Бандл или рукопожатие без постквантового компонента отклоняется целиком, а не тихо принимается как классический — это закрывает очевидную downgrade-атаку (злонамеренный сервер вырезает поле).

**Известные ограничения:**
- Сессии, установленные *до* этого апдейта, имеют чисто классический root key, который нельзя защитить задним числом — только свежее рукопожатие защищает переписку начиная с этого момента. См. заметку о миграции в `SessionKeyManager`.
- Сообщение-бутстрап анонимного mailbox для первого контакта (см. [README.md](README.md)) остаётся классическим — постквантовый ключ ML-KEM (~1.2 КБ) сделал бы инвайт-ссылки/QR-коды непрактично большими. Сессия Double Ratchet, устанавливаемая сразу после него, уже полностью постквантово-гибридная.

### Обмен ключами группы

Каждая группа имеет 256-битный случайный ключ AES (`groupKey`). Он распределяется каждому участнику по отдельности:

1. Администратор вызывает `generateGroupKey()` → `SecureRandom().nextBytes(32)`.
2. Для каждого участника M:
   ```
   shared = ECDH(adminPriv, memberPub)
   encKey = AES-256-GCM(groupKey, KDF(shared))
   ```
3. Пары `{memberId, encKey}` отправляются на сервер в сообщении `create_group`; сервер доставляет каждый `encKey` только соответствующему участнику.
4. Участник вызывает `decryptGroupKey(encKey, myPriv)` → `groupKey`.

Сообщения группы:
```
открытый текст
    │
    ▼ AES/GCM/NoPadding (ключ = groupKey, iv = случайные 12 байт)
iv[12] || шифртекст || тег[16]
```

При исключении участника администратор генерирует новый `groupKey` и распределяет его оставшимся участникам.

При локальном хранении `groupKey` оборачивается SMK (префикс `"smk1:"`) если SMK разблокирован, иначе хранится как обычный Base64.

### Двойное шифрование на устройстве (SMK)

Все чувствительные данные на устройстве получают второй слой шифрования поверх `EncryptedSharedPreferences`.

#### Генерация SMK

При первой регистрации:
```kotlin
val smk  = SecureRandom().nextBytes(32)   // 256-битный случайный ключ
val salt = SecureRandom().nextBytes(32)   // 256-битная случайная соль

enc_smk_pwd = AES-256-GCM(smk, PBKDF2(password, salt, 300_000, 256))
enc_smk_ks  = AES-256-GCM(smk, keystoreKey)   // AndroidKeyStore AES-256
```

Оба шифртекста хранятся в `EncryptedSharedPreferences("smk_config")`.

#### Пути разблокировки SMK

| Путь | Как | Когда |
|---|---|---|
| Вход по паролю | PBKDF2(пароль, соль, 300 000) → расшифровать `enc_smk_pwd` | Каждый вход |
| Биометрический вход | Ключ AndroidKeyStore → расшифровать `enc_smk_ks` | Успех биометрии |
| Разблокировка после блокировки | Те же два пути | После таймаута / выключения экрана |

Операции PBKDF2 выполняются на `Dispatchers.IO` — никогда на Main-потоке.

#### Блокировка SMK

`StorageKeyManager.lock()` заполняет нулями байтовый массив `smk` в памяти и устанавливает его в `null`. Вызывается:
- Перед `isAppLocked = true` (выключение экрана, таймаут автоблокировки)
- Как первая операция в `WipeManager.wipe()`

#### Оборачивание значений

```
wrapBytes(bytes):
    iv = случайные 12 байт
    ct = AES-256-GCM(bytes, smk, iv)
    вернуть "smk1:" + Base64(iv || ct || тег)

unwrapBytes(stored):
    если stored не начинается с "smk1:":
        вернуть Base64.decode(stored)      # путь совместимости с устаревшими данными
    blob = Base64.decode(stored[5:])
    iv = blob[0:12]
    ct = blob[12:]
    вернуть AES-256-GCM-decrypt(ct, smk, iv)
```

Прозрачная миграция: существующие незащищённые значения читаются как обычный Base64 без ошибок. При следующей записи значение оборачивается. EC приватный ключ использует принудительное переоборачивание: если `StorageKeyManager.isUnlocked`, но сохранённое значение не имеет префикса `"smk1:"`, оно немедленно переоборачивается при первом чтении.

#### Что НЕ оборачивается SMK

| Данные | Причина |
|---|---|
| SPK / OPK приватные ключи | Необходимы при холодном старте до входа |
| Состояния сессий Double Ratchet | Необходимы при холодном старте до входа |

### Хеширование паролей

Пароли приложения хешируются перед хранением:

```
v2:<saltB64>:<hashB64>
  соль = SecureRandom().nextBytes(16)
  хеш  = PBKDF2WithHmacSHA256(пароль, соль, итерации=100_000, длина=256)
```

При входе хранимый хеш сравнивается со свежевыведенным. Автоматическая миграция с устаревшего `SHA-256(password)` (формат без префикса `"v2:"`) выполняется при первом успешном входе.

### Шифрование бэкапа

Файлы бэкапа используют ту же схему с пользовательским паролем бэкапа:

```
соль    = SecureRandom().nextBytes(16)
ключ    = PBKDF2-SHA256(паролькопии, соль, 100_000, 256)
iv      = SecureRandom().nextBytes(12)
payload = AES-256-GCM(сериализованные_данные, ключ, iv)
файл    = соль[16] || iv[12] || payload
```

## Аутентификация

### Server Handshake

Аутентификация — challenge-response через ECDSA. Сервер никогда не хранит и не передаёт пароль:

1. Клиент подключается; сервер отправляет `{type: "challenge", data: "<32 случайных байта в base64>"}`.
2. Клиент подписывает байты challenge своим EC приватным ключом (SHA256withECDSA).
3. Клиент отправляет `{type: "register", username, public_key, signature, ...}`.
4. Сервер верифицирует подпись по публичному ключу.
5. При успехе: `{type: "auth_ok"}` + `{type: "turn_config", ...}`.

Таймаут handshake: 15 секунд.

Конфликт сессий: когда второе устройство аутентифицируется под тем же именем пользователя, сервер отправляет `{type: "session_conflict"}` существующей сессии. Существующий клиент отключается и уведомляет пользователя.

### Инвайт-коды

Инвайт-коды — ECDSA-подписанные бинарные блобы, с префиксом и Base64url-кодированием (без паддинга):

```
bc:<base64url(payload)>
```

Структура payload (текущий формат, версия `0x03`):

```
version(1Б) | ts(4Б) | nonce(8Б) | mailboxTag(16Б) | fp(8Б) | ecPoint(65Б) | nameLen(1Б) | name(nameLen Б) | rawSig(64Б)
```

- `ecPoint` — сырая 65-байтная несжатая EC-точка (X9.62 `0x04 || X || Y`); заголовок X.509 SPKI для P-256 восстанавливается при парсинге, а не хранится в инвайте.
- `rawSig` — сырая ECDSA-подпись `r || s` (по 32 байта, со знаковой коррекцией), а не DER — конвертация в/из DER происходит только вокруг вызова JCA `Signature`.
- Версия `0x02` (устаревшая, без поля `mailboxTag`) **отклоняется** при парсинге —
  раньше принималась для обратной совместимости, но это означало бы прямой,
  видимый серверу `get_key`-запрос вместо анонимного mailbox-бутстрапа, что тихо
  ломало гарантию анонимности первого контакта. `InviteCodeManager.parseInviteCode()`
  теперь безусловно требует `version == 0x03`.
- Тег в инвайте — **одноразовый и отдельный от постоянного рабочего тега**
  (`AnonTokenManager.getOrCreateMyInviteMailboxTag()`, не
  `getOrCreateMyPersistentMailboxTag()`): после первого успешного mailbox-депозита
  по этому тегу он вычёркивается из списка опроса (`removeMailboxTagIfEphemeral()`).
  Постоянный тег для повседневной связи никогда не публикуется в инвайт-коде —
  контакт узнаёт его только из поля `mailbox_tag`, зашитого внутрь уже
  зашифрованного сообщения при первом обмене токенами. Кнопки "Копировать"/
  "Поделиться"/"Показать QR" в Profile принудительно ротируют инвайт-тег на
  новый при каждом нажатии.

Подписываемая часть (всё до `rawSig`): `version | ts | nonce | [mailboxTag] | fp | ecPoint | nameLen | name`.
Алгоритм подписи: SHA256withECDSA с identity-ключом приглашающего.
TTL: 7 дней от `ts`.

Верификация:
1. Восстановить EC публичный ключ из `ecPoint` (добавить фиксированный заголовок X.509).
2. Пересчитать `fp` = первые 8 байт SHA-256(X.509-encoded публичный ключ), сравнить.
3. Проверить `ts` + 7 дней > сейчас.
4. Верифицировать ECDSA подпись над подписываемой частью.

Desktop и Android используют этот бинарный формат байт-в-байт идентично (включая конвертацию DER↔raw подписи и восстановление EC-точки) — см. пункт 13 ниже про историю этого переноса.

## Антифорензика

### Параноидный режим

Когда включён:
- Все вызовы `Log.d`, `Log.i`, `Log.w` подавляются через обёртку `BLog` (проверяет `ParanoidMode.isEnabled`).
- Выполняется `logcat -c` для очистки буфера logcat текущего процесса.
- `IntrusionDetector.scan()` запускается при каждом `onResume()` (на `Dispatchers.IO`).
- При обнаружении угрозы (`handleThreat()`):
  1. Logcat очищается повторно.
  2. HTTP POST на настроенный пользователем URL-оповещения (fire-and-forget coroutine).
  3. Если включён "wipe при взломе": `WipeManager.wipe(level)`.
  4. Иначе: режим стелс (показать `DecoyScreen`).

### Защита экрана

`WindowManager.LayoutParams.FLAG_SECURE` применяется к главному окну активности. Это предотвращает:
- Скриншоты через системное сочетание клавиш.
- Захват содержимого экрана приложениями записи.
- Отображение миниатюры приложения в экране "Последние приложения".

### Антиотладка

Проверяется при запуске:
- `android.os.Debug.isDebuggerConnected()` — обнаруживает подключённый JDWP-отладчик.
- Проверка порта JDWP через сокет.

Эти проверки выполняются до показа UI. При обнаружении отладчика приложение может завершиться или подавить чувствительные операции.

### Обнаружение root

Сканирует признаки компрометации устройства:
- Распространённые бинарники в PATH: `su`, `busybox`, `magisk`, `daemonsu`.
- Известные имена пакетов Superuser APK.
- Пути записи, которые должны быть доступны только для чтения на стоковой прошивке.
- Эвристики в стиле RootBeer.

Обнаруженный root считается предупреждением; пользователь уведомляется, но принудительного выхода нет. В Параноидном режиме обнаружение root запускает `handleThreat()`.

### Обнаружение вторжения

`IntrusionDetector.scan()` возвращает `ScanResult` со списком активных угроз:

| Угроза | Серьёзность | Описание |
|---|---|---|
| `PROXY` | Средняя | Настроен системный HTTP-прокси |
| `USER_CA` | Средняя | Установлен пользовательский корневой CA |
| `PROXY + USER_CA` | Критическая | Почти достоверный MITM-прокси |
| `VPN` | Низкая | Активно VPN-соединение |
| `ADB` | Средняя | Android Debug Bridge включён |
| `DEV_OPTIONS` | Низкая | Режим разработчика включён |

В Параноидном режиме результат сканирования с критической серьёзностью запускает `handleThreat()`.

### Привязка сертификата

`CertificatePinner` (OkHttp3) привязывает TLS-сертификат сервера или публичный ключ. Соединение, предъявляющее неожиданный сертификат, отклоняется даже если он подписан доверенным CA. Это нейтрализует атаки с установкой пользовательского корневого CA.

## Механизмы экстренного реагирования

### Уровни уничтожения данных

| Уровень | Операции | Применение |
|---|---|---|
| `HARD` | Удалить все преференции, файлы, базы данных, данные WebView, ключи AndroidKeyStore | Обнаруженная угроза, пересечение границы |
| `NUCLEAR` | `HARD` + `ActivityManager.clearApplicationUserData()` | Максимальная срочность; процесс завершается системой |

`StorageKeyManager.lock()` вызывается как самая первая операция любого уничтожения данных — SMK обнуляется из памяти до любого другого деструктивного шага.

### Пароль-паника

Пользователь может настроить дополнительный "пароль-паника" в настройках. Если при входе введён этот пароль вместо реального:
1. В фоне запускается `WipeManager.wipe(HARD)`.
2. Может отображаться фиктивный экран загрузки для выигрыша времени.

Это позволяет незаметно запустить уничтожение данных, выглядя как обычный вход.

### Мёртвая рука

Запланированный будильник (`AlarmManager.setExactAndAllowWhileIdle`) срабатывает, если пользователь не подал признак жизни в течение настроенного интервала (часы или дни). По будильнику:
1. `WipeReceiver` получает `DMS_FIRE`.
2. Вызывается `WipeManager.wipe()`.

Нормальная отметка о присутствии: пользователь открывает приложение (автоматически) или нажимает кнопку ручной отметки. Временна́я метка последней отметки хранится в `EncryptedSharedPreferences`.

`BootReceiver` восстанавливает будильник DMS после перезагрузки устройства.

### Режим-приманка

Когда уничтожение `HARD` запускается при включённом "режиме-приманке":

1. Перед удалением сохраняется в `beacon_recovery` (открытый файл):
   - `username`
   - `password_hash` (хеш, не сам пароль)
   - `user_id`
   - Случайная выборка имён контактов

2. Выполняется полное уничтожение `HARD`.

3. При следующем запуске приложения обнаруживается `beacon_recovery`:
   - Создаётся фиктивный аккаунт с сохранёнными учётными данными.
   - Заполняются фиктивные записи чатов.
   - Приложение выглядит нормально при поверхностном осмотре.

Фиктивный аккаунт не может расшифровать никакие реальные сообщения (все ключи уничтожены). Обеспечивает правдоподобное отрицание при принуждении.

## Безопасность сессий

- Одна активная сессия на устройство на имя пользователя.
- `device_id` — UUID, генерируется один раз при установке и передаётся при каждой аутентификации.
- Если два устройства аутентифицируются под одним именем, сервер отправляет `session_conflict` старой сессии, которая затем отключается и уведомляет пользователя.
- Токены сессий не хранятся; полная ECDSA-реаутентификация происходит при каждом WebSocket-подключении.

## Известные ограничения

1. **Метаданные на сервере.** Сервер знает, кто с кем общается (социальный граф) и временны́е метки сообщений. Содержимое сообщений ему неизвестно. Защита от анализа трафика не предусмотрена.

2. **SMK в памяти.** Пока приложение разблокировано и находится на переднем плане, SMK живёт в памяти. Полный дамп RAM с рутованного или взломанного устройства может его извлечь.

3. **Программные ключи AndroidKeyStore.** На устройствах без аппаратного Secure Element ключи AndroidKeyStore хранятся как программные ключи в TEE или в `/data`. Атакующий с глубоким доступом к ОС может их извлечь, обходя путь `enc_smk_ks`. Путь `enc_smk_pwd` (PBKDF2 300K) обеспечивает защиту независимо от Keystore.

4. **Истощение OPK.** Если запас OPK пользователя исчерпан и клиент офлайн, сервер может выдать один и тот же OPK нескольким отправителям. Клиенты должны проактивно загружать новые пакеты OPK.

5. **Распределение ключей группы через сервер.** Скомпрометированный сервер может отказаться доставлять новый групповой ключ участнику после ротации, фактически молча исключая его. Для критически важных сценариев рекомендуется внеполосная верификация состава группы.

6. **Пароль бэкапа.** Пароль бэкапа нигде не хранится. Если он утерян, бэкап не может быть расшифрован. Механизма восстановления нет.

7. **Форензика режима-приманки.** Опытный форензический эксперт может обнаружить следы предшествующего уничтожения данных (временны́е метки файловой системы, записи журнала, паттерны wear-leveling на флеш-памяти). Режим-приманка обеспечивает социальное/юридическое прикрытие, а не техническую необнаруживаемость.

8. **Перехват нажатий клавиш на десктопе.** В отличие от `FLAG_SECURE` на Android (реальная гарантия на уровне ОС для окна приложения), защиты от аппаратного кейлоггера (инлайн-устройство на USB) или системного низкоуровневого хука клавиатуры (например, Windows `WH_KEYBOARD_LL`) на уровне обычного приложения не существует — они перехватывают нажатия ещё до того, как их получит любое приложение, включая наше. Десктоп-клиент снижает этот риск экранной клавиатурой — она доступна как для полей пароля (вход, регистрация, бэкап, смена пароля, разблокировка после автолока), так и для обычного набора текста сообщений в чате, с раскладкой, перемешиваемой при каждом открытии — текст вводится кликами мыши без единого нажатия клавиши. Это закрывает самый распространённый на практике класс кейлоггеров (аппаратный/драйверный перехват клавиатуры). Дополнительно подключены исключение окна из захвата экрана (`WDA_EXCLUDEFROMCAPTURE` на Windows, `NSWindowSharingNone` на macOS) — так что ни экранная клавиатура, ни содержимое сообщений не читаются через скриншоты или запись экрана — и гигиена буфера обмена (авто-очистка скопированного текста сообщения через 30 сек, исключение из истории буфера Windows и облачной синхронизации Cloud Clipboard). Ничего из этого не защищает от malware с доступом уровня ядра, читающего память процесса, а также от Windows Accessibility/UI Automation API, который может программно прочитать текст элементов управления — в обход любой защиты уровня пикселей; кросс-платформенного способа исключить из этого окно, не сломав при этом легитимные вспомогательные технологии, не существует. Физический ввод по-прежнему доступен и не блокируется вне полей пароля, поэтому экранная клавиатура включается по желанию на каждое сообщение. На macOS существует более сильный механизм (`EnableSecureEventInput()` — тот же API, что использует Terminal и 1Password при вводе пароля), но он пока не подключён.

9. **Своп/hibernation на десктопе за пределами SMK.** Storage Master Key хранится в заблокированном нестраничном нативном буфере (`VirtualLock`/`mlock`), а ключи сообщений зануляются после использования, но весь JVM heap целиком (включая временный расшифрованный текст сообщений в UI) заблокировать от подкачки на уровне обычного (не привилегированного) процесса практически невозможно. На машине без полнодискового шифрования (BitLocker/FileVault/LUKS) теоретически можно восстановить plaintext из файла подкачки или образа гибернации. Включение полнодискового шифрования на уровне ОС — это рекомендация при развёртывании, а не то, что может обеспечить само приложение.

10. **Временные файлы вложений на десктопе.** Открытие полученного файла-вложения расшифровывает его во временный файл, чтобы передать его внешней программе просмотра. Временный файл затирается через `secureDelete` (3 прохода) по таймеру и при завершении JVM, а не удаляется обычным способом — но жёсткий крэш или принудительное завершение процесса до срабатывания любого из этих механизмов всё ещё может оставить восстановимый plaintext во временной директории ОС. Внешняя программа просмотра также может сохранить собственную ссылку на путь (например, в списке недавних файлов) вне контроля этого приложения.

11. ~~Запрос prekey-бандла раскрывает пару fingerprint серверу~~ — **частично смягчено, с известными остаточными утечками**: `get_prekey_bundle` раньше напрямую говорил серверу «A хочет бандл B» — то же ограничение, что и у собственного сервера Signal. Теперь это снижено двумя способами, оба переиспользуют уже существующие примитивы, а не новую криптографию: (а) **анонимный batched-фетч** (`get_prekey_bundles_batch`) — настоящая цель дополняется приманками из собственных контактов запрашивающего (по аналогии с фейковыми тегами в анонимном mailbox; приманки здесь обязаны быть *настоящими* fingerprint'ами, в отличие от mailbox-тегов, иначе сервер мгновенно вычислит единственный настоящий запрос среди фейков — идея с самостоятельно созданными «призрачными» аккаунтами в роли приманок была рассмотрена и отклонена: аккаунт, никогда не несущий реального трафика, со временем становится различимым и исключаемым), при этом ни у одной приманки не расходуется одноразовый prekey. При отсутствии контактов для прикрытия используется старый прямой fetch — батч размером 1 никакого прикрытия не даёт. (б) **Bootstrap-токен** — каждый бандл, который сервер выдаёт (batched или напрямую), теперь помечается в момент выдачи одним из уже зарегистрированных анонимных токенов владельца бандла (из пула, который и так поддерживает `AnonTokenManager`/`subscribe_tokens`), что позволяет доставить последующий `session_init` через `anon_message`, а не напрямую по адресу — это закрывает утечку, которая иначе свела бы на нет анонимизацию самого fetch'а.

    **Остаточные пробелы, найденные при самоаудите и пока не закрытые:** (i) поскольку приманки берутся из *настоящего* списка контактов запрашивающего, один-единственный батч отдаёт серверу весь граф контактов этого пользователя открытым текстом — механизм меняет «какой fingerprint настоящая цель» на «вот мой полный список контактов», а это реальная цена, а не бесплатная анонимизация; (ii) размер батча уменьшается ниже `MAX_BATCH_BUNDLE_TARGETS`, если у запрашивающего меньше контактов, чем нужно для полного батча — это раскрывает приблизительный размер списка контактов; (iii) если у цели никогда не было зарегистрированного анонимного токена для прикрепления к бандлу (или скомпрометированный сервер просто никогда не прикладывает `bootstrap_token`), клиент молча откатывается на прямую адресацию `session_init` по fingerprint — без какого-либо предупреждения пользователю о том, что анонимизация деградировала. Пассивный сервер может форсировать такой откат безусловно, и клиент никак не может это обнаружить. Ни одна из этих проблем не ломает конфиденциальность самого сообщения (E2EE-полезная нагрузка не затронута), но все они существенно ограничивают то свойство анонимности, ради которого этот механизм создавался.

    **Это смягчение (в отличие от ML-KEM/X3DH криптографии в остальной части документа) — собственный протокольный дизайн, а не реализация независимо проверенного стандарта анонимности** — та же честная оговорка, что уже применяется к системе анонимной маршрутизации/mailbox/cover traffic, которую оно расширяет. Независимого аудита не проходило.

12. **Покрытие анонимной маршрутизации пока не полное.** 1:1 текст, typing, read receipts, реакции, правки, удаления, чанки картинок/файлов/видео, групповые сообщения, удаление группового сообщения и (с пункта 18 ниже) сигналинг 1:1 звонков анонимизируются по токенам, как только для контакта появляется пул токенов (до этого — fallback на адресацию по fingerprint). Сигналинг **групповых** звонков (`call_group_*`) **намеренно исключён** — см. пункт 18 ниже. `channel_post` не покрыт — сервер в принципе мог бы видеть, кто постит, и список подписчиков виден серверу — но фича «Каналы» сейчас отключена на уровне UI на обеих платформах (см. `ARCHITECTURE.md`), так что у этого пробела нет реальной поверхности атаки сегодня. Если каналы когда-нибудь включат обратно, анонимизация распространения потребует того же обмена токенами подписчиков через mailbox, о котором шла речь при принятии решения отключить каналы.

13. ~~Инвайт-коды Android и Desktop несовместимы друг с другом~~ — **исправлено**: `InviteCodeManager` на десктопе переписан под тот же бинарный формат `bc:<...>`, что и Android (побайтово скопированы раскладка полей, конвертация ECDSA-подписи DER↔raw и восстановление EC-точки). Это сделано как перенос кода без живого кросс-платформенного теста — реальный обмен инвайтами Android↔Desktop ещё нужно один раз прогнать, чтобы подтвердить корректность побайтового переноса (см. `desktop/SECURITY_TEST_PLAN.md`, раздел 14).

14. ~~Сервер никогда не привязывал identity из `register` к ключу, доказанному в handshake'е~~ — **исправлено**: `challenge_response` доказывал только владение *каким-то* ключом, но последующее сообщение `register` читало отдельное, присланное клиентом поле `public_key`, из которого вычислялось имя пользователя (`SHA-256(public_key)[:8]`) — без проверки, что это тот же ключ, что прошёл handshake. На практике это позволяло любому, кто знал *публичный* ключ жертвы (публичный по определению — это её identity-ключ), зарегистрироваться под её fingerprint'ом, вообще не владея приватным ключом жертвы: реальное устройство выгонялось через `session_conflict`, а сообщения, адресованные этому fingerprint'у, приходили на соединение атакующего. Это **не** позволяло расшифровать трафик жертвы или подделать валидную сессию — `SessionKeyManager.initiateSession()`/`receiveSession()` проверяют подписи SPK и PQ-ключа относительно заявленного identity-ключа перед использованием бандла, и атакующий не может создать валидную подпись без приватного ключа жертвы — поэтому реальный эффект был в захвате соединения/доступности и утечке метаданных (тайминг, размер входящего трафика), а не в компрометации конфиденциальности или подлинности содержимого сообщений. Исправлено в `ForEXP/server.py`: байты публичного ключа, проверенные во время `challenge_response`, теперь сохраняются, и `register` отклоняется, если его `public_key` не совпадает с ними в точности (федерационные пиры, аутентифицирующиеся отдельной HMAC-схемой, из этой конкретной проверки исключены).

15. ~~Ротация группового ключа при удалении участника могла доставить новый ключ самому удалённому участнику~~ — **исправлено**: в `GroupInfoScreen.kt` удаление участника читало состояние Compose ДО удаления (`group!!.members`) для построения списка получателей после ротации, а `MessengerService.rotateGroupKey()` исключала только самого вызывающего (`it != username`), но никогда — конкретно удаляемого участника. В итоге только что ротированный AES-256 групповой ключ отправлялся напрямую аккаунту, который только что выгнали, что полностью сводило на нет смысл ротации при удалении. Исправлено: список участников группы теперь перечитывается из хранилища уже после завершения удаления, плюс на месте вызова добавлен явный фильтр, исключающий id удалённого участника — вторым слоем защиты. Проверено, что у Desktop-клиента этого бага нет — его `rotateGroupKey()` сама перечитывает состояние группы из хранилища уже после того, как удаление сохранилось.

16. ~~Несколько типов серверных сообщений вообще не проходили через rate-limiting~~ — **исправлено**: в таблице `default_limits` функции `rate_limit_check()` отсутствовали записи для `anon_message` и `mailbox_put`, из-за чего эти типы тихо резолвились в «без лимита» (функция безусловно возвращает `True`, если `max_count` ложно), хотя по коду, который её вызывает, выглядело, будто лимит есть. `register_bundle`, `channel_create`, `subscribe_tokens` и `profile_update` вообще никогда не вызывали `rate_limit_check()`, а `register_bundle` вдобавок не имел ограничения на размер (в отличие от аналогичного пути `publish_prekey_bundle`), что делало его дешёвым вектором роста памяти/диска для любого клиента, готового самостоятельно зарегистрировать одноразовую identity. Теперь у всех пяти типов есть явные лимиты по типу, а `register_bundle` проверяет тот же лимит `MAX_BUNDLE_SIZE_BYTES`, что и основной путь публикации бандла.

17. ~~Самостоятельно развёрнутые relay-серверы («сыновья») были жёстко привязаны к федерации с публичным сервером оператора~~ — **исправлено**: `ForEXP/start-son-server.bat` при первом запуске безусловно записывал `FEDERATION_PEERS=wss://api.beacon-app.org` в сгенерированный `.env`, независимо от намерений пользователя — любой, кто использовал скрипт быстрого старта для построения полностью приватной, самодостаточной федерации из своих же узлов, всё равно получал узел, который пытался подключиться к инфраструктуре оператора. 18. ~~Сигналинг звонков никогда не анонимизировался — во избежание бага с надёжностью~~ — **исправлено через двухфазную схему запрос/ответ** (касается только 1:1 звонков; сигналинг групповых звонков `call_group_*` этим пунктом не затронут и по-прежнему всегда идёт напрямую, см. ниже). Исходная проблема: маршрутизация `call_offer`/`call_ice`/и т.д. через `anon_message` означала, что получатель, хоть на миг оказавшийся офлайн (кратковременный реконнект, сетевой сбой), получал пакет молча положенным в очередь вместо живой доставки — у `anon_message` нет гарантии живой доставки, и нет fallback на пропущенный звонок/разбудить через FCM для анонимно маршрутизируемого трафика (это есть только в *прямой* ветке звонков на сервере). Доставленный с опозданием `call_offer` бесполезен, как только звонящий уже истёк по таймауту, а отложенный `call_end` мог оставить UI звонка на другой стороне висеть. Это было воспроизведено вживую по совпадающим логам клиента/сервера (`[ANON] Токен ... офлайн, сообщение в очереди` точно в момент, когда попытка звонка молча провалилась) и изначально «исправлено» переводом всего сигналинга звонков на прямую адресацию — что закрыло баг с надёжностью, но вновь открыло утечку метаданных (сервер видит, кто кому звонит и когда).

    Двухфазная схема разбивает звонок на два шага: сначала уходит лёгкий пинг `call_request_audio`/`call_request_video` (анонимно маршрутизируемый, устойчивый к отложенной доставке из очереди — если получатель переподключается в рамках уже существующего 45-секундного таймаута дозвона, очередь `token_pending` на сервере сбрасывается ему в момент, когда он заново подписывается на свои токены, а это происходит автоматически при каждом реконнекте). Собеседник отвечает `call_response(accepted=true)` — этот обмен тоже анонимный, тем же путём. Если собеседник реально офлайн (не переподключился за 45 секунд) — звонящий получает чистое «нет ответа», как при обычном телефонном звонке, это ожидаемое поведение.

    **Первая версия этого пункта также анонимизировала настоящий SDP/ICE-сигналинг** (`call_offer`/`answer`/`ice`/`end`) после ответа, рассуждая, что раз живость подтверждена секунду назад — последующие сообщения тоже долетят вживую. **Живое тестирование на реальном телефоне это опровергло**: даже после подтверждённого `call_response`, WebSocket-соединение телефона иногда на долю секунды подвисало прямо посреди SDP/ICE-обмена — сервер в этот момент видел токен как офлайн и клал ОДИН конкретный пакет (ICE-кандидат либо сам `call_answer`) в очередь вместо живой доставки (подтверждено логами сервера: вперемешку `[ANON] Доставлено по токену` и `[ANON] Токен ... офлайн, сообщение в очереди` в рамках одного и того же звонка). SDP/ICE-согласование не терпит даже секундной задержки на одном пакете — в отличие от фазы запроса, здесь нет прощающего таймаута. Поэтому реальный SDP/ICE-сигналинг возвращён на прямую адресацию, как и было до этого пункта — анонимной остаётся только фаза запрос/ответ. Групповые звонки (`call_group_invite`/`call_group_join`/`call_group_answer`/`call_group_ice`/`call_group_leave`) в двухфазную схему не включены вовсе — они как шли, так и идут напрямую.

19. ~~Пул анонимных токенов контакта мог никогда не собраться, навсегда закрепляя переписку на прямой/legacy-адресации~~ — **исправлено**: обмен токенами с контактом (`sendAnonTokensTo`) сам требует завернуть токен-payload в `anon_message`, что требует **уже иметь** токен от этого контакта — а токен они могут дать только тем же способом. 20. ~~Повторное открытие своего же экрана профиля могло молча сломать уже идущий mailbox-обмен, навсегда закрепляя канал с контактом в состоянии "устанавливается"~~ — **исправлено**: инвайт-код, показанный в профиле (и вшитый в него тег анонимного mailbox), пересоздавался при каждом заходе на экран — старый тег сразу удалялся из "тегов, которые я опрашиваю", и вместо него регистрировался совершенно новый, о котором никто больше не знал. Исправлено так же: сохранять и переиспользовать.)

    **Побочный баг, найденный в этом же фиксе, в тот же день**: первая версия вызывала `addMyMailboxTag` только в ветке "генерируем новый код" — при переиспользовании уже сохранённого кода (обычный, частый случай после этого фикса) регистрация тега вообще пропускалась. Если текст инвайт-кода (`UserStorage`) и список "моих mailbox-тегов" (`AnonTokenManager`, отдельный файл зашифрованных настроек) когда-либо расходились между собой — например, из-за частичного сброса данных, который чистит один файл, но не другой (наблюдалось на практике при повторных переустановках во время тестов) — тег переиспользуемого кода мог молча никогда не зарегистрироваться, оставляя `pollMailbox()` без единого реального тега на неопределённый срок (подтверждено вживую: за всю сессию ни разу не сработал лог `pollMailbox`). Исправлено: регистрация тега теперь безусловная при каждом вызове — `addMyMailboxTag` идемпотентна, повторная регистрация уже известного тега — no-op.

Подтверждено вживую на свежей установке, где использовался только диалог "Добавить контакт": `pollMailbox: 20 тегов (0 реальных)` бесконечно — устройство могло класть токены для контактов (у него был *их* тег из погашенного *их* инвайт-кода), но у него не было ничего своего, куда контакты могли бы положить депозит. Оба варианта срабатывают безусловно, как только аккаунт становится рабочим, независимо от того, зайдёт ли пользователь когда-либо в свой профиль.

22. ~~Фото и файлы молча не отправлялись, если PQ-публичный ключ получателя ещё не был закэширован в памяти, без единой повторной попытки~~ — **исправлено**: `sendImage`/`sendFile` используют одноразовое гибридное шифрование (`CryptoManager.encrypt`/`encryptFile`), которому нужны и классический, и PQ публичный ключ получателя локально в кэше — в отличие от текста, который едет через уже установленную сессию Double Ratchet и не нуждается ни в одном из них. Замечено при этом фиксе, не устранено — голосовые сообщения не были заявленным симптомом, и это требует собственной выделенной очереди (по образцу фикса выше), а не быстрой заплатки.

21. ~~Депозит в mailbox автоматически добавлял отправителя в контакты и показывал его сообщение, даже если получатель никогда не добавлял отправителя в ответ~~ — **исправлено**: обладания чьим-то инвайт-кодом достаточно, чтобы вычислить его mailbox-тег и положить туда депозит — но изначально задуманный анти-спам контракт продукта был в том, что сообщение никогда не доходит до пользователя, если *этот пользователь* сам, независимо, не добавил отправителя первым (взаимное добавление), а не просто в том, что отправитель знает, как достучаться до mailbox получателя. Теперь payload депозита несёт имя отправителя, применяется только если у получателя ещё нет своего имени для этого контакта — уже не критично, раз депозиты теперь и так проходят проверку взаимности, но не помешает для законного случая взаимного добавления.)

23. ~~Одноразовый анонимный токен мог быть использован дважды при сбое отправки~~ — **исправлено**: механизм "вернуть токен в локальный пул, если `sendWs()` вернул `false`" исходил из того, что этот сигнал надёжно означает "кадр точно не покинул устройство". Найдено вживую: под сетевой нагрузкой (конкретно — во время видеозвонка, где WebRTC конкурирует за CPU и пропускную способность с самим WebSocket-соединением) `sendWs()` может локально сообщить о неудаче, в то время как пакет всё-таки доходит до сервера и получает `anon_delivery_ack`. Токен, к этому моменту уже "восстановленный" для повторного использования, оказывается потрачен дважды — второе сообщение с ним уходит в никуда (сервер уже стёр маршрут для этого токена после первой доставки), при этом отправитель считает, что сообщение ушло успешно (`sendWs=true` на второй, обречённой попытке). Исправлено: механизм восстановления токена в пул отключён во всех трёх местах, где применялся. Сообщение по-прежнему ставится в очередь на повтор — теряется только сам токен, а не рискует быть использован дважды. Осознанный компромисс: закрыть эту дыру полностью нельзя без надёжного способа знать судьбу байт на проводе в момент локального сбоя, которого не существует в принципе.

24. ~~Порт `server.py` (9000) был напрямую доступен из интернета, в обход Cloudflare и nginx~~ — **исправлено**: nginx настроен пускать входящий трафик только с подсетей Cloudflare (`allow <cloudflare>; deny all;`), но `server.py` слушает `0.0.0.0:9000` — а файрвол (`ufw`) на боевом сервере оказался **неактивен** (`ufw status` → `inactive`), то есть вся защита "только через Cloudflare" не действовала ни секунды на практике: порт 9000 был открыт всем, минуя и Cloudflare, и nginx, и любые ограничения по IP. Обнаружено по питоновскому traceback'у в логе сервера (`websockets.exceptions.InvalidUpgrade: invalid Connection header: keep-alive`) — верный признак прямого, не через nginx, подключения. Исправлено: `ufw` включён (после аудита существующих правил, чтобы не потерять SSH-доступ), порт 9000 явно закрыт снаружи, доступ подтверждён отсутствующим извне (`curl` с другого хоста → таймаут). Урок: наличие правила `allow`/`deny` в конфиге ничего не значит, если сам файрвол не включён — стоит периодически проверять `ufw status`, а не только состав правил.

25. ~~Не было защиты от массовой регистрации новых identity (Sybil-флуд)~~ — **добавлено**: `rate_limit_check()` считает лимиты по `username` — то есть по identity, а identity бесплатно штампуется новым ECDSA-ключом на каждое подключение. Атакующий с множеством устройств/IP обходит любой IP-based лимит тривиально, заводя новую identity вместо одной. Добавлены `MAX_REGISTERED_USERS` (жёсткий потолок на общее число когда-либо зарегистрированных identity, по умолчанию не ограничено — настройка конкретного деплоя) и `POW_DIFFICULTY_BITS` (proof-of-work на первую-в-жизни регистрацию каждого fingerprint'а — цена в реальном CPU-времени устройства, а не в IP-адресе, который атакующий с большим числом устройств меняет бесплатно). Оба применяются только к новым identity, никогда — к реконнекту уже известных, и оба по умолчанию выключены (`0` = не активно).
