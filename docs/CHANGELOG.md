**Добавлено — опциональное шифрование БД сервера (SQLCipher):**
- Все 28 мест `sqlite3.connect(DB_PATH)` в `server.py` заменены на единый
  `db_connect()`. Если задан env `DB_ENCRYPTION_KEY_HEX` (32-байтный hex-ключ)
  — БД открывается через SQLCipher (`sqlcipher3-binary`), иначе прежнее
  поведение на чистом `sqlite3`, обратная совместимость сохранена.
  Защищает от офлайн-доступа к файлу БД (кража диска/бэкапа, доступ хостера)
  — **не** от root-доступа к уже запущенному процессу, ключ неизбежно живёт
  в его памяти. Живьём проверено на VPS: поймали и разобрали по пути кривую
  ошибку `MemoryError` от `sqlcipher3` — на деле означавшую попытку открыть
  старую незашифрованную БД новым ключом (HMAC-проверка страницы 1 не
  проходит), а не нехватку памяти.

**Убраны лишние эмодзи-маркеры из логов и диагностики:**

**Найдено и исправлено — гонка при отправке read-квитанции:**
- В `ChatScreen.kt` два независимых `LaunchedEffect` запускаются практически
  одновременно при открытии чата: один грузит историю и шлёт `sendRead()` за
  последнее непрочитанное сообщение, другой — только в нём `bindService()`
  подключает `messengerService`. Порядок между `LaunchedEffect` не
  гарантирован — если первый выигрывал гонку, `messengerService` был ещё

  этого открытия чата терялась без повтора. Исправлено: дублирующая
  отправка read-квитанции добавлена в `onServiceConnected`, где
  `messengerService` гарантированно не `null`; повторная отправка того же
  watermark-id безвредна.

**Найдено и исправлено — поле ввода TOTP-кода пряталось за клавиатурой:**
- `TotpSettingsScreen.kt` (тот же экран для обязательной настройки при
  регистрации и для профиля) использовал только `imePadding()`, который не
  даёт клавиатуре перекрыть контент физически, но не подтягивает
  сфокусированное поле в видимую область на длинном экране. Добавлен
  `BringIntoViewRequester` на оба поля ввода кода (основной setup-flow и
  форма отключения TOTP).

**Переработана маскировка под калькулятор (была отключена от UI):**
- Тумблер был скрыт в `WipeSettingsScreen.kt` — код разблокировки был
  захардкожен (`4 + 20 =`), что не защита в открытом исходнике для
  публичного приложения. Разблокирована в UI с настраиваемым кодом.
- Код разблокировки теперь — **число-результат**, не фиксированная
  последовательность нажатий: любое выражение на калькуляторе, дающее
  заданное число (`7+15=`, `21×2=` и т.д.), открывает мессенджер.
  `UserStorage.getCalculatorUnlockResult()`/`setCalculatorUnlockResult()`.
- **Дефолтного кода нет вообще** — если код не задан, калькулятор никогда не
  разблокируется (раньше был дефолт `24`, унаследованный от старого
  хардкода `4+20=`, тоже убран по ходу правок).
- Порядок применения переделан: включение тумблера само по себе больше не
  трогает `UserStorage`/`PackageManager` и не убивает процесс — только
  показывает поле ввода. Реальное включение маскировки (замена
  иконки/лаунчера через `PackageManager.setComponentEnabledSetting`, что и
  убивает процесс) происходит только по кнопке "Сохранить и включить", и
  только если введено валидное число. Раньше тумблер применялся мгновенно,
  до того как пользователь успевал ввести свой код — первое включение
  всегда происходило вслепую с дефолтным кодом.
- **Отдельно найдено и исправлено** — паник-вайп и decoy-восстановление
  (`WipeManager.hardWipe()`, `wipeForDecoyKeepAlive()`,
  `MessengerService.performEmergencyWipe()`) переносили флаг "маскировка
  включена" через вайп в промежуточное `beacon_recovery`-хранилище, но не
  переносили сам код разблокировки (стирался вместе с остальной БД). После
  восстановления профиля маскировка включилась бы без кода — постоянный
  локаут. Код теперь переносится вместе с флагом во всех трёх местах;
  `UserStorage.migrateDecoyState()` включает маскировку обратно только если
  код реально дошёл целым, иначе просто оставляет её выключенной.

**Найдено и исправлено — неверная инструкция про invite-код в UI:**
- `ProfileScreen.kt`-предупреждение и текст в "Гиде по защите"
  (`guideInviteDesc`) советовали: "для нового человека жмите Copy/Share
  заново, это сгенерирует свежий код" — а на устройстве в любой момент
  активен только **один** invite-тег (`PREF_MY_INVITE_TAG`); повторное
  нажатие Copy/Share/QR ротирует его и убирает старый тег из списка
  опроса mailbox, даже если предыдущий получатель ещё не подключился. Его
  код при этом выглядит валидным (подпись/TTL проходят), но реально
  никогда не подключится — без ошибки с любой из сторон. Формулировка в
  обоих местах переписана: не нажимать Copy/Share/QR повторно, пока
  текущий собеседник не подключится. Сам механизм (один тег на устройство)
  оставлен как есть — осознанное решение, каждый новый тег снижает
  маскировку остального трафика.

### Исправления (сессия: двойная трата анонимного токена, регистрационный флуд, и закрытие порта 9000 в обход Cloudflare)

Прямое продолжение предыдущей сессии (сетевые фиксы ниже) — цикл живого
тестирования продолжился и нашёл ещё один, отдельный источник потерь
сообщений, плюс всплыла реальная дыра в защите инфраструктуры сервера.

**Найдено и исправлено — двойная трата одноразового токена:**
- После видеозвонка отправитель продолжал считать, что сообщения уходят
  (`sendWs=true`, валидный токен), получатель их не видел. Серверный лог
  показал: тот же самый токен уже был использован и подтверждён
  доставленным ~12 минут раньше, во время звонка, а клиент выдал его
  повторно для нового сообщения — сервер закономерно ответил "офлайн",
  потому что маршрут для одноразового токена уже стёрт после первой
  доставки.
- Причина — механизм "вернуть токен в пул, если `sendWs()` вернул
  `false`" (добавлен ранее в этой же сессии, чтобы не терять токен при
  явном сбое отправки). Под сетевой нагрузкой (именно видеозвонок —
  камера, кодирование, WebRTC) `sendWs()` может локально считать
  отправку неудавшейся, а пакет всё равно доходит до сервера и
  получает подтверждение — токен в этот момент уже "восстановлен" для
  повторного использования, и получается двойная трата.
- **Исправлено**: механизм восстановления токена в пул отключён во всех
  трёх местах вызова (закомментирован, не удалён) — по прямому запросу
  пользователя. Сообщение по-прежнему уходит в очередь на повтор;
  меняется только судьба токена — он теперь просто теряется при
  неудачной отправке, вместо риска быть использованным дважды. Осознанный
  компромисс: изредка потерянный токен дешевле, чем сообщение, молча
  ушедшее в никуда с виду успешно.

**Добавлено — защита от Sybil-флуда регистраций:**
- `MAX_REGISTERED_USERS` (env, лимит на общее число зарегистрированных
  identity, выше — отказ новым) и `POW_DIFFICULTY_BITS` (env,
  proof-of-work на первую-в-жизни регистрацию — цена в реальном
  CPU-времени устройства, не в IP, который атакующий с кучей устройств
  меняет бесплатно). Оба выключены по умолчанию, включаются под
  конкретный сервер отдельно. Клиент прозрачно решает PoW и повторяет
  регистрацию, если сервер попросил.

**Найдено вживую при настройке VPS-защиты (Endlessh + CrowdSec, по
запросу пользователя) — порт 9000 был открыт всему интернету напрямую:**
- В процессе диагностики нестабильных переподключений в серверном логе
  всплыл питоновский traceback `websockets.exceptions.InvalidUpgrade`
  — верный признак, что кто-то стучится **не через nginx**. `server.py`
  слушает `0.0.0.0:9000`, а файрвол (`ufw`) на сервере оказался вообще
  **неактивен** — то есть вся защита "только Cloudflare может достучаться"
  (настроенная в nginx через `allow <cloudflare-подсети>; deny all;`)
  не работала ни секунды на практике: порт 9000 был доступен напрямую,
  в обход и Cloudflare, и nginx, и любых предполагаемых ограничений.
- **Исправлено**: `ufw` включён с полным аудитом уже существующих правил
  (SSH-порт 2222 добавлен в разрешённые до включения — иначе включение
  отрезало бы SSH), порт 9000 явно закрыт (`deny`). Заодно поставлены
  Endlessh (SSH-tarpit на 22-м порту — настоящий SSH переехал на 2222)
  и CrowdSec (общий крауд-сорсинг блоклист IP-атакующих между серверами)
  — обе меры не касаются кода мессенджера, чисто инфраструктурные.
- **Побочная находка**: `server.py` под systemd запускался без
  `PYTHONUNBUFFERED=1` — вывод `print()` буферизовался и появлялся в
  `journalctl` с задержкой (иногда сильной), из-за чего в паре прошлых
  раундов диагностики казалось, что сервер "не видит" подключения, хотя
  реально уже их обработал. Добавлено через `systemctl edit` —
  логи теперь появляются мгновенно, без искажения картины при будущей
  live-диагностике.

### Исправления (сессия: очередь токенов без TTL, честный индикатор "онлайн", застрявшие сообщения)

- **TTL 24ч на серверную очередь `token_pending`** — раньше не было
  вообще, запись висела в ОЗУ безгранично, пока получатель не
  переподключится. Часовой watchdog чистит записи старше суток.
- **Блокировка отправки после 10 сообщений подряд без единой квитанции
  `delivered`** — раньше пользователь мог сколько угодно писать в
  пустоту, не зная, что собеседник не получает вообще ничего. Теперь
  после 10 неподтверждённых подряд отправка в этот диалог
  приостанавливается с объясняющим диалогом, до первой пришедшей
  квитанции.
- **Индикатор "онлайн" в шапке чата был обманом** — показывал статус
  **своего** подключения к серверу (`isConnected`), а не собеседника.
  Архитектурно у анонимного роутинга нет и не может быть настоящего
  presence-протокола (сервер не должен знать, кто с кем переписывается)
  — индикатор переписан на честный сигнал "от контакта реально приходила
  активность за последние 2 минуты" на основе уже существующего
  `ContactHealthManager`.
- **"Удалить у всех" молча терялось офлайн** — `sendDeleteMessage()`
  просто выходила, если нет соединения, никакой очереди/ретрая, сигнал
  собеседнику никогда не уходил. Убрана лишняя проверка — путь
  доставки и так умеет ставить пакет в очередь сам.
- **Кнопка "Отправить снова"** для сообщений, зависших дольше 60с без
  подтверждения — по запросу пользователя.
- **Экран блокировки мог утечь пароль в поле ввода чата** — это оверлей
  поверх уже открытого экрана, а не полноценная замена; без явного
  `FocusRequester` фокус клавиатуры мог остаться на поле ввода сообщения
  под оверлеем. Пойман живьём: пользователь ввёл пароль вслепую сразу
  после обновления APK, тот осел текстом в черновике одного из чатов.
  Исправлено явным перехватом фокуса при появлении экрана блокировки.
- Подсказка сверки эмодзи (safety number) не говорила явно "по другому
  каналу связи" — сверка через тот же чат, который проверяется,
  бессмысленна против MITM именно на этом канале. Текст переписан,
  ru+en.
- Описание Dead Man's Switch не упоминало, что теперь также отзывает
  identity на сервере (добавлено раньше в этой же сессии) — исправлено.

### Исправления (сессия: гонка потоков в токенах, звонки жгли пул, дизайн-находки)

Началось с добавления фото/файлов в групповые чаты и мелких доработок
(перевод RootDetector, автопрокрутка BackupScreen), но основная часть
сессии — многочасовой цикл живого тестирования нестабильной связи
(эмулятор+телефон, реальные обрывы сети), где почти каждый найденный
баг маскировал следующий. Полные разборы каждой находки — в
`docs/ISSUE_backup_identity_hijack.md`, тут только сводка.

**Новые фичи:**
- **Фото и файлы в групповых чатах** — раньше кнопки были буквальными
  заглушками "(скоро)". Групповое шифрование (тот же AES-256-GCM
  групповой ключ), батчинг чанков по 15 на сообщение × по получателю,
  как у видеокружков — без батчинга это стоило бы `чанки × участники`
  одноразовых токенов.
- **Серверная ревокация identity** — кнопка "Меня скомпрометировали"
  раньше была чисто локальной операцией, сервер не знал об отзыве
  ключа, и укравший бэкап+пароль злоумышленник мог продолжать
  регистрироваться под старым fingerprint. Теперь клиент шлёт
  `revoke_identity` перед локальной чисткой; сервер хранит отозванные
  fingerprint'ы персистентно (переживает рестарт) и отказывает им в
  `register()`. То же самое подключено к Dead Man's Switch. Prekey
  bundle отозванной identity теперь помечается `revoked` — контакт,
  пытающийся завести с ней новую сессию, видит явное предупреждение.
  Тот же принцип применён и к Dead Man's Switch.
- **Резервные коды для TOTP-защищённого бэкапа** — раньше забытый
  TOTP-секрет означал тупик (бэкап нечем разблокировать). Переиспользованы
  те же 8 одноразовых кодов, что сервер и так выдаёт при включении
  TOTP — их хэши теперь дополнительно кладутся в сам экспортируемый
  бэкап.
- **Запрос на исключение из оптимизации батареи** — проактивный шаг
  онбординга (после обязательного TOTP, пропускаемый) плюс тумблер в
  Profile. Без этого разрешения оболочки некоторых OEM (MIUI и
  подобные) душат фоновое соединение без единой видимой ошибки.
- **Выбор видимости сервисного уведомления** — раньше значок сервиса
  был жёстко скрыт (`IMPORTANCE_MIN`, осознанный выбор скрытности).
  Теперь пользователь сам решает: скрытность или надёжность фона (у
  скрытых уведомлений ниже приоритет для батарейных менеджеров).

**Цепочка сетевых багов, весь вечер одного и того же паттерна
"телефон/эмулятор теряют сообщения при нестабильной связи":**
- **`pingInterval` был отключён (`0`) на Android** — Desktop-клиент уже
  имел `pingInterval(25с)`, только Android — нет. Без него мёртвое
  соединение обнаруживалось лишь при следующей реальной записи,
  отставая от реального разрыва на десятки секунд. Включён (`20с`).
- **`onLost()` в network callback рвал живое соединение при потере
  ЛЮБОЙ отдельной сети** — `onLost()` в Android срабатывает per-transport
  (WiFi отдельно от мобильных), не "интернета вообще"; при обычном
  переключении WiFi↔мобильные мог закрыть только что восстановленный
  сокет. Теперь проверяет `activeNetwork != null` перед закрытием.
- **Сервер стирал `known_tokens` (список "существует ли токен")
  при ЛЮБОМ дисконнекте**, а не только `token_to_ws` (маршрутизация) —
  любой, даже секундный обрыв делал все выданные контакту токены
  "неизвестными", сервер трактовал их как decoy-мусор и слал
  отправителю поддельный `ack`, хотя ничего не доставлялось.
- **PQ-ключ контакта был чисто in-memory, терялся на каждом рестарте
  сервиса** — в отличие от классического EC-ключа, у которого всегда
  был резерв на диске. Добавлена персистентность
  (`ChatStorage.saveContactPqPublicKey`/`getContactPqPublicKey`).
  Заодно: принимающая сторона первого контакта раньше вообще не
  получала PQ-ключ отправителя из `session_init` (его там физически
  нет — только PQ-шифротекст против получателя) — теперь запрашивает
  bundle проактивно, а не откладывая до первой попытки легаси-пути.
- **Токен терялся безвозвратно, если сокет уже был мёртв в момент
  отправки** — `consumeNextContactToken()` необратимо забирает
  одноразовый токен из локального пула **до** попытки записи в сокет;
  `sendWs()` была `Unit`-функцией, результат `webSocket?.send()`
  нигде не проверялся. Теперь возвращает `Boolean`, и на `false`
  токен восстанавливается (`AnonTokenManager.restoreContactToken`), а
  пакет уходит в уже существующую очередь вместо забвения.
- **`SessionKeyManager.initialize()` гонялся на каждом реконнекте** —
  защита-guard проверяла сессию под sentinel-fingerprint'ом
  (`"__init_check__"`), который нигде не создаётся — условие было
  всегда истинным. Заменено на настоящий одноразовый флаг.
- **`send_safe()`-успех на сервере считался финальной доставкой** — это
  означает лишь "запись в сокет не бросила исключение", не "получатель
  реально обработал сообщение". Соединение, умирающее ровно в этот
  момент, роняло сообщение без всякого следа. Добавлено настоящее
  end-to-end подтверждение: получатель шлёт новый `anon_delivery_ack`
  только после того, как реально обработал полезную нагрузку;
  сервер держит страховочную копию в `token_pending` до этого ACK.
  Существующий флаш `token_pending` при `subscribe_tokens` естественно
  стал ретраем — отдельный механизм не понадобился.
- **ACK слал ложное подтверждение при ошибке расшифровки** — сразу
  после включения предыдущего пункта поймали живьём: обработчики
  `"message"`/`session_init`/`"voice"` ловят decrypt-ошибку **сами**,
  делают восстановление (`session_reset`) и не пробрасывают исключение
  дальше — с точки зрения ACK-логики "всё прошло гладко". Добавлен
  `throw e` после восстановления в этих трёх местах (полный аудит
  остальных ~60-80 catch-блоков `handleMessage()` на тот же паттерн не
  проводился — отдельная задача).
- **Флаш при `subscribe_tokens` тоже не учитывал новую ACK-модель** —
  выкидывал запись из `token_pending` перед повторной попыткой
  доставки, результат `asyncio.create_task(send_safe(...))` нигде не
  проверялся. Если повторная попытка тоже не доходила — сообщение
  пропадало насовсем, второй раз тем же путём, что чинили в основном
  пути. `pop` → `get`.
- **Главный корень: `SessionKeyManager.deleteAllSessions()` вызывался
  безусловно на каждом успешном `connect()`** — не только при первом
  запуске, а на любом сетевом моргании. Стирает Double Ratchet-сессии
  со всеми контактами и в памяти, и **на диске**. Объясняет всю цепочку
  разом: вчерашний "OPK уже использован", сегодняшние "Пакет повреждён
  (ephemeral key)" + взаимные `session_reset`, постоянные
  "X3DH сессия инициирована" сразу после реконнектов. Убрано —
  `initialize()` и так уже вызывается один раз за жизнь процесса через
  отдельный, правильно гейтящийся вызов. **Сообщения, потерянные из-за
  этого бага, не восстановимы принципиально — это forward secrecy
  делает то, что должна, стёртый ratchet-ключ не воскресить.**

Desktop получил зеркальные фиксы там, где применимо (ACK-протокол).
Ни один из сегодняшних фиксов не задеплоен на боевой сервер и не
протестирован после деплоя — только живое тестирование, приведшее к
диагнозам, плюс `compileDebugKotlin`/`py_compile` на каждый шаг.

### Исправления (сессия: гонка потоков в токенах, звонки жгли пул, дизайн-находки)

Продолжение предыдущей сессии — тот же контакт всё ещё не поднимался стабильно после
фикса mailbox-тегов. Корень оказался глубже: гонка потоков при потреблении anon-токена.

- **`AnonTokenManager` делал read-modify-write в `SharedPreferences` без всякой
  синхронизации** — при параллельных отправках (текст + пачка ICE-сигналов + пинг почти
  одновременно) два потока могли прочитать один и тот же токен, оба его "успешно"
  потребить локально, а сервер принимал только первого — второй получал "токен офлайн",
  хотя локально всё выглядело нормально. Найдено по серверным логам (известные токены
  массово не распознавались при живом, не перезапускавшемся сервере — единственное
  объяснение: два клиента-потребителя одного токена). Добавлен единый `lock`,
  все read-modify-write функции обёрнуты в `synchronized`.
- **Видеозвонок выжигал общий пул токенов сильнее видеокружка** — ICE-кандидаты
  (10-30+ штук на один звонок) шли по одному `anon_message` на кандидата. Теперь
  батчатся: `queueIceCandidate()`/`flushIceCandidates()`, debounce 250мс, один
  `call_ice_batch` пакет вместо десятков одиночных.
- **Резерв токенов** — `consumeNextContactToken()` теперь не отдаёт последние
  `RESERVE_TOKENS` (3) обычному трафику, только сигналу пополнения
  (`sendAnonTokensTo`, `allowReserve=true`). Раньше пул мог обнулиться полностью,
  включая возможность попросить добавки.
- **Повторное пополнение токенов было одноразовым за весь процесс** — `tokensSentThisSession`
  был `Set`, не сбрасывался; после первой выдачи контакту новых токенов больше не
  давалось до перезапуска сервиса, даже если пул снова опустел (например, после звонка).
  Заменён на кулдаун 3 минуты на контакт.
- **`forgetContact()` при удалении контакта чистил не всё** — не трогал пул токенов от
  контакта, кулдаун пополнения, историю health-check и bootstrap-очереди. Из-за этого
  удалённый и заново добавленный контакт (тот же fingerprint) наследовал устаревшее
  состояние вместо чистого листа.
- **Удалённый контакт мог "воскреснуть"** — `handleIncomingDecryptedMessage()` (обычные
  сообщения, в отличие от mailbox-пути) не проверял, что контакт действительно взаимно
  добавлен, и "застрявшее" в очереди сообщение от уже удалённого контакта могло его
  вернуть в список с устаревшим именем. Добавлена та же проверка, что уже была у mailbox.
- **Тег в инвайт-коде теперь отделён от постоянного рабочего тега** — раньше один и тот
  же тег и публиковался в шаринг-коде, и использовался для повседневной связи. Теперь
  инвайт-код несёт одноразовый "invite-тег" (умирает после первого использования — тот же
  `removeMailboxTagIfEphemeral`, просто теперь применяется по назначению), а постоянный
  тег никогда не публикуется — передаётся только внутри уже зашифрованных сообщений после
  первого контакта. Кнопки "Копировать"/"Поделиться"/"Показать QR" в Profile теперь
  явно ротируют инвайт-тег при каждом нажатии.
- **`call_offer` без метки времени** — застрявший в очереди (из-за нехватки токенов)
  оффер звонка мог доставиться через много минут и всё равно вызвать звонок, как будто
  свежий. Добавлена метка времени + отбрасывание, если оффер старше `RINGING_TIMEOUT_MS`
  (тот же паттерн, что уже был у `call_request_audio/video`).
- **Набор эмодзи для сверки ключей** содержал визуально неотличимые пары (верблюды,
  киты, тигр/тигр-морда, рыбы) и плохо узнаваемые глифы (сверчок, скорпион, осьминог,
  орангутан) — подрывает смысл сверки (подмену ключа не заметить). Заменены на визуально
  самостоятельные символы.

Также в этой сессии: диалог экстренного удаления и диалог добавления сервера переделаны
(кнопки переставали влезать и переносились по буквам в узком `AlertDialog`); три кнопки
в диагностике безопасности слиты в одну; список серверов больше не зацикливался навечно
на недоступном onion-сервере при выключенном Tor; клик по серверу в списке теперь и
переключает, и закрепляет; добавлен новый экран **"Гид по защите"** (Profile → Безопасность)
с раскрывающимися карточками по всем функциям — инвайт-код (явно про одноразовость),
сверка ключей, TOTP, пароль под принуждением, экстренное удаление, автоблокировка, бэкап,
Tor, cover traffic, параноидальный режим, мёртвая рука, удаление по неактивности, кнопка
паники в уведомлении, уровни уничтожения, самовосстановление связи, смена identity.
ТОТП-состояние теперь сбрасывается при регистрации нового аккаунта (устройство могло
унаследовать флаг "TOTP уже настроен" от предыдущей identity через OEM-бэкап вроде MIUI,
который игнорирует `android:allowBackup="false"`).

**Известная, осознанно отложенная дыра** (см. `docs/ISSUE_backup_identity_hijack.md`,
Tier 5): "Смена identity" и срабатывание "мёртвой руки" — чисто локальные операции,
серверу не сообщается об отзыве ключа. При реальной краже ключа атакующий с копией
старого приватного ключа может продолжать проходить аутентификацию и получать
prekey bundle под старым fingerprint, пока контакты не перейдут на новый инвайт-код.
Предложено решение (серверная ревокация) — не реализовано.

### Исправления (сессия: канал не поднимался после re-add контакта + кружки зависали)

Цепочка из шести независимых багов, каждый маскировал следующий — воспроизводилась только
живым тестированием на паре телефон+эмулятор, задача решалась по одному живому логу за раз:

- **`InviteCodeManager.generateInviteCode()` генерировал новый случайный тег ящика на
  каждый вызов** — вместо переиспользования единого `AnonTokenManager.
  getOrCreateMyPersistentMailboxTag()`. Каждая регенерация инвайт-кода (TTL, рестарт
  сервиса) могла зашить тег, который никто больше не слушал.
- **Персистентный тег вычёркивался из списка опроса после первого же успешного
  депозита** — `handleMailboxResult()` вызывал `removeMyMailboxTag()` безусловно для
  любого тега, включая постоянный. После первого обмена устройство переставало слушать
  свой же тег навсегда. Исправлено через `removeMailboxTagIfEphemeral()`.
- **Персистентный тег мог разойтись с тегом в закэшированном (ещё валидном по TTL)
  инвайт-коде** — `ensureMyMailboxTagRegistered()` при переиспользовании старого кода не
  синхронизировал `PREF_MY_PERSISTENT_TAG`, и его первое чтение создавало не связанный ни
  с чем новый тег. Добавлен `AnonTokenManager.syncMyPersistentMailboxTag()`, вызывается
  при каждом резолве активного инвайт-кода (регистрация, Profile, сервис).
- **`send()` стирал сохранённый тег контакта, если публичный ключ ещё не успел
  закэшироваться** (чисто временная гонка) — тег терялся навсегда, восстановить нечем
  (bootstrap нужен тег, тег появляется только через bootstrap). Убрано деструктивное
  стирание.
- **Пакетный ответ на `get_prekey_bundles_batch` фильтровался по `pendingSessionMessages`**,
  куда попадают только отложенные текстовые сообщения — видеокружки/изображения/файлы
  туда не пишутся, их bundle-ответ отбрасывался как декой. Добавлен отдельный набор
  `pendingBundleRequests`, не привязанный к причине запроса.
- **`handleFetchedPrekeyBundle()` делал ранний `return`, если очередь текстовых сообщений
  пуста** — пропуская `flushPendingVideoCircles/Images/FileSends` в конце функции. Ключ
  кэшировался, но ничего из ждавшего его не отправлялось. X3DH-инициация теперь просто
  пропускается при пустой очереди вместо `return`, flush выполняется всегда.
- **Кружки съедали весь общий пул анон-токенов на контакта** — каждый чанк уходил
  отдельным `anon_message` (токены одноразовые по дизайну сервера), и 100+ чанков видео
  выжигали пул раньше текстовых сообщений. Чанки теперь батчатся по 15 в один
  `video_chunk_batch` пакет — один токен на батч вместо одного на чанк.

Также: **Tor сделан opt-in** — новый тумблер в Profile (выключен по умолчанию), запуск
Orbot больше не блокирует старт приложения на 10-15 секунд, если Tor не включён.

### Исправления

- **Анонимная маршрутизация теперь охватывает весь трафик** — typing, read, delivered,
  session_reset, реакции, редактирование, удаление сообщений, таймер исчезающих сообщений,
  чанки изображений/файлов/видео, групповые сообщения (group_create, group_message,
  group_reaction, group_member_removed, group_key_rotation, group_invite_accepted),
  WebRTC call_end — всё идёт через `anon_message → token` если токены есть.
  Прямая отправка по fingerprint остаётся только как fallback до первого обмена токенами.
  **[Устарело, см. правку ниже]** — этот fallback был позже убран: даже до первого обмена
  токенами используется анонимный mailbox-тег, а не fingerprint. Актуальное состояние (сверено
  с кодом): прямая fingerprint-адресация в 1:1-переписке — это не штатный fallback, а
  единственный аварийный edge-case (нет ни токена, ни mailbox-тега, ни ключа вообще), с явным
  warning-логом. Штатных исключений из анон-маршрутизации для 1:1 два и оба задокументированы
  в README: сигналинг **групповых** звонков (не 1:1) и утечка контакт-листа при anti-fingerprinting
  запросе prekey bundle.

- **session_init теперь тоже анонимен** — если токены уже получены через mailbox,
  X3DH handshake отправляется через `anon_message`, а не напрямую по fingerprint.
  Сервер не видит пару A → B ни разу после первого mailbox-обмена.

- **Задержка после первого контакта устранена** — после получения токенов от контакта
  `contactMailboxTag` очищается, и последующие сообщения идут через быстрый anon-маршрут
  вместо ожидания 30-секундного polling'а mailbox. Дополнительно: если токены уже есть,
  `send()` минует mailbox-путь даже если тег ещё не очищен.

- **Mailbox polling каждые 30 секунд** — ранее `pollMailbox` вызывался только при
  подключении; теперь периодически повторяется пока клиент онлайн, чтобы не пропускать
  новые первые контакты.

- **Устранён бесконечный цикл BAD_DECRYPT / session_reset** — оба клиента одновременно
  вызывали `requestPrekeyBundle` после `session_reset`, инициируя X3DH с обеих сторон
  и создавая несовпадающие сессии. Исправлено: `session_reset` больше не запрашивает
  bundle — инициатива остаётся за тем, кто отправил первое сообщение.

- **Контакт сохраняется при обмене только токенами** — ранее `addContact` не вызывался
  если первым приходил системный пакет `__beacon_tokens__`.

- **Без Orbot приложение подключается немедленно** — таймаут ожидания Orbot уменьшен
  с 90 до 12 секунд; добавлен обработчик `onTorError` чтобы `connect()` вызывался
  сразу при ошибке, не зависая в ожидании.

- **Токены отправляются только через анонимную почту** — убран прямой fingerprint-fallback
  в `sendAnonTokensTo`; если нет анон-токена для отправки — ждём mailbox-обмена.

## Предыдущие версии

### Анонимная маршрутизация (токены + mailbox + cover traffic)

- Токенная маршрутизация: клиент регистрирует пул из 50 одноразовых токенов;
  сообщения адресуются по токену, а не по fingerprint.
- Анонимный mailbox: первое сообщение кладётся в mailbox по тегу из инвайт-кода;
  получатель запрашивает всегда ровно 20 тегов (реальные + фейки).
- Constant-rate cover traffic (режимы: выкл / умеренный 5 сек / агрессивный 1 сек).
- Поддержка Tor hidden service через Orbot SOCKS.

### WebRTC видеозвонки

- Библиотека `stream-webrtc-android:1.3.10`, Camera1Enumerator, VP8+H264 Baseline.
- Фикс краша: `onTrack` и `handleCallEnd` диспатчатся на main thread.
- TURN через TCP порт 4433 (UDP заблокирован провайдером).

### Двойное шифрование at-rest (SMK)

- Storage Master Key (256-bit AES), хранится через PBKDF2 и AndroidKeyStore.
- Защищает EC private key, групповые ключи, блобы сообщений.
- Прозрачная миграция legacy данных.
