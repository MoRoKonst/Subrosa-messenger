# Сценарии поведения

## Зачем этот файл

Держать в голове всё поведение мессенджера, чтобы находить дыры в защите,
не получится — слишком много пользовательских действий, слишком много
путей в коде, слишком легко упустить, как взаимодействуют две фичи,
написанные с разницей в несколько месяцев. Этот файл — альтернатива:
**один сценарий на пользовательское действие**, описанный на уровне
*кода* (функции/типы сообщений/переходы состояний), а не на уровне UI, и
максимально коротко. Смысл не в документации ради документации — а в том,
чтобы смотреть на сценарий и пытаться его сломать: читать шаги и
спрашивать "а что если шаг 3 не сработает", "а что если шаг 5 контролирует
атакующий", "что видит сервер на каждом шаге" — и проверять, выдерживает
ли сценарий такую проверку.

**Формат сценария — дерево развилок, а не линейный "счастливый путь".**

Линейный список "шаг 1, шаг 2, шаг 3" прячет как раз то, ради чего этот
файл существует: развилку в коде, которая не является счастливым путём.
На каждом месте, где код разветвляется (`if`/`else`, успех/неудача, поле
версии, которое может отличаться, тип сообщения, который может
присутствовать или нет) — выписываются **все** ветки, а не только та,
которая была в голове в момент написания. Каждая ветка должна куда-то
вести:

- → ведёт в другой описанный сценарий (указать, в какой)
- → безопасно завершается, и дерево прямо говорит, как именно (показана
  ошибка, тихо отброшено, будет повтор и т.д.)
- → **`❓ НЕ ПРОДУМАНО`** — ветка существует в коде, но никто не решил,
  что должно происходить, либо хуже — то, что происходит сейчас,
  неочевидно правильно. Это самая важная пометка — ради неё всё и
  затевалось. Сценарий без единого `❓` означает либо что путь
  действительно продуман до конца, либо что развилки искали не
  достаточно тщательно.

Нотация дерева:
```
Шаг N: <от чего зависит развилка>
  ├─ <условие A> → <что происходит> → следующий шаг / сценарий / ❓
  ├─ <условие B> → ...
  └─ <условие C> → ...
```

Обновлять файл при каждом изменении соответствующего кода — устаревший
сценарий хуже, чем отсутствие сценария, потому что он внушает доверие к
тому, что уже не соответствует реальности.

## Сценарий: первый контакт (обмен инвайт-кодами)

**Триггер**: Пользователь A делится своим инвайт-кодом (вне приложения —
скриншот, другой мессенджер, лично) с пользователем B, который вставляет
его в "Добавить контакт".

**Шаг 1 — A генерирует код** (`InviteCodeManager.generateInviteCode()`,
[InviteCodeManager.kt:26](app/src/main/java/com/example/test/InviteCodeManager.kt:26)):
версия формата + таймстамп + nonce + свежий случайный 16-байтный
mailbox-тег + fingerprint A + публичный ключ A + отображаемое имя, всё
подписано ECDSA, `bc:` + Base64. Развилки нет — всегда пишется текущий
формат (`FORMAT_VERSION = 0x03`, mailbox-тег включён). Тег сохраняется и
переиспользуется до истечения 7-дневного TTL самого кода, а не
перегенерируется при каждом заходе на экран профиля.

**Шаг 2 — B вставляет код**
(`InviteCodeManager.parseInviteCode()` + `verifyInviteCode()`,
[ChatsScreen.kt:403](app/src/main/java/com/example/test/ChatsScreen.kt:403)):
  ├─ **Подпись неверна или payload повреждён** → `parseInviteCode`
  │  возвращает null или `verifyInviteCode` возвращает false → тост
  │  "неверный или истёкший инвайт-код", ничего не добавляется.
  │  Обработано.
  ├─ **`сейчас - timestamp > 7 дней`** → тот же отказ, тот же тост.
  │  Обработано.
  └─ **Версия = `FORMAT_VERSION` (0x03), mailbox-тег присутствует** →
     продолжение в шаге 3 (анонимный bootstrap через mailbox — теперь
     единственный путь).

~~Раньше здесь была вторая ветка (legacy-формат `0x02`, без mailbox-тега,
с прямым видимым серверу запросом `get_key`)~~ — **вырезано**. Код,
парсящий и принимающий `0x02`, удалён на обеих платформах
(`InviteCodeManager.parseInviteCode()` теперь безусловно отвергает всё,
что не `FORMAT_VERSION`), вместе с веткой `request_key` в
`ChatsScreen.kt`/`MessengerService.kt` (Android) и безусловным
`WebSocketClient.requestPublicKey()` в `acceptInvite()` (Desktop — там
было даже хуже: этот прямой запрос уходил при **любом** добавлении
контакта, не только при отсутствии тега). Старый код, распознавший себя
на legacy-код, теперь просто получает "неверный или истёкший инвайт-код"
и должен попросить у отправителя код заново.

**Шаг 3 — попытка bootstrap** (`sendAnonTokensTo`,
[MessengerService.kt:3283](app/src/main/java/com/example/test/MessengerService.kt:3283)):
  ├─ **У B уже есть живой анон-токен для A** → отправить токены через
  │  `anon_message` напрямую. Никогда не верно при настоящем первом
  │  контакте (ещё неоткуда взять токен) — упомянуто здесь, потому что та
  │  же функция переиспользуется позже для пополнения токенов, где эта
  │  ветка — обычный случай.
  └─ **Токена нет, но у B есть mailbox-тег A** (единственный путь теперь,
     раз mailbox-тег всегда присутствует) → `mailbox_put` кладёт токены B
     в mailbox A. Сервер хранит депозит, но — по замыслу — не может
     отличить, что это токены, а не реальное сообщение, и не может
     привязать депозит к отправителю. → Шаг 4.

**Шаг 4 — на стороне A, независимо** (поллинг `mailbox_fetch`, с decoy-
тегами через `buildFetchTagList`, чтобы сервер не мог понять, какой из
запрошенных тегов настоящий):
  ├─ **A ЕЩЁ НЕ погасил инвайт-код B** → `getContactMailboxTag(from) ==
  │  null` → депозит отбрасывается сразу, контакт не создаётся, A ничего
  │  не видит. Это намеренный барьер взаимного добавления
  │  (`SECURITY.md`, пункт 21) — одного лишь владения кодом A со стороны
  │  B недостаточно, чтобы достучаться до A.
  ├─ **A ТОЖЕ погасил код B** (обычный случай "мы обменялись кодами") →
  │  контакт создаётся у A, токены импортируются, канал помечается
  │  готовым. Обе стороны дальше маршрутизируют через `sendAnonOrDirect()`
  │  с этими токенами вместо прямой адресации по fingerprint'у. → ведёт в
  │  сценарий *"Первое сообщение"* для собственно переписки.
  └─ **Сервер теряет/роняет депозит** → неотличимо от "A ещё не погасил
     код" с обеих сторон; депозиты в mailbox не подтверждаются так, как
     обычные сообщения, так что сигнала об ошибке доставки нет вообще.
     ~~Приемлемо ли бесконечное молчание?~~ — **сделано**
     (`bootstrapChannelFor()`/`checkChannelStuck()`,
     [MessengerService.kt:3529](app/src/main/java/com/example/test/MessengerService.kt:3529)):
     повторные попытки каждые 30с (первые 3 раза), затем каждые 90с —
     без верхней границы, транзиентная проблема может само-разрешиться
     позже. Спустя `CHANNEL_STUCK_THRESHOLD_MS` (5 минут) без успеха —
     один раз (`channelStuckNotified`, не повторяется при каждой
     следующей попытке): видимое пользователю уведомление
     "не удаётся связаться" + `bootstrap_diagnostic` пакет на сервер —
     **без** идентификатора собеседника в пакете (это утекло бы именно
     ту метаданность, которую вся mailbox-схема должна скрывать), просто
     "у этого аккаунта завис первый контакт". Не автоматический репорт
     разработчику напрямую — просто помеченная строка в логе сервера,
     которую оператор находит через `ForEXP/admin_logs.py` при
     расследовании.


**Связанный, более широкий пробел (та же природа, но не только для
первого контакта) — сделано.** `sendAnonTokensTo()` сама по себе всё ещё
чисто реактивна, но поверх неё теперь есть отдельный фоновый механизм —
"Забота о собеседнике" (`ContactHealthManager.kt` +
`checkContactSilence()`,
[MessengerService.kt:3803](app/src/main/java/com/example/test/MessengerService.kt:3803),
вызывается при каждом `isConnected`-событии): контакт считается
"молчащим" (`isSilent()`), когда **и** входящих сообщений, **и**
`delivered`-подтверждений на свои исходящие не было дольше
`SILENCE_THRESHOLD_MS` (15 минут) — оба направления, а не одно (просто
читающий, но пока не ответивший собеседник — не "молчание").
  ├─ **Впервые обнаружено молчание** (`PingState.NONE`) → шлётся
     `contact_ping` через обычный `sendAnonOrDirect` (если токен есть —
     напрямую; если нет — тот же существующий mailbox-каскад бутстрапа
     подключается сам). Собеседник отвечает `contact_pong` → канал
     подтверждён живым.
  └─ **Пинг отправлен, `MAILBOX_RETRY_WAIT_MS` (5 минут) прошло без
     `contact_pong`** (`PingState.PINGED`) → один запасной прямой
     `mailbox_put` свежей партии токенов в mailbox-тег контакта — на
     случай "это я пересох, а не он" не срабатывает,
     а срабатывает случай "мой пинг до него тоже не дошёл". После этого
     (`PingState.MAILBOX_TRIED`) — намеренно **больше ничего**: не
     бесконечный цикл, контакт остаётся в покое до возобновления
     настоящего трафика в любую сторону.

**Известные пробелы**:
- ~~Путь legacy-формата (`0x02`)~~ — **закрыто**: код, который парсил и
  принимал `0x02`, и прямой fallback-запрос `get_key`/`requestPublicKey`
  вырезаны на обеих платформах (см. выше). Дырка, найденная при
  построении этого дерева, устранена в тот же день.
- Bootstrap через mailbox в шагах 3/4 — это система анонимной
  маршрутизации/mailbox из `SECURITY.md`, см. там же про оговорку насчёт
  корреляции decoy-тегов при батчевом fetch (`buildFetchTagList`).
- ~~Нет видимого пользователю сигнала, отличающего "всё ещё ждём другую
  сторону" от "что-то тихо сломалось"~~ — **закрыто**: 5-минутный
  уведомление + `bootstrap_diagnostic`-тикет (см. шаг 4 выше).
- ~~**Только Android**: `contact_ping`/`contact_pong` и весь
  `ContactHealthManager` реализованы только на Android~~ — **закрыто**:
  портировано на Desktop (`ContactHealthManager.kt`, тот же API без
  `Context`, поверх `DesktopStorage`), обработчики `contact_ping`/
  `contact_pong`/`delivered` и 60-секундный цикл `checkContactSilence()`
  добавлены в `WebSocketClient.kt`. Логика идентична Android
  build-for-build (тот же `SILENCE_THRESHOLD_MS`/`MAILBOX_RETRY_WAIT_MS`,
  та же двухступенчатая эскалация ping → mailbox-депозит →
  успокоиться). Compiles clean, не проверено вживую на реальном
  сеансе связи Android↔Desktop.

## Сценарий: первое сообщение (X3DH handshake)

**Триггер**: пользователь A печатает и отправляет первое сообщение
контакту, с которым ещё нет сессии Double Ratchet
(`SessionKeyManager.hasSession(to) == false`).

**Шаг 1 — запрос ключевого бандла получателя**:
  ├─ **У отправителя есть другие контакты для прикрытия** →
     батчевый `get_prekey_bundles_batch` (настоящая цель подмешана к
     decoy-целям из реальных контактов — см. `SECURITY.md`, пункт 11, о
     том, почему decoy обязаны быть реальными контактами, а не
     одноразовыми аккаунтами).
  └─ **Контактов для прикрытия нет** → обычный `get_prekey_bundle`,
     сервер видит ровно, кто про кого спрашивает. Худший случай — ровно
     тот, где decoy из реальных контактов не спасает: у пользователя
     объективно мало реальных собеседников (два журналиста, пишущих
     только друг другу).

**Обсуждено** (см. `ISSUE_backup_identity_hijack.md`, раздел "decoy-
контакты с реальным трафиком"): предложение — не фейковые контакты без
активности (они статистически вычисляются со временем, никогда не
участвуют в настоящей переписке), а **опциональный модуль** для
маленьких self-hosted инсталляций: боты, реально обменивающиеся
трафиком друг с другом (можно на отдельной VPS, в другой юрисдикции),
служат decoy. Реалистичность имитации — вопрос качества реализации, не
архитектурная проблема. Важное уточнение по защите: боты всё равно
регистрируются в базе основного сервера, так что от **оператора этого
сервера** структурно не скрыты (для self-hosted-инсталляции, где
пользователь сам себе оператор, это не критично); отдельная VPS/
юрисдикция защищает не от этого, а от возможности юридически доказать
и привлечь к ответственности организатора схемы — другой уровень защиты.
Дизайн, реализация не начата.

**Шаг 2 — сервер отвечает бандлом**: identity-ключ получателя, signed
prekey (SPK) + подпись ECDSA, до 5 одноразовых prekey'ев (OPK), публичный
ключ ML-KEM + подпись, и (если у получателя зарегистрирован анон-токен)
`bootstrap_token`, прикреплённый сервером в момент выдачи.
  ├─ **`bootstrap_token` присутствует** → дальнейший `session_init`
     (шаг 6) пойдёт анонимно.
  └─ **`bootstrap_token` отсутствует** (получатель офлайн / токенов нет
     / злонамеренный сервер всегда его вырезает) → ~~тихий откат на прямую
     адресацию~~ **решено** (см. шаг 6 ниже — то же решение закрывает
     обе развилки сразу).

**Шаг 3 — проверка подписей** (`SessionKeyManager.initiateSession()`):
  ├─ **Подпись SPK или подпись PQ-ключа неверна** → `SecurityException`,
     отправка прерывается. Это защита от подмены сервером ключевого
     материала (отказать в доставке сервер всё ещё может, но подделать
     сессию — нет).
  └─ **Обе подписи верны** → продолжение в шаге 4.

**Шаг 4 — классический X3DH + PQ**: четыре ECDH-операции (identity↔SPK,
ephemeral↔identity, ephemeral↔SPK, ephemeral↔OPK если он был доступен)
объединяются через HKDF вместе с shared secret от инкапсуляции ML-KEM —
строка домен-разделения `"BeaconX3DHpq"`, `SessionKeyManager.kt`. Именно
в этой точке сессия становится устойчивой к квантовому компьютеру, даже
если классическую часть уже сохранили сегодня для расшифровки в будущем.

**Шаг 5 — производный root-ключ сразу используется как первый шаг Double
Ratchet** (не в сыром виде) — `sendChainKey`/`recvChainKey` выведены,
сессия сохранена (`saveSession`, обёрнута в SMK если разблокирован — см.
раздел SMK в `SECURITY.md`).

**Шаг 6 — доставка заголовка `session_init`** (ephemeral-ключ, spk_id,
opk_id если использован, session_id, DH ratchet pub, PQ-шифротекст):
  ├─ **`bootstrap_token` был получен в шаге 2** → доставка через
     `anon_message`, анонимно.
  └─ **`bootstrap_token` отсутствовал** → ~~прямая адресация, молча~~ —
     **согласовано решение** (тот же принцип "отрезать прямой fallback",
     уже применённый к `sendAnonOrDirect` в целом): вместо тихого отката
     на прямую адресацию — доставка через `mailbox_put` в тег получателя
     (он у отправителя уже есть с момента "Первого контакта"). Тот же
     запасной канал, которым уже пользуется bootstrap токенов, просто
     применён ещё к одному месту, где раньше был тихий прямой fallback.
     Реализация не начата, зафиксировано как решение (см.
     `ISSUE_backup_identity_hijack.md`).

**Шаг 7 — получатель обрабатывает `session_init`** (`receiveSession()`):
  ├─ **Ссылка на OPK есть, но этот OPK сервер уже отдал другому
  │  отправителю** (пул OPK исчерпан на сервере, `SECURITY.md`, пункт 4)
  │  → обе сессии выводят разный DH4 из формально одного и того же OPK,
  │  корректно завершается только одна; вторая проявляется как ошибка
  │  расшифровки позже, а не синхронный сигнал о проблеме в момент
  │  handshake. `❓` — узнать о поломке сразу нечем.
  └─ **Всё совпало** → зеркальная математика (приватный SPK/OPK
     получателя × публичные ephemeral/identity ключи отправителя),
     независимо выводится тот же root-ключ, свои send/recv chain-ключи
     (асимметрично — "send"-цепочка Bob'а — это "recv"-цепочка Alice).
     Если использовался OPK — `consumeOpk()` убирает его из пула, один
     OPK годится ровно на один handshake.

**Известные пробелы**: `SECURITY.md`, пункт 11, целиком — утечка
примерного размера списка контактов через паддинг батча (шаг 1 —
обсуждаемое решение: опциональный модуль decoy-ботов с реальным
трафиком, дизайн см. `ISSUE_backup_identity_hijack.md`); тихий откат на
прямую адресацию из шагов 2/6 — решение согласовано (mailbox вместо
прямой адресации), реализация не начата.

## Сценарий: голосовой/видеозвонок

**Триггер**: пользователь A нажимает "позвонить" существующему контакту.

**Шаг 1 — фаза вызова, только для 1:1** (групповые звонки — отдельная
ветка, см. шаг 5): `call_request_audio`/`call_request_video` через
`sendAnonOrDirect()`:
  ├─ **Анон-токен для получателя есть** → доставка анонимно.
  └─ **Токена нет** → пакет встаёт в очередь, повтор при появлении
     токена (прямой адресации как запасного варианта нет — см. решение
     "убрать прямой fallback", `SECURITY.md`/`ISSUE_backup_identity_hijack.md`).
  Таймаут ожидания ответа — 45 секунд.

**Шаг 2 — получатель B переподключается в пределах таймаута** (даже
после короткого сетевого сбоя): очередь `token_pending` на сервере сама
досылает накопленное при переподписке на токены — именно это делает фазу
вызова устойчивой к кратковременному обрыву связи, в отличие от сырого
SDP/ICE (следующий шаг).
  ├─ **B успел переподключиться и принял звонок** → `call_response(accepted=true)`,
     тем же анонимным путём обратно к A. → Шаг 4.
  └─ **B реально офлайн (не переподключился за 45с)** → чистое "нет
     ответа", как при обычном телефонном звонке. Обработано.

**Шаг 3** *(включён в шаг 2 выше — оставлен для нумерации)*.

**Шаг 4 — только после подтверждённого `call_response`**: настоящий обмен
SDP/ICE — `call_offer`/`call_answer`/`call_ice`/`call_end` — идёт через
**тот же** `sendAnonOrDirect()`, без отдельной прямой ветки специально
для звонков. Это уже один раз откатывали и чинили заново
(`SECURITY.md`, пункт 18) после того, как живое тестирование показало:
даже уже подтверждённое соединение может на долю секунды моргнуть
посреди обмена SDP/ICE и тихо поставить в очередь один ICE-кандидат.
Фикс, который сделал повторное включение безопасным: `call_end` получил
P2P DataChannel "bye" как настоящий основной путь, а маршрутизация
`call_end` через сервер стала лишь запасным вариантом на случай, если
этот канал ещё не открыт.

**Шаг 5 — групповые звонки принципиально другие**:
`call_group_invite/join/answer/ice/leave` всегда отправляются напрямую,
никогда через `sendAnonOrDirect` — намеренно исключены из схемы анонимной
маршрутизации целиком (`SECURITY.md`, пункт 18, явно это оговаривает).

**Известные пробелы**: сервер видит метаданные звонка (кто кому звонит,
когда, продолжительность по таймстампам request/end) в любой момент,
когда анонимная маршрутизация деградирует до прямой — тот же класс
проблемы, что и откат `session_init` выше, отдельно для звонков не
смягчён.

## Сценарий: экспорт и восстановление бэкапа

Это *исходный* сценарий, ради которого вообще заведён файл
`ISSUE_backup_identity_hijack.md` — открытая, непочиненная уязвимость
целиком живёт в этом потоке.

**Триггер (экспорт)**: пользователь заходит в Profile → Backup (экран
доступен **только уже залогиненному** устройству, не часть онбординга)
и нажимает "Экспорт".

**Шаг 1 — ввод пароля** (`BackupScreen.kt`):
  ├─ **Пароль пустой** → ошибка, отказ. Обработано.
  ├─ **Пароль ≠ подтверждение** → ошибка, отказ. Обработано.
  ├─ **Пароль короче 8 символов** → ошибка, отказ. Обработано.
  └─ **Всё ок** → `BackupManager.exportBackup()`.

**Шаг 2 — сборка содержимого бэкапа** (`BackupManager.kt:24`): версия 6,
username, display_name, **приватный EC-identity-ключ** (разворачивается
из SMK через `StorageKeyManager.unwrapBytes()`), список серверов, все
контакты (имя + публичный ключ), **все сообщения в виде обычного
текста** (`ChatStorage.loadMessages()` — то есть на момент экспорта
сообщения уже расшифрованы), все группы **включая сырой байтовый
groupKey**, все групповые сообщения.
  ├─ **SMK разблокирован** → приватный ключ успешно разворачивается,
     сборка продолжается нормально.
  └─ **SMK заблокирован** → `unwrapBytes()` бросает исключение
     ("StorageKeyManager is locked"), пойманное общим `catch (e:
     Exception)` в `launchExport()` в UI — пользователь видит **сырое
     сообщение исключения**, а не понятную подсказку вида "сначала
     разблокируйте приложение". `❓` — UX-пробел, не крит по
     безопасности (экспорт просто не пройдёт), но плохой опыт
     пользователя.

**Важно, чего НЕТ в бэкапе**: состояние Double Ratchet-сессий
(`SessionKeyManager`), анон-токены, mailbox-теги. Бэкап переносит
identity и историю сообщений, но не переносит *живые* сессии связи —
см. последствия в шаге про импорт ниже.

**Шаг 3 — упаковка**: JSON → gzip → AES-256-GCM с ключом, выведенным
через **Argon2id** (64 МБ памяти, 3 итерации, параллелизм 1 —
Argon2id устойчивее к перебору на GPU/ASIC, чем PBKDF2, использованный
для пароля приложения) с 32-байтным солью и 12-байтным IV. Итог —
`salt || iv || ciphertext`, Base64.

**Шаг 4 — куда уходит файл**, два независимых пути на выбор пользователя:
  ├─ **"Поделиться"** → файл пишется во временный `cacheDir`, отдаётся
  │  через `FileProvider` в системный share-sheet (`ACTION_SEND`) —
  │  пользователь сам выбирает целевое приложение (облако, почта, другой
  │  мессенджер). Временный файл удаляется сразу после запуска интента,
  │  но URI-грант на чтение живёт столько, сколько выбранное приложение
  │  его удерживает — вне контроля этого приложения. `❓` — зашифрованный
  │  бэкап-блоб транзитом через произвольное стороннее приложение,
  │  которое пользователь выбрал сам; это осознанный компромисс
  │  UX/приватности, но нигде не проговорено пользователю явно в моменте.
  └─ **"В файлы"** → системный `ACTION_CREATE_DOCUMENT` — сохранение
     напрямую в выбранную пользователем папку/облачно-синхронизируемую
     директорию, без промежуточного приложения-получателя.

**Триггер (импорт)**: тот же экран, кнопка "Импорт" → `OpenDocument`
пикер (только если поле пароля уже заполнено).

**Шаг 5 — расшифровка** (`BackupManager.importBackup()`):
  ├─ **Неверный пароль / повреждённый файл** → `decryptBackup()`
     бросает исключение при `cipher.doFinal()` (GCM tag mismatch) →
     `Result.failure`, показано пользователю. Обработано.
  └─ **Пароль верный** → расшифровано, gunzip (с fallback на "не сжато"
     для очень старых бэкапов без gzip-шага), парсинг JSON.

**Шаг 6 — ключевой момент: замена identity** (`version >= 6` и в бэкапе
есть `ec_private_key`/`ec_public_key`):
  ├─ **SMK этого (принимающего) устройства заблокирован** →
     `Result.failure("SMK не разблокирован...")`, явный отказ,
     ничего не тронуто. Обработано, причём тут (в отличие от экспорта)
     сообщение уже понятное.
  └─ **SMK разблокирован** → приватный ключ из бэкапа оборачивается в
     SMK **этого** устройства и сохраняется как identity-ключ этого
     устройства, fingerprint пересчитывается из публичного ключа и
     **`UserStorage.setUserId()` перезаписывает id устройства на
     fingerprint из бэкапа**. Это и есть буквальный "угон" — устройство,
     которое до этого момента было условным Bob, теперь технически
     Alice (или что бы ни было в бэкапе), и любой, у кого есть файл
     бэкапа и пароль, может провернуть это на своём устройстве.
     Никакой дополнительной проверки/подтверждения владельца, кроме
     пароля к самому файлу, здесь нет.

  **Что происходит со СТАРОЙ identity этого устройства при перезаписи —
  решено, сделано.** Раньше это было `❓` НЕ ПРОДУМАНО (смешение старой и
  новой identity в одном хранилище). Теперь `importBackup()` вызывает
  `wipeCurrentIdentityData()`
  ([BackupManager.kt:28](app/src/main/java/com/example/test/BackupManager.kt:28))
  **до** восстановления содержимого бэкапа — `UserStorage.logout()`
  (username/user_id/password_hash + сами чаты/очередь сообщений),
  `GroupManager.clearAll()`, `AnonTokenManager.clearAll()`,
  `SessionKeyManager.deleteAllSessions()`. Решение пользователя: это
  строго "я потерял телефон, верните мне мои данные", а не машина
  времени для истории чатов — откат в старую переписку устройства и не
  нужен был. Полный автовайп с явным предупреждением о потере текущих
  данных перед импортом — заложено в `BackupScreen.kt`
  (`showImportWipeWarning`).

**Шаг 7 — восстановление contacts/messages/groups**: контакты (имя +
публичный ключ), сообщения (только текст/`isOwn`/timestamp — **без
исходных ID сообщений**, `❓` при повторном импорте того же бэкапа,
скорее всего, задублирует всю историю, а не будет идемпотентным), группы
(`version >= 4`, включая сырой `groupKey`), групповые сообщения
(`version >= 4`).

**Шаг 8 — можно ли сразу писать контактам после восстановления? Нет.**
`❓` **реальный функциональный пробел, не только дизайн-вопрос**: бэкап
переносит identity-ключ, но **не** переносит состояние Double Ratchet
(шаг 2 выше). У контактов с той стороны сессия по-прежнему привязана к
их send/recv chain state, синхронизированному со *старым* устройством,
которого больше нет. Восстановленное устройство criptографически имеет
ту же identity, но не имеет продолжения ratchet-цепочки — то есть
входящие сообщения от контактов, всё ещё считающих сессию активной, не
расшифруются на новом устройстве, пока не пройдёт свежий X3DH-handshake
(a значит — пока разработчик/пользователь не пройдёт через
`session_reset` или контакт не удалит-добавит заново). Это не
дизайн-вопрос "как лучше" — это, похоже, реальный сломанный UX сразу
после восстановления, не проверено вживую.

**Известные пробелы (сводка)**:
- **Сама исходная проблема файла**: identity = обладание приватным
  ключом + пароль к бэкапу, второго фактора нет — кто угодно с файлом и
  паролем получает identity целиком, никакого способа отличить
  легитимного владельца.
- Отсутствие переноса сессий/токенов/mailbox-тегов (шаг 8) — вероятный
  сломанный UX, не проверено вживую.
- ~~Неясное поведение при смешении старой/новой identity на одном
  устройстве~~ — **закрыто** (шаг 6, подпункт): полный автовайп текущей
  identity перед импортом.
- Отсутствие идемпотентности повторного импорта сообщений (шаг 7) — при
  повторном импорте того же бэкапа сообщения задублируются (не проверено
  вживую); больше не смешивается с ДРУГОЙ identity, но дубли сообщений
  внутри одного и того же импорта остаются открытым вопросом.
- UX при заблокированном SMK на экспорте — сырой текст исключения
  вместо понятной подсказки (шаг 2).

## Сценарий: создание группы, добавление/удаление участника

**Триггер**: пользователь A создаёт группу с участниками [B, C, D] в
`CreateGroupScreen.kt`.

**Шаг 1 — создание, на стороне A**: `Group(members = [A,B,C,D], admins =
[A], groupKey = <случайные 256 бит>)` сохраняется **локально у A с
полным списком участников** (`CreateGroupScreen.kt:224-234`), затем
`MessengerService.createGroup()` в цикле рассылает **каждому** участнику
по отдельности `group_create` через `sendAnonOrDirect`.

**Шаг 2 — что реально лежит в пакете `group_create`**
(`MessengerService.kt:3768`): `group_id`, `group_name`, `group_avatar`,
`encrypted_group_key` (ключ группы, зашифрованный лично для этого
получателя), подпись. **Поля `members`/`admins` в пакете нет вообще.**

**Шаг 3 — что происходит на стороне получателя** (`group_create`
handler, `MessengerService.kt:1775`):
  ├─ **Группа с таким `group_id` уже есть локально** → игнорируется
     ("уже состоим в группе"). Обработано, защита от повторной
     обработки при ретрае.
  └─ **Группы нет** → создаётся `Group(members = listOf(from, username),
     admins = listOf(from), ...)` — **только отправитель приглашения и
     сам получатель**, не полный список.

**Это и есть находка** — не гипотетическая, проверено построчным чтением
кода: **у группы из N участников (N>2) правильный полный список
участников есть только у создателя.** Каждый приглашённый видит группу
как разговор из двух человек — "я и тот, кто меня позвал", и ничего не
знает про остальных.

**Как это ломает реальную переписку** — прослеживается через
`sendGroupMessage()`/`sendGroupReaction()`/`rotateGroupKey()`, которые
все рассылают **по локальному `group.members` отправителя**
(`members.filter { it != username }.forEach { sendAnonOrDirect(...) }`):
  ├─ **B (не создатель) пишет в группу** → рассылает по своему
     локальному списку `[A, B]` → сообщение уходит **только A**, C и D
     никогда его не получат, хотя формально состоят в группе.
  └─ **A (создатель) пишет в группу** → у A список полный `[A,B,C,D]` →
     доходит всем. Асимметрия: только сообщения от создателя долетают
     до всех, сообщения от кого угодно ещё — только до создателя.

**Шаг 4 — B принимает приглашение**: `group_invite_accepted` уходит
**только тому, кто прислал приглашение** (`from` в исходном
`group_create`, то есть создателю A) — не всем остальным участникам.
Создатель A получает это, вызывает `GroupManager.addMember()` **у
себя** (и так уже знал про B, это no-op) — но C и D по-прежнему не
узнают о B, и B по-прежнему не узнаёт о C и D. `❓` — нет вообще
механизма, который довёл бы полный ростер до всех сторон.

**Шаг 5 — админ добавляет нового участника E** (`GroupInfoScreen.kt:455`):
  ├─ Локально у админа: `GroupManager.addMember()` — админский список
     пополняется.
  └─ Сетевой уровень: `addGroupMember()` шлёт `group_create` **только
     E** — точно так же без поля `members`. Существующие B, C, D **не
     уведомляются о добавлении E вообще**, никаким пакетом. Их локальные
     списки участников остаются как были, теперь ещё и без E.

**Шаг 6 — админ удаляет участника** (`GroupInfoScreen.kt:513`,
`notifyMemberRemoved`) — **этот путь устроен иначе и правильно**:
`members.filter { it != username && it != removedMemberId}.forEach {
sendAnonOrDirect(memberId, ...) }` — рассылка идёт **всем оставшимся
участникам** по списку админа, не только удаляемому. Это уже
починенный путь (см. `SECURITY.md`, пункт про ротацию группового ключа
— чинили именно эту ветку, чтобы удалённый участник не получил новый
ключ). Здесь всё симметрично работает — потому что у рассылающего
(админа) на этот момент список участников ещё полный и правильный.

**Итог асимметрии**: путь **удаления** уже правильно рассылается всем
(починен ранее), а путь **добавления** — нет, и никогда не был. Именно
поэтому баг с добавлением не поймали тогда — чинили ротацию ключа при
удалении, а не рассылку ростера при добавлении, это разные ветки кода.

**Предложенное решение** (не реализовано, план):
1. Включить полный `members`/`admins` в сам пакет `group_create` —
   подписанный вместе с остальным содержимым, чтобы получатель мог
   сразу инициализировать правильный локальный ростер, а не строить его
   из `[from, username]`.
2. При добавлении нового участника — не только слать ему `group_create`,
   но и разослать **всем существующим участникам** уведомление о
   пополнении состава (симметрично тому, как уже работает удаление),
   чтобы их локальные списки не отставали.
3. Задел на будущее — рассмотреть периодическую сверку ростера
   (например, создатель/админ время от времени рассылает полный
   актуальный список всем, идемпотентно) на случай, если какое-то из
   точечных уведомлений потеряется — то же rationale, что и у
   health-check идеи для 1:1 контактов выше в этом файле.

**Известные пробелы (сводка)**:
- Главная находка выше — рассылка при добавлении участника не покрывает
  существующих членов группы, только вновь добавляемого. Реальный,
  воспроизводимый баг, не гипотеза.
- Групповой ключ (`groupKey`) хранится и передаётся как сырые байты —
  тот же уровень риска, что и приватный EC-ключ в бэкапе (см. сценарий
  выше), если устройство скомпрометировано.
- `group_reaction` (`MessengerService.kt:1901`) не проверяет подпись
  вообще (`onGroupReactionReceived` вызывается без верификации
  `CryptoManager.verify`, в отличие от `group_message`/`group_create`)
  — `❓`, не исследовано, насколько это осознанное решение (реакции
  менее чувствительны, чем текст) или недосмотр.

## Сценарий: panic wipe

Три независимых триггера ведут в **один и тот же** приёмник
(`WipeReceiver`, зарегистрирован статически в манифесте — работает
независимо от того, открыто ли приложение, `exported="false"`).

**Триггер 1 — panic-пароль на экране входа** (`LoginScreen.kt:175`):
пользователь вводит специальный пароль вместо обычного.
  ├─ **`UserStorage.isPanicPassword()` = true** → `onPanicMode()`
     (`MainActivity.kt:910`) → `isPanicMode=true`.
     ├─ **Устройство ещё не в decoy-режиме** →
        через 400 мс → `WipeManager.wipeForDecoyKeepAlive()` (см. ниже,
        это НЕ `wipe(HARD)`, отдельная функция).
     └─ **Устройство уже в decoy-режиме** (уже был вайп раньше) →
        вайп не повторяется, просто показывается decoy-экран — стирать
        уже нечего.
  └─ **Обычный пароль, но `UserStorage.isDecoyMode()` = true** → тоже
     `onPanicMode()`, но без вайпа (условие `!isDecoyMode` не
     выполняется) — устройство уже "чистое", штатный сценарий показа
     decoy после первого вайпа. Handled — не путать с триггером 1, это
     разные условия входа в один и тот же `onPanicMode()`.

**Триггер 2 — 5× громкость вниз при заблокированном экране**
(`EmergencyService.kt`, Accessibility Service): считает нажатия
`KEYCODE_VOLUME_DOWN` с дебаунсом 150 мс и таймаутом сброса счётчика
3 секунды.
  ├─ **`UserStorage.isEmergencyWipeEnabled() == false`** → сервис вообще
     не реагирует на клавиши, `return super.onKeyEvent(event)`. Handled.
  └─ **Включено, 5 нажатий за 3 секунды** → `sendBroadcast("com.subrosa.
     messenger.EMERGENCY_WIPE")` → `WipeReceiver` → см. триггер 3 (тот
     же код).

**Активация триггера 2 — многошаговый флоу** (`ProfileScreen.kt:726`,
Android 13+/TIRAMISU): переключатель "Экстренное стирание" при попытке
включить:
  ├─ **Accessibility Service уже включён в системе** → просто сохраняет
     флаг, работает сразу.
  └─ **Ещё не включён** → диалог с двумя кнопками — "Открыть настройки
     приложения" (нужно для Android 13+, где сайдлоуженные приложения по
     умолчанию получают "ограниченные настройки", accessibility нельзя
     включить, пока пользователь вручную не снимет это ограничение через
     меню "⋮" в App Info) и "Открыть настройки Accessibility" (собственно
     включить сервис). Это тот самый флоу, который **разработчик сам
     запутался включать**, тестируя вживую (см. более раннюю запись в
     этом файле). Есть автоматическая защита от рассинхрона: при каждом
     возврате в Profile (`ON_RESUME`) состояние переключателя сверяется
     с реальным системным состоянием сервиса и автоматически гасится,
     если сервис на самом деле не включён — так что UI не может врать о
     состоянии, но сам процесс включения остаётся многошаговым.

**Триггер 3 — уведомление "Экстренное стирание"**
(`PanicNotificationManager`, тот же `ACTION_EMERGENCY_WIPE`): показывается
отдельно (при подозрительной активности через `ParanoidMode`/детект
вторжения — сценарий детекта не описан отдельно, см. заглушку ниже).
  ├─ **`UserStorage.getPanicButtonDecoy() == true`** (включён режим
     "показать decoy вместо явного вайпа") → `ParanoidMode.
     activateFromNotification()`, запускается приложение, и **через
     600 мс** → `WipeManager.wipeForDecoyKeepAlive()`.
  └─ **Обычный режим** → сразу `WipeManager.wipe(context, Level.HARD)`.

**Что реально стирается — три разных функции, не просто "уровни"**:
  - **`wipe(HARD)`**: `SessionKeyManager.deleteAllSessions()`,
    `CryptoManager.deleteKeys()`, AndroidKeyStore-алиасы SMK, весь
    `shared_prefs`/`filesDir`/`cacheDir`/`databases`/`app_webview`/
    `no_backup`/внешние файлы приложения — затем **убивает процесс**
    (`Process.killProcess`). Опционально (`withDecoy=true`) сохраняет
    ДО стирания username/password_hash/calc_disguise в отдельный
    `beacon_recovery` prefs, чтобы после перезапуска показать
    правдоподобный "чистый" вход.
  - **`wipeForDecoyKeepAlive()`**: делает **то же самое стирание**, но
    **не убивает процесс** — приложение продолжает работать (иначе
    Activity, которая уже открыта в момент срабатывания, вылетела бы,
    выдав тревогу вместо тихого перехода в decoy). Это то, чем
    отличаются триггеры 1 и 3(decoy-ветка) от обычного HARD.
  - **`wipe(NUCLEAR)`**: та же зачистка ключей + `SessionKeyManager`,
    затем `ActivityManager.clearApplicationUserData()` (системный вызов
    ОС — стирает вообще всё, включая то, что не перечислено вручную;
    при сбое — падает обратно на `hardWipe()`). Используется только
    dead man's switch (см. следующий сценарий) — ручные триггеры его не
    используют вообще.
  - **`Level.SOFT`**: `❓` **мёртвый код** — существует в `enum
    Level` и в `when`-ветке `wipe()`, но нигде в проекте не вызывается
    ни одним триггером. Не удалён, не документирован как
    "зарезервировано на будущее" или как то, что нужно выпилить.

**Известные пробелы**:
- `Level.SOFT` — мёртвая ветка, не подключена ни к одному UI/триггеру.
  Не решено, оставлять ли как задел или выпилить.
- Многошаговый флоу активации триггера 2 остаётся объективно сложным для
  обычного пользователя (не UX-баг сам по себе — во многом навязан
  ограничениями Android 13+, но стоит рассмотреть более понятный
  пошаговый визард в приложении вместо голого системного диалога).
- Не проверено вживую (см. testing checklist в
  `ISSUE_backup_identity_hijack.md`): что именно каждый уровень вайпа
  реально стирает на настоящем устройстве, не только по чтению кода.

## Сценарий: dead man's switch

**Триггер**: включён в настройках, интервал N минут/часов
(`DeadMansSwitchManager.enableMinutes()`).

**Шаг 1 — обычная жизнь, check-in**: любой удачный вход по паролю
обновляет `lastCheckin` и **пересоздаёт** таймер вылета
(`checkIn()` → отменяет старые алармы → если включён, планирует
`ACTION_DMS_FIRE` через `lastCheckin + intervalMinutes`).

**Шаг 2 — интервал истёк без check-in** (`ACTION_DMS_FIRE`, ловится
`WipeReceiver`, будильник через `AlarmManager`, работает даже если
приложение не запущено): показывается предупреждающее уведомление с
кнопкой "Я здесь" + планируется `ACTION_DMS_WIPE` через `GRACE_PERIOD_MS`
(15 минут).
  ├─ **Пользователь нажимает "Я здесь" в течение 15 минут** →
     `ACTION_DMS_CHECKIN` → `checkIn()` → алармы отменены, уведомление
     скрыто, обычный цикл продолжается. Handled.
  └─ **15 минут прошло, реакции нет** → `ACTION_DMS_WIPE` →
     `WipeManager.wipe(context, Level.NUCLEAR)`. Безвозвратно —
     `clearApplicationUserData()`.

**Шаг 3 — избыточная проверка при живом запуске приложения**
(`MainActivity.onResume()`, независимо от алармов): при каждом возврате
в приложение отдельно проверяется `now - lastPasswordEntry >
timeoutWipeHours` и, если превышено, **немедленно** вызывает
`triggerWarningImmediate()` — тот же эффект, что и штатное срабатывание
будильника. Это осознанный дублирующий защитный механизм на случай,
если системный алярм по какой-то причине не сработал (устройство было
выключено дольше интервала, ОС убила alarm и т.п.) — при следующем же
открытии приложения несостыковка всё равно будет поймана. `❓` — не
исследовано, что произойдёт, если приложение вообще ни разу не
открывается достаточно долго (телефон лежит выключенным дольше и
интервала, и grace period) — сработает ли будильник корректно после
включения телефона (Android может отложить неточные alarm'ы), или
устройство останется в "подвешенном" состоянии до следующего открытия
приложения.

**Известные пробелы**:
- Как и в panic wipe — не проверено вживую, что NUCLEAR действительно
  добирается до всех данных на реальном устройстве.
- `❓` выше — поведение при очень долгом простое устройства (выключен
  телефон), полагается ли защита только на "проверку при следующем
  открытии" или таймер действительно может сработать в фоне.
- Тестовые тиры 15/30 минут (добавленные в этой же сессии проекта) не
  протестированы вживую на реальном срабатывании будильника и вайпа —
  см. testing checklist.

## Сценарий: отправка фото / файла / голосового сообщения

**Триггер**: пользователь выбирает вложение и отправляет.

**Шаг 1 — какой путь выбора вложения** (три разных UI-триггера, три
разных набора обработки):
  ├─ **Фото через пикер "Фото"** (`selectedPhotoUri`, `ChatScreen.kt`) →
     `MediaStore.Images.Media.getBitmap()` декодирует в `Bitmap`, затем
     `compressImageForSend()` — пересжатие в WebP. EXIF физически не
     попадает в `Bitmap` (пиксели без метаданных) — эта ветка уже была
     безопасна архитектурно, до всякого явного стриппинга. → Шаг 2.
  ├─ **Файл через универсальный пикер** (`selectedFileUri`) → сырые
     байты читаются как есть. **Если MIME `image/*`** → `stripExif()`
     (уже реализовано в этой сессии — чистит GPS/устройство/таймстампы,
     сохраняет ориентацию). Иначе — байты как есть, без изменений. →
     Шаг 2.
  └─ **Голосовая запись** (`AudioHelper`) → запись в `.3gp`, кодирование
     в Base64 напрямую, без промежуточного сжатия/переупаковки. → своя
     ветка отправки (`sendVoice`), не через `sendImage`/`sendFile`.

**Шаг 2 — есть ли кэшированный ключ получателя** (`sendImage`/`sendFile`/
`sendVoice`, `MessengerService.kt`):
  ├─ **И классический, и PQ-ключ в кэше** → шифрование и отправка сразу
     (см. шаг 3).
  ├─ **Ключа нет (фото/файл)** → запрос бандла (`requestPrekeyBundle`),
     вложение встаёт в очередь (`pendingImages`/`pendingFileSends`),
     отправка автоматически повторяется, когда бандл придёт. Это уже
     чинили в этой же сессии проекта (`SECURITY.md`, "photos and files
     silently failed to send" — было полностью тихо, без ретрая, теперь
     с ретраем).
  └─ **Ключа нет (голосовое)** → `❓` **известный, задокументированный,
     не починенный баг** (`SECURITY.md`, тот же пункт, "Related, not yet
     fixed"): `sendVoice` кладёт неудавшуюся отправку в
     `pendingSessionMessages` — очередь для **текстовых** сообщений,
     закодировав голосовое как строку `"__voice__|id|duration|base64"`.
     Когда очередь этой строкой воспроизводится через обычный текстовый
     путь (`sendWithForwardSecrecy`), получатель увидит **буквально этот
     текст как обычное сообщение**, а не голосовое. Нужна отдельная
     очередь по аналогии с `pendingImages`/`pendingFileSends` — не
     сделано.

**Шаг 3 — шифрование и упаковка** (`CryptoManager.encryptFile()` для
фото/файла, `CryptoManager.encrypt()` для голосового): гибридный
классический+PQ, плюс паддинг контента (1024–4096 случайных байт для
файлов, `SECURITY.md`, раздел про паддинг). Затем чанкование
(`120_000` символов Base64 на чанк, партиями по 5 с задержкой 30 мс
между партиями — видимый серверу ритм отправки, не сглажен).

**Шаг 4 — что уходит в каждом `file_chunk`-пакете, НОВАЯ находка**:
```
type, from, to, file_id, file_name, chunk_index, total_chunks, data, signature, encrypted
```
`data` — зашифровано (гибрид classic+PQ). **`file_name` — в открытом
виде**, отдельным полем того же JSON-пакета, который заворачивается в
`anon_message` (анонимность по токену/маршруту есть, но сам JSON-payload
не шифруется целиком — шифруется только `data`). Сервер, даже при
полностью анонимной доставке (когда есть anon-токен), **видит
оригинальное имя файла в чистом виде** на каждой передаче. Плюс
`total_chunks`/размер чанка дают приблизительный размер файла — паддинг
пакета до 512-байтных корзин (`addPadding`, уже реализован) на этом
масштабе (десятки/сотни КБ на чанк) погоды не делает, это заметно
только для мелких текстовых сообщений.
  - Сравнение: у `sendImage`/`sendVoice` такой утечки нет — `image_chunk`
    не несёт имени файла вообще (у фото его в принципе нет как
    отдельного атрибута), `voice`-пакет несёт `duration` в открытом виде
    (секунды записи) — тоже утечка метаданных, но существенно менее
    чувствительная, чем произвольное имя файла.
  - `❓` **не продумано, не зафиксировано нигде раньше в документации**:
    название файла может само по себе быть чувствительным
    ("compromat_source_ivanov.pdf") — то есть даже при полном соблюдении
    анонимной маршрутизации + шифрования содержимого, метаданные
    вложения раскрывают то, что должны были скрыть паддинг и
    обфускация имени на диске (уже сделанная в этой сессии — но она
    касалась *локального хранения*, а не самого протокола передачи).

**Шаг 5 — получатель собирает чанки** (`file_chunk`/`image_chunk`
handler): подпись каждого чанка проверяется (`CryptoManager.verifyChunk`)
до накопления; `file_id`/`file_name`, пришедшие от контакта, теперь
санитизируются перед построением пути на диске (path traversal —
починено в этой сессии), путь на диске — непрозрачный `blobs/<id>.enc`
(обфускация имени на диске — тоже починено в этой сессии). Полученное
`file_name` из пакета используется только как **отображаемое** имя в UI
— то, что оно пришло в открытом виде по сети, эта более поздняя починка
не отменяет (обфускация на диске ≠ обфускация в протоколе передачи).

**Известные пробелы (сводка)**:
- **Новое**: `file_name` передаётся в открытом виде в каждом
  `file_chunk`-пакете — единственный тип вложения с такой утечкой
  метаданных, не закрыто. Возможное решение (не реализовано): либо не
  посылать оригинальное имя вообще, заменяя его на generic-плейсхолдер
  + расширение по MIME (аналогично тому, как уже обфусцировано хранение
  на диске), либо шифровать это поле тем же ключом, что и `data`.
- **Известное, задокументированное**: `sendVoice` при отсутствии ключа
  получателя ломает воспроизведение через неправильную очередь
  ретраев — нужна отдельная voice-очередь.
- `duration` в `voice`-пакете — метаданные в открытом виде, менее
  чувствительно, не приоритет.
- Ритм отправки чанков (5 штук / 30 мс пауза) — заметный паттерн
  трафика для крупных вложений, не смягчается паддингом пакетов (тот
  расчитан на мелкие текстовые сообщения).

## Сценарий: ротация SPK/OPK

Два независимых механизма гигиены ключей — ротация SPK по времени и
пополнение пула OPK по расходу — и оба **проверяются только в момент
переподключения/инициализации**, не на постоянном фоновом таймере.

**Шаг 1 — ротация SPK, проверяется при `initialize()`/`reloadSessionsIfNeeded()`**
(`SessionKeyManager.kt`, `SPK_ROTATION_INTERVAL_MS = 7 дней`):
  ├─ **С момента `spk_created_at` прошло больше 7 дней** → старый SPK
     сохраняется как "предыдущий" (действителен ещё 14 дней —
     `SPK_GRACE_PERIOD_MS`, чтобы уже начатые handshake завершились),
     генерируется новый SPK + новая пара PQ-KEM, привязанная к нему.
  └─ **Меньше 7 дней** → используется существующий SPK как есть.

  `❓` — **проверка происходит только когда `initialize()`/
  `reloadSessionsIfNeeded()` реально вызываются** — то есть при старте
  сервиса, реконнекте, разблокировке SMK. Если приложение (foreground
  service) проработало без перезапуска дольше 7 дней подряд, никакого
  отдельного таймера, который бы это заметил, нет — ротация просто
  отложится до следующего события, которое повторно вызовет
  `initialize()`. На практике реконнекты по сети случаются часто
  (мобильная связь редко держит один WS-коннект неделями), так что
  вряд ли фатально, но это не осознанно спроектированная гарантия, а
  побочный эффект частоты реконнектов.

**Шаг 2 — публикация бандла на сервер** (`publishPrekeyBundle()`,
`MessengerService.kt:1023`): вызывается **один раз, сразу после
установления WS-соединения** — не периодически.

**Шаг 3 — расход OPK на сервере** (`server.py`, `get_prekey_bundle`
handler): каждый раз, когда кто-то запрашивает бандл этого пользователя,
сервер выдаёт **один** OPK из списка и удаляет его из своей копии.
  ├─ **Остаток OPK ≥ `OPK_LOW_WATERMARK` (5)** → просто отдаёт бандл,
     ничего больше не происходит.
  └─ **Остаток < 5** → сервер **сам, проактивно**, шлёт владельцу бандла
     `{"type": "prekey_bundle_request"}` — сигнал "пополни бандл".

**Шаг 4 — как клиент реагирует на этот сигнал — АСИММЕТРИЯ МЕЖДУ
ПЛАТФОРМАМИ, новая находка**:
  ├─ **Desktop** (`WebSocketClient.kt:1375`) → `"prekey_bundle_request"
     -> publishPrekeyBundle()` — обрабатывает правильно, republish
     сразу по сигналу сервера.
  └─ **Android** (`MessengerService.kt`, диспетчер входящих типов) →
     **обработчика для `prekey_bundle_request` нет вообще.** Не
     найдено ни одного вхождения в проекте под Android. Сигнал сервера
     тихо падает в default-ветку диспетчера и ни на что не влияет.

**Чем это грозит на практике**: локальный пул OPK на Android
пополняется до 10 штук только при `initialize()` (`refillOpkPool
(targetCount = 10)`), и republish на сервер происходит только при новом
WS-подключении (шаг 2). Значит между моментом, когда у Android-клиента
на сервере кончаются OPK, и следующим реконнектом, **все новые X3DH
handshake с этим пользователем идут по already-existing протокольному
fallback "без OPK"** (`SessionKeyManager` это уже поддерживает —
не крах, деградация форвард-secrecy на один компонент DH, не потеря
шифрования целиком). Не катастрофа, но однозначно не то поведение,
которое сервер пытался вызвать своим сигналом, и не то, что уже
корректно работает на Desktop.

**Известные пробелы**:
- **Главная находка**: `prekey_bundle_request` не обработан на Android
  вообще — асимметрия платформ, Desktop делает правильно, Android нет.
  **Предложенное решение**: добавить в диспетчер `MessengerService.kt`
  ветку `"prekey_bundle_request" -> publishPrekeyBundle()`, зеркально
  Desktop. Минимальное, локализованное изменение.
- Ротация SPK и republish бандла оба привязаны к событиям
  подключения/инициализации, а не к независимому таймеру — работает
  на практике благодаря частым реконнектам, но не гарантированно.

## Сценарий: угон сессии (session_conflict)

**Триггер**: второе устройство (может быть легитимным вторым телефоном
владельца, а может — атакующим, восстановившим identity из украденного
бэкапа, см. сценарий "Экспорт/восстановление бэкапа") подключается и
регистрируется под тем же fingerprint, что уже онлайн.

**Шаг 1 — сервер получает `register`** (`server.py:943`): fingerprint
вычисляется из публичного ключа, доказанного в handshake (не может быть
подделан — уже почищенная дыра, `SECURITY.md`, пункт про identity-binding).
  ├─ **Fingerprint уже онлайн, `device_id` совпадает** → это то же
     устройство переподключается (например, после сетевого сбоя) →
     `[RECONNECT]`, старое WS-соединение просто закрывается, новое
     занимает его место. Не конфликт. Handled.
  └─ **Fingerprint уже онлайн, `device_id` ДРУГОЙ** → `[SESSION_CONFLICT]`
     → см. шаг 2.

**Шаг 2 — сервер вытесняет старую сессию** (`server.py:971-983`):
  - Старому WS-соединению шлётся `{"type": "session_conflict", "ts":
    <момент>}`, затем соединение закрывается сервером.
  - **Параллельно** (не вместо, а дополнительно) — если у старой сессии
    есть сохранённый FCM-токен, туда же уходит **видимое** push-
    уведомление ("Активна сессия на другом устройстве") — специально
    сделано, чтобы владелец узнал, даже если приложение свёрнуто/убито,
    не только пока WS открыт. Это уже сделанная в этой сессии проекта
    доработка.

**Шаг 3 — старое устройство обрабатывает `session_conflict`**
(`MessengerService.kt:1152`): `isConnected=false`, соединение закрыто,
показывается уведомление с таймстампом конфликта.

**Шаг 4 — НОВАЯ находка: что происходит дальше, автоматически, без
участия пользователя.** `connect()` — это самоподдерживающийся цикл
(`while (scope.isActive) { ... }`), который внутри себя ждёт, пока
`isConnected` не станет false, затем **безусловно** переподключается
через 3 секунды — **без проверки причины разрыва**. Обычный обрыв связи
и `session_conflict` обрабатываются этим циклом абсолютно одинаково.
  ├─ **Старое (вытесненное) устройство переподключается через ~3с** →
     повторно шлёт `register` с тем же (своим) `device_id` → сервер
     видит: fingerprint уже онлайн (это подключилось устройство B —
     атакующее), `device_id` не совпадает → **сам процесс с шага 2
     повторяется в обратную сторону** — теперь уже B получает
     `session_conflict`.
  └─ **B (если это реальный атакующий, а не просто второй телефон
     владельца) тоже настроен на автопереподключение** → тот же цикл →
     кикает обратно A.

  Получается **"война переподключений"**: оба устройства попеременно
  выбивают друг друга каждые ~3+ секунды, пока один из них не
  перестанет пытаться (пользователь закроет приложение / выключит
  телефон / осознанно остановит попытки). Ни то, ни другое устройство
  не выигрывает "по праву" — сервер отдаёт слот тому, кто подключился
  последним, чисто по времени, без понятия "легитимный владелец".

  **Update — частично смягчено device-gated регистрационным TOTP**
  (`server.py`, `user_totp_secrets` + `is_new_device` проверка при
  `register`): если у аккаунта включён TOTP, **новый `device_id`**
  обязан прислать верный TOTP-код в `register`, иначе сервер отвечает
  `totp_required` и не пускает это устройство вообще — не давая ему
  даже войти в цикл войны переподключений. Это не решает войну для
  случая, когда TOTP **не включён** (по умолчанию выключен). Важная
  деталь: бэкап (см. сценарий "Экспорт и восстановление бэкапа")
  переносит только флаг `totp_enabled`, **не** сам секрет — атакующий с
  украденным файлом бэкапа и паролем к нему всё равно не пройдёт
  `totp_required`, если у владельца TOTP включён, ровно тот случай, где
  device-gated TOTP реально помогает. Не помогает только против
  человека, у которого есть сразу и файл, и пароль, и сам TOTP-секрет
  (например, скриншот QR-кода) — три независимых фактора сразу, что уже
  ближе к "потерял вообще всё".

  **Это не ухудшает саму компрометацию** (атакующий, получивший
  identity, уже имеет полный доступ независимо от исхода этой войны) —
  но `❓` **не спроектировано и не задокументировано нигде раньше**: (а)
  создаёт заметную нагрузку/шум на сервер и оба устройства без явного
  предела попыток; (б) с другой стороны, у этого есть неожиданный
  побочный плюс — повторяющиеся уведомления `session_conflict`
  оказываются даже более заметным сигналом тревоги для легитимного
  пользователя, чем один разовый кик, просто как случайное следствие
  архитектуры, а не осознанный дизайн.

**Шаг 5 — что первое (вытесненное легитимное) устройство МОЖЕТ и НЕ
МОЖЕТ сделать**:
  - **Может**: увидеть уведомление с таймстампом, узнать, что кто-то
    ещё использует его identity.
  - **Теперь может — сделано**: кнопка "🔄 Меня скомпрометировали" в
    Profile (`ProfileScreen.kt`, `BackupManager.resetCompromisedIdentity()`)
    — жжёт текущую identity (EC-ключ, контакты, чаты, группы, сессии,
    анон-токены) целиком и переводит устройство на `RegisterScreen` для
    создания новой identity с нуля. Это технически лишает атакующее
    устройство доступа **к аккаунту жертвы** (сервер видит новую
    identity, старый fingerprint для владельца больше не используется),
    но **не** отзывает старый fingerprint у атакующего — тот, у кого уже
    есть старый приватный ключ, по-прежнему может подключаться и
    представляться этим fingerprint'ом сколько угодно, просто владелец
    им больше не пользуется. См. отдельный сценарий "Смена identity
    после компрометации" ниже. Дизайн намеренно "дешёвый" (решение
    пользователя): без попытки понять, какое устройство легитимно, без
    уведомления старых контактов через (возможно скомпрометированный)
    старый ключ, без переноса истории — контакты нужно будет заново
    обменяться инвайт-кодом.

**Известные пробелы**:
- **Новое**: автопереподключение не различает "обычный обрыв связи" и
  "меня только что выбили session_conflict'ом" — приводит к
  automatic reconnect war между двумя копиями одной identity. Не
  вредит компрометации сильнее (она уже произошла), но не
  спроектированное, шумное поведение.
  **Возможное решение (не реализовано, только идея)**: при получении
  `session_conflict` — не переподключаться немедленно тем же циклом,
  что и при обычном разрыве; вместо этого требовать явного действия
  пользователя (например, экран "кто-то ещё вошёл в ваш аккаунт —
  переподключиться / разобраться"), прежде чем снова слать `register`.
- ~~Нет управляемого флоу ротации identity после компрометации, только
  уведомление~~ — **закрыто**, см. шаг 5 выше и отдельный сценарий
  "Смена identity после компрометации" ниже.

## Сценарий: смена identity после компрометации ("Меня скомпрометировали")

**Триггер**: пользователь заходит в Profile → нажимает "🔄 Меня
скомпрометировали" (отдельная кнопка от "❗ Это не я!" — см. ниже, чем
они различаются) → подтверждает диалог с явным предупреждением.

**Дизайн-решение пользователя, дословно**: "мы просто обнуляем
фингерпринт и всё что с ним связано, дальше только новый аккаунт" — без
попытки выяснить, какое из устройств легитимно (это структурно
невозможно понять с сервера), без уведомления старых контактов через
потенциально скомпрометированный старый ключ, без переноса истории.

**Шаг 1 — подтверждение** (`ProfileScreen.kt`, `showCompromisedConfirm`):
  ├─ **Отмена** → ничего не происходит. Обработано.
  └─ **Подтверждено** → `BackupManager.resetCompromisedIdentity(context)`.

**Шаг 2 — что стирается** (`BackupManager.kt`):
`UserStorage.resetIdentityFields()` (только identity-поля из
`user_prefs` — username/user_id/password_hash/display_name/invite_code/
avatar — **не** весь файл целиком, см. следующий шаг) + чаты/очередь
сообщений, `GroupManager.clearAll()`, `AnonTokenManager.clearAll()`,
`SessionKeyManager.deleteAllSessions()`, `CryptoManager.deleteKeys()`
(EC-ключ, реально нужный шаг — без него `generateKeyPair()` на
следующем экране регистрации был бы no-op, см. шаг 4).

**Шаг 3 — что НЕ стирается, специально**: TOTP-секрет, пароль
приложения, настройки паники/автовайпа/dead man's switch, calculator
disguise, тема/язык. Это отличает эту кнопку от существующей "❗ Это не
я!" (`WipeManager.hardWipe()`, тот же экран) — та вызывает
`clearApplicationUserData()` и стирает вообще всё, задумана как duress-
кнопка (принуждение отдать пароль), а не как ответ на "мой ключ мог
утечь". Компрометация messenger-identity не означает, что и локальные
настройки устройства скомпрометированы — эта кнопка на них не
покушается.
  ├─ **SMK (StorageKeyManager) при этом тоже разбирается специально** →
     `smk_config` prefs + AndroidKeyStore-алиас `beacon_smk_wrap`
     удаляются, `StorageKeyManager.lock()`. Без этого при следующей
     регистрации новый пароль не переобернул бы SMK (в `RegisterScreen`
     `StorageKeyManager.setup()` вызывается только если `!isSetup()`) —
     старый SMK остался бы завязан на старый пароль, и расшифровка
     сообщений на новой identity сломалась бы. Найдено и предотвращено
     до реализации, не задним числом.

**Шаг 4 — процесс убивается** (`Process.killProcess`, тот же паттерн,
что у `WipeManager.hardWipe()`) — гарантирует отсутствие "залипшего" в
памяти состояния identity в `MessengerService`/менеджерах сессий, вместо
попытки аккуратно перезапустить каждый компонент по отдельности.

**Шаг 5 — холодный старт**: `UserStorage.isRegistered()` теперь `false`
(проверяет только наличие `username`) → навигация приложения
естественно приводит на `RegisterScreen`, тот же путь, что при первой
установке — `CryptoManager.generateKeyPair()` генерирует
**действительно новый** ключ (старый уже удалён шагом 2, а не просто
проигнорирован — `generateKeyPair()` no-op, если алиас/файл ключа уже
существует), новый пароль (может совпадать со старым или нет — SMK
переобернётся, см. шаг 3), новый инвайт-код.

**Известные пробелы**:
- Контактам старой identity нужно вручную сообщить о смене (вне
  протокола — WhatsApp, лично, любой другой канал) и обменяться новым
  инвайт-кодом — это осознанный компромисс дизайна ("дёшево"), не
  недосмотр.
- Старый fingerprint остаётся действительным для того, кто владеет
  старым приватным ключом (если это атакующий) — эта кнопка защищает
  аккаунт **владельца** вперёд, не отзывает прошлый ключ у атакующего
  технически (отозвать чужой приватный ключ на сервере невозможно в
  этой архитектуре — сервер не может отличить "легитимного" держателя
  ключа от нелегитимного, см. сценарий "Угон сессии").
- Не проверено вживую на устройстве — только `compileDebugKotlin`.

## Сценарий: восстановление бэкапа на втором, уже активном устройстве

Отличие от сценария "Экспорт/восстановление бэкапа" выше: там речь про
устройство, куда бэкап приносит identity впервые. Здесь — устройство,
которое **уже залогинено и активно работает под своей identity** (свой
`MessengerService` уже запущен, свой WS-коннект открыт, свои сессии
живы) в момент, когда пользователь идёт в Profile → Backup → Импорт.

**Триггер**: то же самое действие импорта (`BackupManager.importBackup()`,
см. предыдущий сценарий, шаги 5-7) — но на устройстве, где
`MessengerService` уже запущен и подключён.

**Шаг 1 — импорт меняет то, что лежит на диске**: `UserStorage.setUserId()`
перезаписывает identity в постоянном хранилище, `CryptoManager`'ов
приватный ключ в `EncryptedSharedPreferences` тоже перезаписан на ключ
из бэкапа. Это происходит **синхронно**, прямо во время вызова
`importBackup()` — и теперь, **в отличие от прошлой версии этого
сценария, `BackupScreen.kt` после успешного импорта форсирует полный
перезапуск `MessengerService`** (`context.stopService(...)` +
`context.startForegroundService(...)`,
[BackupScreen.kt:103](app/src/main/java/com/example/test/BackupScreen.kt:103)),
именно чтобы `onStartCommand()` пересчитал `username`/identity из уже
изменённого хранилища, а не продолжал жить со старым кэшем. Шаг 2 ниже —
это уже описание того окна рассинхрона, которое существовало бы **без**
этого форс-перезапуска; теперь оно закрыто на уровне
"перезапустить сервис", но что происходит **внутри** самого окна
перезапуска (миллисекунды между stop/start) не проверено вживую.

**Шаг 2 — окно рассинхрона между уже работающим сервисом и только что
изменённым хранилищем — теперь закрыто форс-перезапуском из шага 1;
раньше выглядело так:**
`MessengerService`'s `username` (переменная в памяти, используется как
поле `from` в каждом исходящем пакете и как identity, под которой открыт
текущий WS-коннект) устанавливается **один раз за вызов**
`onStartCommand()` (`MessengerService.kt:570`) — читает текущий публичный
ключ из `CryptoManager`, вычисляет fingerprint, кэширует в `username`.
Сам вызов `importBackup()` этот код не трогает — если бы `BackupScreen.kt`
**не** форсировал перезапуск (шаг 1), уже работающий сервис не узнал бы,
что что-то изменилось, до следующего органического перезапуска.
  ├─ **Гипотетически, если бы сервис не перезапускался** → `❓`
     **потенциально сломанное состояние, теперь не воспроизводимо
     благодаря форс-перезапуску из шага 1, но задокументировано для
     понимания, зачем этот перезапуск вообще нужен**:
     `CryptoManager.sign()`/`encrypt()` читают приватный ключ из
     хранилища **при каждом вызове, без кэширования** (в отличие от
     `username`) — то есть подписи/шифрование сразу начинают
     использовать **новый** (импортированный) ключ, а поле `from` в
     исходящих пакетах и WS-сессия на сервере всё ещё числятся под
     **старой** identity этого устройства. Получатель видит `from:
     СТАРЫЙ_fingerprint`, но подпись сделана **новым** ключом — проверка
     подписи (`CryptoManager.verify(data, signature,
     публичный_ключ_СТАРОГО_fingerprint)`) должна провалиться, потому
     что фактически подписывал другой ключ. Сообщения в этом окне,
     скорее всего, либо не проходят проверку на приёме, либо (если
     получатель вообще не проверяет `from` строго) создают путаницу,
     кому реально принадлежит sender. Это не проверено на реальных
     устройствах — только прослежено по коду.
  └─ **После перезапуска сервиса** (пользователь закрыл и открыл
     приложение, или Android перезапустил процесс) → `onStartCommand()`
     отрабатывает заново, `username` пересчитывается из нового ключа,
     сервис переподключается — но это уже отдельный `register` с новым
     fingerprint'ом → см. сценарий "Угон сессии" **если у старой
     identity этого fingerprint'а на сервере в этот момент есть другая
     активная сессия где-то ещё** (например, оригинальное устройство,
     чей бэкап был восстановлен, всё ещё онлайн) — тогда это уже не
     просто "перезапуск", а настоящий session_conflict с третьим
     устройством.

**Шаг 3 — что происходит со старыми, уже живыми Double Ratchet-сессиями
этого устройства** (не той identity, что импортирована, а той, под
которой устройство работало ДО импорта): `SessionKeyManager`'ы сессии в
памяти (`sessions` map) **не очищаются и не трогаются импортом вообще** —
`importBackup()` их не касается. Получается: в памяти одновременно живут
сессии старой (до-импортной) identity этого устройства **и** старая
identity больше не совпадает с тем, что теперь лежит в хранилище как
"я". `❓` — не продумано, что происходит с исходящими/входящими
сообщениями для контактов старой identity после того, как identity
сменилась под ними.

**Известные пробелы**:
- ~~**Главная находка**: отсутствие какой-либо синхронизации между
  моментом импорта и уже запущенным `MessengerService`~~ — **закрыто**:
  `BackupScreen.kt` теперь принудительно перезапускает `MessengerService`
  сразу после успешного импорта (шаг 1 выше). Не проверено вживую на
  реальном устройстве, что окно между `stopService`/`startForegroundService`
  не оставляет короткий рассинхрон само по себе.
- Судьба старых Double Ratchet-сессий этого устройства при смене
  identity под ними — не продумано. Форс-перезапуск сервиса решает
  рассинхрон `from`-поля/ключа, но не чистит `SessionKeyManager`'ы
  сессии старой (до-импортной) identity этого устройства — они всё ещё
  не тронуты импортом.
- Каскадный случай "восстановление на активном устройстве +
  оригинальное устройство тоже ещё онлайн" сводится к сценарию "Угон
  сессии", но именно эта комбинация (не одно, а сразу два предыдущих
  сценария происходят одновременно) нигде отдельно не проверялась.

## Сценарий: регистрация на сервере — access-code allowlist + device-gated TOTP

Оба механизма — независимые опциональные ворота внутри одного и того же
обработчика `register` на сервере (`server.py`, вокруг строки 1195), но
проверяются последовательно, поэтому имеет смысл описать их одним
деревом. Оба — по умолчанию **выключены** (`SERVER_ACCESS_PROTECTED`
пустой; TOTP включается пользователем вручную в приложении).

**Триггер**: клиент подключился, прошёл ECDSA challenge-response
(fingerprint доказан), шлёт `register` с `public_key`, `device_id`,
опционально `access_code`/`totp_code`.

**Шаг 1 — вычисление fingerprint и privacy-инвариант**: `fingerprint =
sha256(public_key)[:8].hex().upper()`, обязан совпадать с ключом,
доказанным в handshake (`SECURITY.md`, identity-binding) — эта часть не
изменилась, всё новое ниже начинается уже после неё.

**Шаг 2 — access-code allowlist** (`SERVER_ACCESS_PROTECTED`):
  ├─ **Выключен на сервере** → пропуск, сразу к шагу 3. Обычный публичный
     сервер, задел на будущее, но по умолчанию открыт всем.
  ├─ **Включён, но `db_is_fingerprint_registered(fingerprint)` уже
     `true`** → пропуск, код не проверяется вообще — гейт только на
     **самую первую** регистрацию этого fingerprint'а в истории (не на
     каждый `register`, иначе убивал бы UX каждым переподключением).
  └─ **Включён, fingerprint регистрируется впервые** →
     `access_code` обязан быть непустым и пройти
     `db_check_and_consume_access_code()` (одноразовый, помечается
     использованным на этом же fingerprint'е):
       ├─ **Кода нет / неверный / уже использован** → сервер отвечает
          `access_code_required`, регистрация обрывается (`continue`).
          Android показывает Toast (`s.serversAccessCodeRequired`), поле
          `accessCode` в `ServerManager.Server` — заполняется через QR
          (сгенерированный офлайн на сервере, `admin_gen_codes.py`/сам
          `server.py` при старте) или загрузку картинки QR из файла.
       └─ **Код валиден** → потребляется (больше не годится), → шаг 3.
     Коды генерируются офлайн, никакого стороннего QR-сервиса — важное
     решение пользователя ("сторонний сервис — это утечка данных").

**Шаг 3 — device-gated TOTP** (`user_totp_secrets`, только если у
**этого** fingerprint'а вообще включён TOTP — большинство аккаунтов
здесь не задерживаются):
  ├─ **У аккаунта TOTP не включён** → пропуск, к шагу 4 (обычная логика
     `session_conflict`/`RECONNECT`, см. сценарий "Угон сессии").
  ├─ **TOTP включён, но `device_id` совпадает с уже известным для этого
     fingerprint'а** (`is_new_device == false`, обычное переподключение
     того же устройства) → пропуск, TOTP не спрашивается — иначе каждое
     переподключение по нестабильной сети требовало бы кода, что и было
     первой (отвергнутой) версией этой фичи, см. `feedback_totp_scope_
     clarification` в памяти проекта.
  └─ **TOTP включён, `device_id` новый для этого fingerprint'а**
     (именно то условие, которое иначе привело бы к `session_conflict`
     — см. "Угон сессии") → `totp_code` из `register` обязан пройти
     `totp_verify_and_consume()`:
       ├─ **Код неверный/отсутствует** → сервер отвечает
          `totp_required`, регистрация обрывается. Android:
          `totp_required` handler показывает запрос кода
          (`totpRequiredNotified`).
       └─ **Код верный** → одноразовое потребление (тот же TOTP-код
          повторно не сработает), → шаг 4, обычная логика вытеснения
          старой сессии.

**Шаг 4 — обычная логика `session_conflict`/`RECONNECT`** — см.
отдельный сценарий "Угон сессии" выше, отсюда без изменений.

**Известные пробелы**:
- Access-code и TOTP-секрет живут в разных хранилищах на сервере
  (SQLite таблицы `server_access_codes`/`registered_fingerprints` vs.
  in-memory `user_totp_secrets`, персистится отдельно) — не найдено
  проблем при чтении кода, но совместное поведение при рестарте сервера
  (in-memory `user_totp_secrets` подгружается заново из `loaded_totp` при
  старте, судя по `server.py:2604`) не проверялось вживую в этой сессии
  документации.
- ~~Desktop не обрабатывает ни `access_code_required`, ни
  `totp_required` вообще~~ — **закрыто**: `register()` теперь шлёт
  `access_code` (из нового поля в `ProfileScreen.kt`,
  `DesktopStorage["server_access_code"]`, одноразовый — сохраняется, но
  сервер его один раз потребляет и дальше игнорирует, как и на Android)
  и `totp_code` (если `TotpManager.isEnabled()` — Desktop включает TOTP
  только через `enable()` при импорте TOTP-защищённого бэкапа, отдельного
  экрана "включить TOTP" на Desktop, в отличие от Android, всё ещё нет).
  Оба типа отказа (`access_code_required`/`totp_required`) теперь
  обрабатываются в `WebSocketClient.kt` — `disconnect()` +
  `onChannelError` с понятным текстом, тем же путём, что и
  `session_conflict`. **Осталось не идеально**: `onChannelError` на
  Desktop сейчас подписан только диалогом создания канала
  (`CreateChannelDialog` в `ChatsScreen.kt`) — реального глобального
  баннера ошибок подключения на Desktop нет, так что при живом
  тестировании сообщение об отказе регистрации, скорее всего, никуда не
  попадёт в UI, только в stderr. Это уже осознанная граница этой правки
  (добавить обработчики протокола, не строить новую систему уведомлений
  с нуля), а не забытый пробел.
